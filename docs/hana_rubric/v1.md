Context activity answers "should this context see input at all"; the runtime answers "given input, what matches, and what is still held."

### Phase 1 — `bevy_kana`: `Keystroke`, `Modifiers`, and the chord parser · status: todo

#### Work Order

**Goal:** `"cmd-shift-p"` parses to a canonical `Keystroke` carrying a bevy `KeyCode` plus a modifier set, and renders back to a canonical string.

**Spec:**

Create `crates/bevy_kana/src/input/keystroke/` with `mod.rs` and `sequence.rs`. Add `mod keystroke;` to `crates/bevy_kana/src/input/mod.rs` and re-export the public types there, from `lib.rs`, and from the prelude.

**Not feature-gated.** Both intended consumers (hana, nateroids) need keyboard input, so gating buys nothing, and it costs nothing to ungate: keystroke parsing produces bevy `KeyCode` + modifiers and needs `bevy_input`, **not** `bevy_enhanced_input`. Ungating does not drag the optional dep into the default build. `keybindings.rs` stays behind the `input` feature, since it genuinely uses `bevy_enhanced_input`.

`mod.rs` holds `Keystroke` (the module-name type, so it lives at the root) and `Modifiers`. `Modifiers` stays in `mod.rs` under the field-type exception — you cannot read `Keystroke` without it. This is the one permitted deviation from "module roots are table-of-contents only."

- `Modifiers` — a set of `{ control, alt, shift, platform }`. `platform` is the Cmd/Ctrl abstraction; reuse the existing `PlatformShortcutMode` in `keybindings.rs:209-223` (`Command` on macOS, `Control` elsewhere, selected by `current()`) as the normalization authority rather than duplicating the `cfg!` test.
- `Keystroke` — `{ modifiers: Modifiers, key: KeyCode }`. Comparison and hashing are on the **canonical** value, never on source text.
- **Parser** — a tokenizer over a fixed modifier vocabulary, splitting on `-`, last token is the key. Accepted modifier spellings, all normalizing to the same canonical value: `cmd`, `super`, `win`, `platform` → platform modifier; `ctrl`, `control`; `alt`, `opt`, `option`; `shift`. Modifier order in the source string is irrelevant (`shift-cmd-p` == `cmd-shift-p`); canonical `Display` order is fixed (suggested: platform, ctrl, alt, shift, key).
- Left/right modifier spellings must not be able to slip through as distinct — normalize them to the same canonical modifier.
- Key-name vocabulary maps to `bevy::input::keyboard::KeyCode`. Cover letters, digits, function keys, arrows, and the named keys hana already binds (see `global_shortcuts.rs` reference for the in-use set). Unknown key names are a parse error naming the offending token, never a panic.
- Errors are a typed `KeystrokeParseError` carrying the offending token and its byte offset within the input string — Phase 6 needs the offset for source-located diagnostics.

`sequence.rs` holds `KeystrokeSequence` — an ordered, **non-empty** sequence of `Keystroke`. The non-empty invariant is enforced by construction (private field, fallible constructor), not by convention. Parse from a space-separated string (`"g g"`, `"cmd-k l"`). `Display` round-trips.

**Write our own test cases.** Zed's tests are copyrightable; reimplementation is from observed behavior only.

### Phase 2 — `bevy_kana`: `SequenceMatcher<T>` · status: todo

#### Work Order

**Goal:** a prefix-indexed matcher that consumes completed `Keystroke` values and yields opaque `T` indices, with pending state and timeout-driven resolution.

**Spec:**

Create `crates/bevy_kana/src/input/keystroke/sequence_matcher.rs` holding `SequenceMatcher<T>`, `MatchOutcome`, and `PendingSequence`. The file is named for its anchor type, not `matcher.rs`; `MatchOutcome` and `PendingSequence` are its return and field types.

**Domain-free.** The matcher knows nothing of JSON, commands, conditions, tombstones, or `World`. It returns opaque `T` and **takes its timeout as an input parameter** rather than owning a policy value.

**Input boundary — fixed now so deferred simultaneous chords stay additive.** `SequenceMatcher<T>` consumes *completed canonical `Keystroke` values*, never raw key edges. If simultaneous chords (`"j+k"`) are ever built, they arrive as one preprocessing stage beside it (`keystroke/chord.rs` + `keystroke/simultaneous_matcher.rs` emitting a completed `Keystroke`), and `sequence.rs` plus the prefix/timeout behavior are untouched. Had the matcher consumed key edges, adding chords would mean rewriting it, because simultaneity timing and sequence-prefix timing would share one state machine.

**Construction:** built from a set of `(KeystrokeSequence, T)` pairs into a prefix index keyed by canonical strokes. Construction is the only place that allocates or scans; matching does neither.

**Multistroke timing — the required behavior:**
- When both `g` and `g g` are live, **defer** `g`. Fire it on timeout.
- On a non-matching next stroke, **fire the deferred command and reprocess the unmatched stroke once from the root** — two physical strokes can therefore invoke two commands, which is the conventional behavior.
- Reload, a context change, and the recovery chord all **cancel pending state without firing the deferred command**. Expose this as an explicit `cancel_pending()` that discards rather than resolves.
- When no longer sequence survives, a complete short match fires immediately — no timeout wait.

`MatchOutcome` must distinguish at minimum: an immediate match (`T`), a deferred-but-complete match now pending a longer candidate, pending-with-no-match-yet, an unmatched stroke (with any deferred `T` to fire first, plus the stroke to reprocess), and no-match-and-nothing-pending.

**Input-path budget applies here:** on a key edge inspect only current prefix candidates; check the timeout only while a sequence is pending. No allocation, no string parsing, no full scan.

**Files:**
- `crates/bevy_kana/src/input/keystroke/sequence_matcher.rs` — create
- `crates/bevy_kana/src/input/keystroke/mod.rs` — add `mod sequence_matcher;` and re-export `SequenceMatcher`, `MatchOutcome`. `PendingSequence` stays private unless it appears in the public outcome.
- `crates/bevy_kana/src/input/mod.rs`, `crates/bevy_kana/src/lib.rs` — re-export

**Constraints from prior phases:**
- Phase 1 built `Keystroke` (canonical, `{ modifiers: Modifiers, key: KeyCode }`) and `KeystrokeSequence` (non-empty by construction) in `crates/bevy_kana/src/input/keystroke/`. The module is **not** feature-gated; `keybindings.rs` remains behind `input`.
- Comparison and hashing are on canonical values, never source text — the prefix index keys on canonical strokes.

**Acceptance gate:** `verify.sh check|test|lint bevy_kana` green. Tests prove: `g` alone fires immediately when no longer sequence exists; `g` defers when `g g` is live and fires on timeout; `g` + a non-matching stroke fires `g` **and** reprocesses the stroke from the root, yielding two outcomes; `cancel_pending()` discards without firing; a three-stroke sequence resolves; two sequences sharing a two-stroke prefix disambiguate on the third. Assert no allocation on the steady-state match path (construct once, match many).

### Phase 4 — `hana_rubric`: command registry, `Command` trait, `command!` macro · status: todo

#### Work Order

**Goal:** `command!` declares an input action, a semantic event, an id, authored palette text, and a capability in one invocation; a validated id → registration table is built at startup and dispatches by name.

**Spec:**

**The registry holds semantic command *events*, not input actions (R2).** `"camera::home"` resolves to the `bevy_kana` `event!` type (e.g. `CameraHomeEvent`), not the `action!` input-action marker. The command events already derive `Reflect` with `#[reflect(Event)]`, so `ReflectEvent::trigger` fires them by name at runtime — the same mechanism BRP uses (`TypeRegistration::data::<ReflectEvent>()` then `ReflectEvent::trigger`, `bevy/crates/bevy_ecs/src/reflect/event.rs:67`; BRP's `process_remote_trigger_event_request`, `bevy/crates/bevy_remote/src/builtin_methods.rs:1480`).

**Do not plan on dynamically emitting `Start<A>`.** `bevy_enhanced_input::Start<A>` derives only `EntityEvent` — no `Reflect`, no `ReflectEvent` — and enhanced-input's dynamic `ActionFns` table is private. A registry of input actions has no supported way to invoke what it resolved.

`src/command/reflect_command.rs` — the `Command` trait, its `#[reflect_trait]` machinery, the `ReflectCommand` type data, and the `command!` macro. The trait lives here, not in `command/mod.rs`: the table-of-contents exception covers the module-name *type* and the types in its fields or enum payloads; a trait has no fields and does not anchor the directory in that structural sense. The trait clears the `dont-create-traits-for-single-implementations` bar on two counts — dozens of generated implementations plus a documented downstream extension contract.

**The macro names both types.** Stable `macro_rules!` cannot derive `CameraHomeEvent` from a supplied `CameraHome`, and R2 requires a distinct input action and semantic event, so both identifiers are supplied. Bevy's reflect derive resolves `#[reflect(Command)]` through an unqualified `ReflectCommand` in the invocation module, so **that helper is public and imported at every call site**:

```rust
use hana_rubric::{command, ReflectCommand};

command! {
    action:      CameraHome,
    event:       CameraHomeEvent,
    id:          "camera::home",
    title:       "Reset Camera to Home",
    description: "Return the camera to its default framing.",
}
```

- The macro wraps `bevy_kana`'s existing `action!` and `event!` rather than reimplementing them, emits `#[reflect(Event, Command)]` on the event type, and implements `Command` for it. A blanket `impl<T: Command> FromType<T> for ReflectCommand` reads the associated metadata.
- **title** → the palette row and the fuzzy-search target. **description** → the palette's secondary line and the JSON schema's hover text. Both required; startup validation rejects a missing or empty one.
- It lives here and **not** in `bevy_kana` because declared ids and `CommandId` are the keymap file's vocabulary; putting them in the device crate is what the D4 split exists to prevent. No cycle — this crate already depends on `bevy_kana`.
- `id` is const-validated at expansion using the `CommandId` validator from Phase 3.

**Capability** — a closed enum carried by the declaration and stored in the registry entry:
- `OneShot` — the default; binds to any `KeystrokeSequence`.
- `Held` — **binds to any single keystroke including modifiers** (`f`, `shift-f`, `cmd-shift-f`) and **not** to a multi-key sequence. Binding a held command to a sequence is rejected per-binding at load with a message naming the hold-to-act restriction. This is a property of the command carried by the registry, not a format limitation (R3).
- `Unremappable` — the command is reachable only through the app's permanently-registered bindings and may never be named in a keymap file (G3). The loader rejects any entry naming it, with a diagnostic explaining that it is reserved for recovery. The library never learns what an input context is.

`src/command/registry.rs` — `CommandRegistry` and `CommandEntry` (title, description, capability, registration handle). They stay in one file until a second split criterion joins line count; the anticipated split is `entry.rs` (entry, capability, reflected invocation) vs `registry.rs` (construction, validation, lookup).

- Built and validated **once in `Plugin::finish`** by scanning the type registry for `ReflectCommand` type data. Wire the plugin call in Phase 12; expose the construction and validation as callable functions now so this phase is testable with a bare `App`.
- Validation rejects: duplicate declared ids, an empty or missing title or description, and any shipped default that does not resolve.
- Invocation caches the `ReflectEvent` handle at build time. **No reflection lookup on the input path** — resolve id → handle once, then trigger through the cached handle.
- `#[reflect(Command)]` is discovered automatically: `reflect_auto_register` is already enabled on this workspace's `bevy`. Note that automatic registration **never covers generic instantiations** (M4), so any generic command type needs an explicit `register_type`.

**Visibility:** `pub` — `command!` (at the crate root, where `#[macro_export]` puts it), `Command`, `ReflectCommand`, `CommandId`, the capability type, and the read-only `CommandRegistry` query/invoke façade. `pub(crate)` — `CommandEntry`, its reflection handle, and mutable registry construction. `#[doc(hidden)] pub` — only the macro-support items downstream expansion must name.

### Phase 5 — `hana_rubric`: conditions, the `KeymapContext` contract, `ActiveCondition` · status: todo

#### Work Order

**Goal:** an application declares its context enum by deriving strum traits, and the library registers its variants, descriptions, and active value with no glue code in the app.

**Spec:**

`src/condition.rs` — a single file, not a directory: hana owns `InteractionContext`, so what remains here is one small cluster. It holds `ConditionName`, `ConditionRegistry`, the `KeymapContext` trait and its blanket impl, the `ActiveCondition` resource, and the generic sync system.

**The crate cannot name `InteractionContext`** — that enum is hana's, does not exist yet, and hana already depends on this crate; reading it here would be a crate cycle. The crate declares the contract; the application satisfies it by deriving (R7):

```rust
#[derive(Resource, Copy, Clone, Eq, PartialEq, EnumIter, AsRefStr, EnumMessage)]
#[strum(serialize_all = "snake_case")]
enum GameContext {
    #[strum(message = "While flying the ship")]
    Flying,
    #[strum(message = "While the pause menu is open")]
    Paused,
}

app.add_plugins(KeymapPlugin::new().for_context::<GameContext>());
```

`KeymapContext` is a **blanket impl** over `Resource + Copy + Eq + IntoEnumIterator + AsRefStr + EnumMessage + 'static`, so no downstream app writes an impl by hand. One bound instead of six at the call site, a comprehensible compiler error naming the missing derive, and a documented extension point. It takes the same extension-point exception to `dont-create-traits-for-single-implementations` that `Command` takes — one implementation *per application*, not one in total.

| library needs | source |
| --- | --- |
| every variant at startup — registry construction, rejecting unknown condition names, the schema's enum of valid strings | `EnumIter` |
| each variant's name as a string | `AsRefStr` + `serialize_all = "snake_case"` |
| each variant's description — schema hover text, generated reference file | `EnumMessage` via `#[strum(message = "…")]` |
| which variant is active right now | `as_ref()` on the current value |

**Two registration entry points over one generic sync system (R8):**

```rust

```

Supporting both costs one wrapper function, since the sync system is already generic over `C`. Hana takes the state path; the resource path serves an app that computes its context ad hoc.

- `ConditionRegistry` — variants and descriptions from strum, **duplicate condition ids rejected at load**. A missing `#[strum(message)]` on a variant is caught by startup validation, not by the compiler — same treatment as a missing command title.
- `ActiveCondition` — a plain resource holding **only a registry-resolved condition handle**, updated by change detection. The input path reads this one resource; it never scans contexts, compares strings, or reflects.
- **Mutual exclusivity is structural** — the enum has exactly one active variant by construction. Do not add a runtime check for it; do enforce that duplicate *names* cannot register.
- **The design never needs `in_state::<T>`** — that gates *systems*, while the keymap needs data-driven selection inside one system.
- **The context enum needs no Bevy reflection.** `EnumInfo::variant_names()` is not used and `reflect_documentation` is not needed. Commands still use reflection for dispatch; conditions use none.
- Export a public `KeymapSystems` ordering handle (with at least a `Route` variant) so an app can guarantee its own context derivation runs before the keymap reads it.

### Phase 6 — `hana_rubric`: JSONC document model with retained source spans · status: todo

#### Work Order

**Goal:** a keymap file parses into typed stages that remember where every binding came from, so diagnostics can point at the offending key.

**Spec:**

`src/keymap/mod.rs` (table of contents), `src/keymap/constants.rs` (the sequence timeout — keymap policy, passed into the matcher; the matcher itself owns no timeout), and `src/keymap/document.rs`.

`document.rs` owns source decoding and location indexing: the `KeymapDocument` anchor, its private serde wire structs, JSONC parsing with retained source spans, `BindingEdit`, and `ContextExpr`. Parser tests live beside the types they construct. **Do not split into `wire.rs` + `parse.rs`** — that is the prohibited definitions-versus-construction split; every parser change would cross the boundary, widen visibility, and separate tests from the types they build.

**File format — root object envelope (R4, supersedes the bare root array):**

```jsonc
{
  "$schema": "./keymap.schema.json",
  "bindings": [
    { "bindings": { "space": "transport::toggle_playback" } },
    { "context": "dimension_lock",
      "bindings": { "space": "dimension_lock::pause_tracking", "b": "dimension_lock::toggle_coupling" } }
  ]
}
```

- The document root is an **object**; the ordered blocks array nests under `"bindings"`. The envelope is required because an editor learns which schema applies from a `$schema` member, and an array has no members.
- Each block has an optional `"context"` and its `"bindings"` map. **Order matters** — later blocks override earlier ones for the same key. JSON objects guarantee neither key order nor duplicate-key rejection, so an object keyed by condition cannot express "these bindings, then those on top," and overriding is the entire point.
- Parse with `serde_json_lenient` — comments and trailing commas. The shipped defaults need explanatory comments, and rejecting a trailing comma in a user file is a bad first experience.
- A binding value is a command id **string**, or `null` (the tombstone, R1/D5b). The `[id, args]` array form is *specified* in the type but **rejected in v1** with a diagnostic saying arguments are not yet supported — this keeps A3 additive.

**Typed stages, private where possible:**
- `ContextExpr` — an enum holding **only** `Name(ConditionName)` in v1, so appendix A2 (boolean `&&`/`||`/`!` composition) is additive. A bare name is a valid expression in any boolean grammar, so `"context": "rotating"` parses identically under a future grammar. Document this in the type's doc comment so nobody flattens it to a `ConditionName`.
- `BindingEdit::{ Bind(CommandId), Unbind }` — `Unbind` is the tombstone.
- `KeystrokeSequence` from `bevy_kana`, guaranteeing at least one stroke.

**Source spans are deliberate work, not free.** `serde_json_lenient` reports line and column for *deserialization* errors, but unknown commands, contexts, and keystrokes are detected **after** deserialization, and its public byte offset covers completed stream values rather than per-binding spans. Index source locations during parsing: for each binding record its byte range, 1-based line and column, block index, context, and original keystroke text, keyed so a later semantic failure can retrieve them.

**Diagnose within the document, before any semantic resolution:** duplicate condition names across blocks, and duplicate keys within one block.

**Visibility:** `pub(super)` for `BindingEdit`, `ContextExpr`, and the resolved/merged stages shared among `keymap/` siblings. Note that a `pub(super)` item cannot be re-exported as `pub(crate)` — if the plugin root needs one, the source item must already be `pub(crate)`.

- `crates/hana_rubric/src/keymap/mod.rs` — create
- `crates/hana_rubric/src/keymap/constants.rs` — create (sequence timeout)
- `crates/hana_rubric/src/keymap/document.rs` — create
- `crates/hana_rubric/src/lib.rs` — `mod keymap;` (private)

**Constraints from prior phases:**

### Phase 7 — `hana_rubric`: layering, tombstone resolution, compiled per-context matchers · status: todo

#### Work Order

**Goal:** defaults plus user edits resolve to one immutable compiled keymap holding a matcher per context, with tombstones applied before compilation.

**Spec:**

`src/keymap/merged.rs` — `MergedKeymap` and `ResolvedEdits`. `src/keymap/compiled.rs` — `CompiledKeymap` and `Generation`. Both are pure semantic resolution and matcher construction: **no `World` mutation, no I/O**. `merge.rs` would be operation-named where `MergedKeymap` and `ResolvedEdits` already supply the anchor.

**The merge algorithm, exactly (all four review lenses converged on this):**

1. Process embedded defaults first, then the user file; within each source, blocks in file order.
2. Canonical merge identity is `(condition-or-global, complete canonical keystroke sequence)`.
3. At each identity the last **valid** edit wins, as either `Bind(handle)` or `Tombstone`. **An invalid edit is skipped and leaves the prior valid entry in place — a bad user line can never erase a working default.**
4. For active context `C` and sequence `S`: use `(C, S)` when present, **including when it is a tombstone**. Only genuine absence falls through to `(global, S)`. A tombstone dispatches nothing and suppresses the global fallback.
5. Tombstones apply to complete sequences, never to prefix subtrees. A tombstone on `g` does not remove `g g`; a tombstone on `g g` lets `g` fire immediately when no other longer sequence survives.
6. **Compile one resolved matcher per context after applying tombstones and global fallback**, so only live sequences contribute prefixes. Cost is `O(contexts × bindings)` of setup memory and reload-time work; it removes context scans, string comparison, reflection, and allocation from the input path.
7. Diagnose duplicate condition names and duplicate keys within one block (Phase 6 does the document-level half; this phase covers cross-source cases).

**Three distinct states at an identity, and the distinction is load-bearing:** absent means inherit the global, a command means replace it, `null` means the key is inert. `"space": null` inside the `dimension_lock` block wins at that identity and dispatches nothing while a lock is engaged; it does **not** expose the global `Space`. To get global behavior inside a context, bind that command there explicitly.

**One precedence rule, no specificity ranking:** a binding with a condition beats a binding without one for the same keystroke. Mutually-exclusive computed states mean at most one block is live, so there is nothing to rank — which is why full boolean expressions are deferred (A2).

**Prefix collisions are not a merge concern.** Defaults binding `g g` while the user binds `g` are not the same keystroke, so layering sees no conflict; the matcher resolves it.

**Semantic resolution happens here, producing diagnostics with suggestions:**
- Unknown command id → diagnostic naming **the closest matches**. Fuzzy matching is already in the crate for the command palette, so this is nearly free and covers typos, which are likelier than renames while the only keymap files are ours. (No alias machinery in v1 — A1.)
- Unknown condition name → diagnostic listing the registered condition names.
- A `Held`-capability command bound to a multi-key sequence → per-binding rejection naming the hold-to-act restriction (R3).
- An `Unremappable`-capability command named anywhere in a file → per-binding rejection saying it is reserved for recovery (G3).
- **Protected recovery chord:** reject any sequence whose **first canonical stroke** is the protected chord — `cmd-p x` can never complete because recovery consumes its first stroke. **Compare parsed, platform-normalized keystrokes, never raw strings**, so `super-p`, `ctrl-p`, and left/right modifier spellings cannot slip through. Report the stroke index and the reserved command. Define **one canonical parsed keystroke constant** shared by the always-on handler, protected-entry validation, the generated default comment, and the tests (M1). **Keep the protected list to exactly one entry** — the bar for a second is that the app is unrecoverable without it.
- Command and condition names resolve to **stable handles** here. No name survives into the compiled form.

`CompiledKeymap` is **immutable** and carries a `Generation`. It holds one `SequenceMatcher<T>` per context, where `T` is an opaque index into a table of resolved command handles.

**Files:**
- `crates/hana_rubric/src/keymap/merged.rs` — create
- `crates/hana_rubric/src/keymap/compiled.rs` — create
- `crates/hana_rubric/src/keymap/mod.rs` — declare and re-export

**Constraints from prior phases:**
- Phase 2's `SequenceMatcher<T>` is constructed from `(KeystrokeSequence, T)` pairs and takes its timeout as a parameter — pass `keymap/constants.rs`'s value in.
- Phase 4's registry resolves id → cached `ReflectEvent` handle and carries the capability (`OneShot` / `Held` / `Unremappable`) on each entry. Capability checks happen here, at merge time, not at dispatch.
- Phase 5's `ConditionRegistry` supplies the valid condition names and their handles; `ActiveCondition` holds a handle, so the compiled per-context map must be keyed by the same handle type.
- Phase 6's document stages (`BindingEdit`, `ContextExpr::Name`, source spans) are `pub(super)` — this file is a `keymap/` sibling and can see them.
- Phase 3's `Diagnostic` carries `suggested replacements` — this is the phase that fills that field.

Tests prove each numbered rule above: a user block overrides a default at the same identity; an **invalid** user line leaves the prior valid default intact; a tombstone in a context suppresses the global fallback rather than exposing it; a tombstone on `g` leaves `g g` live; a tombstone on `g g` lets `g` fire immediately; a conditioned binding beats an unconditioned one; an unknown id names close matches; a `Held` command bound to `g f` is rejected; an `Unremappable` command is rejected wherever it appears; the protected chord is rejected as a bare chord, as a sequence prefix, and through the `super-p` / `ctrl-p` / modifier-order aliases.

```
  keymap.default.jsonc  ← generated, 0444, reference to copy from

```

4. **Any failure** of directory creation, write, permission change, or replacement continues with embedded defaults and a readable user keymap, recording a **durable companion-publication warning separate from keymap parse errors**.

### Phase 10 — `hana_rubric`: the disk worker — watch, debounce, retry, poll · status: todo

#### Work Order

**Goal:** one I/O worker owns every filesystem touch, so editor save patterns, network filesystems, and watcher failures never reach the frame schedule.

**Spec:**

`src/disk/worker.rs` — `DiskWorker`. It owns initial read, first-launch stub creation, the parent-directory watch, debounce, retry, the polling audit, confirmed deletion, and companion publication. It communicates with the app through a **bounded coalescing slot**.

**Give a dedicated I/O worker ownership** rather than running this on the schedule: `notify` documents that **NFS may emit no events at all without reporting watcher failure**, so an error-triggered fallback is not sufficient. Run a **slow polling audit alongside native events** rather than waiting for an error. This keeps network-filesystem latency off the frame schedule.

**Watching:**
- **Watch the parent directory non-recursively** and filter the canonical filename **including rename destinations**. Watching the file directly loses the watch when an editor replaces the directory entry.
- **The gotcha to design for, not discover:** editors save by writing a temp file and renaming over the target. The watcher sees several events per save and may briefly observe the file as *missing*. **Debounce, and treat transient absence as "wait", never as "the user deleted their keymap, revert to defaults".**
- Coalesce notifications into **one bounded dirty flag with trailing-edge debounce**.
- **Retry transient `NotFound` for a bounded grace interval**, then apply a documented **confirmed-deletion policy: deleting the user file removes its overrides and restores embedded defaults.**
- Treat **watcher errors, rescan signals, and channel disconnection as durable health failures: reread completely and recreate the watch.**

**First launch (R4):** write an **empty user stub only if absent**, and never overwrite it afterward. Editor assistance therefore begins after the app has run once — state that as the installation contract in the crate docs.

**Startup order:** embedded defaults load first (they cannot fail), then the config directory is touched. Companion publication (Phase 9) runs from this worker; its failure does not prevent the watch from starting.

**The worker never parses.** It produces byte snapshots plus a source path and hands them across the slot; parsing, merging, and compiling are pure and happen on the app side.

### Phase 11 — `hana_rubric`: the per-frame runtime · status: todo

**Held actions.** Each keeps **one statically spawned `Action<A>` bound to `Binding::Custom(id)`**, using enhanced-input's public custom-input mechanism — `CustomInput`, `CustomInputs::register_input()`, `Binding::Custom`, all verified present in 0.26.0 (`src/context/input_reader/custom.rs`, `src/binding.rs:112`). **The matcher writes that input's `ActionValue` before enhanced-input evaluates**, so `Start`/`Complete` pairing, `require_reset`, and blocking remain enhanced-input's job. **Remapping a held key changes which physical stroke drives the custom input — not the action entity.** This is what avoids the spurious `Complete`-then-restart that entity respawn causes while a key is held.

**Why entity respawn is wrong, verified from source** (`bevy_enhanced_input-0.26.0/src/context.rs:369` `reset_action`, `:553` `FirstActivation`): removing an action's `ActionOf<C>` resets it and emits `Complete` from `Fired`; removed bindings enter `PendingBindings` **only** when `require_reset` is set. Hana's own actions use `ActionSettings::default()`, so `require_reset` is false and only `bevy_kana`'s modifier actions set it. Consequence: despawning and rebuilding action entities while a key is held completes the held action and can immediately reactivate its replacement from the still-held key. **Keep action entities and held-input handles stable.**

- Cancel pending sequences **without firing a deferred binding**.
- Drive active old-generation held routes inactive so **exactly one `Complete`** is emitted.
- Clear held-source reference counts.
- **Inhibit already-down keys until physical release.**

The recovery chord also cancels pending state without firing the deferred command.

**Input-path budget — enforced here:** no heap allocation, string parsing, reflection lookup, or full-keymap scan. Command and condition names were resolved to stable handles at load; sequences live in a prefix index keyed by canonical strokes; the active condition id is cached from state transitions; on a key edge inspect **only current prefix candidates**; check the timeout **only while a sequence is pending**.

### Phase 12 — `hana_rubric`: plugin assembly and the reload transaction · status: todo

#### Work Order

**Goal:** `KeymapPlugin` wires every module together and a reload is a transaction over a compiled resource — never over ECS entities.

**Spec:**

```text

command, condition  → diagnostic
disk                → diagnostic
keymap              → command, condition, diagnostic, bevy_kana

```

`keymap → disk` is **deliberately absent.** The plugin root hands generated companion buffers to the worker, receives byte snapshots back, calls the pure keymap compiler, then invokes the runtime transaction.

**Reload is a transaction over a compiled resource, not over ECS entities:**

Parse, validate, merge, and compile a candidate **with no world mutation**, then swap **one immutable compiled-keymap resource in a single main-thread system ordered before `EnhancedInputSystems::Update`**. `reload::commit_reload` is ordered **before** `route_input` and swaps `CompiledKeymap` through `ResMut` or an exclusive system — **never deferred `Commands`**.

**Two-tier failure (D7), mirroring Zed's `JsonParseFailure` vs `SomeFailedToLoad` split:**

| Failure | Behavior |
| --- | --- |
| Whole-file parse failure (missing brace, bad JSON) | **Keep the last good keymap running, untouched.** Report the error. |
| Per-binding failure (unknown command id, unparseable keystroke, unknown context) | **Apply the good bindings, report the rest.** |

Not all-or-nothing, because one typo costs the other 34 bindings. Not apply-whatever-parsed, because a brace error drops you to *zero* bindings mid-session, including whatever you would use to recover. Two-tier is the only option where the app stays usable through every intermediate state an editor writes — **the worst outcome of a bad save is that nothing changes and you are told why.**

Precisely: **a whole-file parse failure changes nothing — not the generation, not the pending sequence, not held actions.** A partial semantic failure **commits one complete generation of defaults plus every valid edit.**

Each `mod.rs` re-exports with an explicit qualifier (`pub(crate) use reload::commit_reload;`).

### Phase 19 — hana: the unremappable recovery chord · status: todo

**Blocked by:** G1, G2.

#### Work Order

**Goal:** the recovery palette chord works when nothing else does, and a user who tries to bind it is told why they cannot.

**Spec:**

**The requirement.** `hana/docs/hana/tool-graph.md:175` requires the recovery chord to be unremappable, independent of `Ready`, and excluded from user key maps. **The chord is system-key + P — `⌘P` on macOS, `ctrl-P` elsewhere** (changed from `⌘⇧P` because hana does not print). Its job is to work when nothing else does — empty world, mangled graph, no `Ready` — because it opens the palette containing factory reset.

A keymap file makes this harder: the escape hatch must survive a user rebinding `cmd-p`, nulling it, **and** writing a file that fails to parse.

**Three parts (D8), as resolved by G3:**

1. **Registered in Rust unconditionally**, before any file is read and regardless of whether reading succeeds. Checked ahead of the keymap matcher; consumes the keystroke. **This is the survival property — it does not depend on the keymap system at all.** Catalyst already implements `OpenCommandPalette` on Cmd/Ctrl+P hand-rolled with `KeyCode::KeyP.with_mod_keys(…)`; the mechanism exists, so reconcile rather than rebuild.
2. **Documented in `keymap.default.jsonc` as a comment** (Phase 17 wrote the file), so it is discoverable by reading the file rather than the source.
3. **The loader rejects any keymap entry claiming it** — Phase 7 implements the rejection; this phase supplies the constant and the `Unremappable` declarations.

**`PermanentShortcutsContext` is the mechanism.** Catalyst's second input context — documented as holding commands "intentionally absent from user key maps" — **is** D8's mechanism and a better one than the design had. Rather than the loader special-casing individual chords, commands that must stay reachable live in a context the keymap system never reads. D8's loader-rejection survives as the diagnostic emitted when a keymap file names a command belonging to that context.

- `PermanentShortcutsContext` **stays in hana**; it is a `bevy_enhanced_input` context (marker component plus `Actions::<PermanentShortcutsContext>` spawn). It does **not** move into `hana_rubric`.
- What crosses the boundary is only the *declaration* that a command is unremappable, carried by `command!`'s capability field. **hana owns the binding; `hana_rubric` owns the refusal.**
- Mark every command in that context `Unremappable` in its `command!` invocation.

**Why not Rust-only and silent:** a user who binds `cmd-p` and sees nothing happen has no way to find out why. **Why not a protected entry in the keymap file:** then the chord is carried by the keymap system, so a catastrophic keymap failure takes the recovery path with it — the exact scenario it exists for.

**One canonical parsed keystroke constant (M1)** shared by the always-on handler, protected-entry validation, the generated default comment, and the tests. Not four string literals.

**Keep the protected list to exactly one entry.** Every protected keystroke is one the user can never use for anything else. The bar for a second: the app is unrecoverable without it — true of the recovery palette, nothing else currently.
