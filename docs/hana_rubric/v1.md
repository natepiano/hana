### Phase 1 — `bevy_kana`: `Keystroke`, `Modifiers`, and the chord parser · status: done (`523c3471`)

#### Work Order

**Goal:** `"cmd-shift-p"` parses to a canonical `Keystroke` carrying a bevy `KeyCode` plus a modifier set, and renders back to a canonical string.

**Spec:**

Create `crates/bevy_kana/src/input/keystroke/` with `mod.rs` and `sequence.rs`. Add `mod keystroke;` to `crates/bevy_kana/src/input/mod.rs` and re-export the public types there, from `lib.rs`, and from the prelude.

**Not feature-gated.** Both intended consumers (hana, nateroids) need keyboard input, so gating buys nothing, and it costs nothing to ungate: keystroke parsing produces bevy `KeyCode` + modifiers and needs `bevy_input`, **not** `bevy_enhanced_input`. Ungating does not drag the optional dep into the default build. `keybindings.rs` stays behind the `input` feature, since it genuinely uses `bevy_enhanced_input`.

`mod.rs` holds `Keystroke` (the module-name type, so it lives at the root) and `Modifiers`. `Modifiers` stays in `mod.rs` under the field-type exception — you cannot read `Keystroke` without it. This is the one permitted deviation from "module roots are table-of-contents only."

- `Modifiers` — a set of `{ control, alt, shift, platform }`, represented as a **`bitflags` set, not four `bool` fields**. `bitflags = "2"` is already a `[workspace.dependencies]` entry (MIT OR Apache-2.0, so the dual-license invariant holds); `bevy_kana` adds `bitflags.workspace = true` and the root manifest needs no edit. One `u8` gives a single-compare `Eq` and a single-write `Hash` — `Keystroke` is the key of Phase 2's prefix index, so both run on every key edge — and the parser accumulates modifiers by `insert`ing rather than assigning four fields. `platform` is the Cmd/Ctrl abstraction; reuse the existing `PlatformShortcutMode` in `keybindings.rs:209-223` (`Command` on macOS, `Control` elsewhere, selected by `current()`) as the normalization authority rather than duplicating the `cfg!` test. **Canonicalization is a masking step at construction**: the `PLATFORM` flag is set only on macOS, and a platform-modifier token folds into `CONTROL` elsewhere, so `platform-p == ctrl-p` off macOS and `platform-p != ctrl-p` on it are true by construction rather than by a comparison special case. Uncanonical flag combinations must be unconstructible from outside the module — keep the `bitflags` type's raw constructors out of the public surface.
- `Keystroke` — `{ modifiers: Modifiers, key: KeyCode }`. Comparison and hashing are on the **canonical** value, never on source text.
- **Parser** — a tokenizer over a fixed modifier vocabulary, splitting on `-`, last token is the key. Accepted modifier spellings, all normalizing to the same canonical value: `cmd`, `super`, `win`, `platform` → platform modifier; `ctrl`, `control`; `alt`, `opt`, `option`; `shift`. Modifier order in the source string is irrelevant (`shift-cmd-p` == `cmd-shift-p`); canonical `Display` order is fixed (suggested: platform, ctrl, alt, shift, key).
- Left/right modifier spellings must not be able to slip through as distinct — normalize them to the same canonical modifier.
- Key-name vocabulary maps to `bevy::input::keyboard::KeyCode`. Cover letters, digits, function keys, arrows, and the named keys hana already binds (see `global_shortcuts.rs` reference for the in-use set). Unknown key names are a parse error naming the offending token, never a panic.
- Errors are a typed `KeystrokeParseError` carrying the offending token and its byte offset within the input string — Phase 6 needs the offset for source-located diagnostics.

`sequence.rs` holds `KeystrokeSequence` — an ordered, **non-empty** sequence of `Keystroke`. The non-empty invariant is enforced by construction (private field, fallible constructor), not by convention. Parse from a space-separated string (`"g g"`, `"cmd-k l"`). `Display` round-trips.

**Write our own test cases.** Zed's tests are copyrightable; reimplementation is from observed behavior only.

**Files:**

### Retrospective

**What worked:**
- `bitflags` over four `bool`s, with canonicalization as a masking step at construction. `platform-p == ctrl-p` off macOS and `!=` on macOS both fall out of the representation; no comparison special case exists anywhere.
- The feature-gate restructure landed cleanly: `keystroke` is ungated, `action`/`bind_action_system`/`event`/`keybindings` moved behind `#[cfg(feature = "input")]`, and `bevy_enhanced_input` is absent from `bevy_kana`'s normal dependency edges with default features off.
- One `CANONICAL_KEY_MAPPINGS` table now backs parsing, `Display`, and the round-trip test, so a key added later cannot drift out of sync between them.

**What deviated from the plan:**
- **Added `pub const fn Keystroke::new(Modifiers, KeyCode)`**, which the Work Order did not list. Both reviews called its absence a blocker: Phase 2's matcher must build a `Keystroke` per key edge from a live `KeyCode` plus held modifiers, and with `FromStr` as the only route it would have had to format a string and reparse it — which also breaks Phase 2's no-allocation-on-the-match-path requirement. It takes an already-canonical `Modifiers`, so it cannot introduce an uncanonical value. User-approved.
- `PlatformShortcutMode` was **moved** out of `keybindings.rs` into its own module, `crates/bevy_kana/src/input/platform_shortcut_mode.rs`, as `pub(super)` rather than referenced in place — `keystroke` is ungated and `keybindings` is not, so the ungated module could not depend on the gated one. Its `cfg!(target_os = "macos")` body is unchanged; `keybindings.rs` now imports it.
- `crates/bevy_kana/Cargo.toml` needed `bevy = { features = ["bevy_log", "keyboard"] }` — the plan anticipated only `bitflags`. `keyboard` must be unconditional, not under `input`, because ungated `keystroke` names `KeyCode`.

**Surprises:**
- **Every gate command refused to run, and the first delegate pass therefore coded blind.** `-p bevy_kana` was ambiguous: the workspace crate (`0.2.0-dev`) and a published `bevy_kana 0.1.0` were both in the graph, the latter reached through `fairy_dust` → `bevy_brp_extras 0.20.1` → crates.io. Cargo aborts on an ambiguous spec before compiling, so `verify.sh` reported nothing and the delegate reported success on code that did not compile. CI never caught it because CI names no package — it runs `--workspace`. Resolved permanently by publishing `bevy_kana 0.2.0` and a `bevy_brp_extras 0.22.2` that drops the dependency, then bumping the workspace pin (commit `eeacc29b`).
- `cargo tree`'s default edge set includes dev-dependencies, so the `bevy_enhanced_input`-absence check reported four hits from `bevy_kana`'s own dev-dep loop through `fairy_dust`. The gate line needed `-e normal`; as originally written it could never have passed.
- Feature unification hid a compile error: dev-dependencies pull `bevy` with a larger feature set, so a broken `KeyCode` import compiled under `test` and `clippy` but failed under `check --lib`.

**Implications for remaining phases:**
- Phase 2 constructs keystrokes with `Keystroke::new(modifiers, key)`; no format-then-reparse path is needed.
- `-p <package>` is now unambiguous workspace-wide, so every later phase's `verify.sh` lines work as written.
- `PlatformShortcutMode` is `pub(super)` within `input/` — reachable from `keybindings.rs`, not from outside `input/`. Anything in `hana_rubric` or `hana` needing the Cmd/Ctrl distinction must go through `Modifiers::with_platform`/`has_platform`, not the mode enum.
- Platform-split tests are `#[cfg]`-split and CI is Ubuntu-only, so the macOS half of the platform behavior never runs in CI. Recorded, deliberately not fixed.

### Phase 2 — `bevy_kana`: `SequenceMatcher<T>` · status: done (`27b33a1f`)

#### Work Order

**Goal:** a prefix-indexed matcher that consumes completed `Keystroke` values and yields opaque `T` indices, with pending state and timeout-driven resolution.

**Spec:**

Create `crates/bevy_kana/src/input/keystroke/sequence_matcher.rs` holding `SequenceMatcher<T>`, `MatchOutcome`, and `PendingSequence`. The file is named for its anchor type, not `matcher.rs`; `MatchOutcome` and `PendingSequence` are its return and field types.

**Domain-free.** The matcher knows nothing of JSON, commands, conditions, tombstones, or `World`. It returns opaque `T` and **takes its timeout as an input parameter** rather than owning a policy value.

**Input boundary — fixed now so deferred simultaneous chords stay additive.** `SequenceMatcher<T>` consumes *completed canonical `Keystroke` values*, never raw key edges. If simultaneous chords (`"j+k"`) are ever built, they arrive as one preprocessing stage beside it (`keystroke/chord.rs` + `keystroke/simultaneous_matcher.rs` emitting a completed `Keystroke`), and `sequence.rs` plus the prefix/timeout behavior are untouched. Had the matcher consumed key edges, adding chords would mean rewriting it, because simultaneity timing and sequence-prefix timing would share one state machine.

**Construction:** built from a set of `(KeystrokeSequence, T)` pairs into a prefix index keyed by canonical strokes. Construction is the only place that allocates or scans; matching does neither.

**Multistroke timing — the required behavior:**
- When both `g` and `g g` are live, **defer** `g`. Fire it on timeout.
- On a non-matching next stroke, **fire the deferred command and reprocess the unmatched stroke once from the root** — two physical strokes can therefore invoke two commands, which is the conventional behavior.
- Reload, a context change, and the recovery chord all **cancel pending state without firing the deferred command**. Expose this as an explicit `cancel_pending()` that discards rather than resolves.
- When no longer sequence survives, a complete short match fires immediately — no timeout wait.

`MatchOutcome` must distinguish at minimum: an immediate match (`T`), a deferred-but-complete match now pending a longer candidate, pending-with-no-match-yet, an unmatched stroke (with any deferred `T` to fire first, plus the stroke to reprocess), and no-match-and-nothing-pending.

**Input-path budget applies here:** on a key edge inspect only current prefix candidates; check the timeout only while a sequence is pending. No allocation, no string parsing, no full scan.

**Live keyboard state → `Modifiers`.** Phase 1 shipped `Modifiers` as a parse-and-compare type; nothing converts the keys currently held down into one, and Phase 11's per-frame runtime needs that on every key edge. Add it here, in `bevy_kana`, because this is the only crate that can see `PlatformShortcutMode` — `hana_rubric` reimplementing the rule would fork the canonicalization the whole design rests on.

Add `Modifiers::from_pressed(&ButtonInput<KeyCode>) -> Modifiers` to `keystroke/mod.rs`. It reads the modifier key pairs and applies the platform rule internally:
- Both platforms: `AltLeft`/`AltRight` → `ALT`, `ShiftLeft`/`ShiftRight` → `SHIFT`.
- macOS: `SuperLeft`/`SuperRight` → `PLATFORM`, `ControlLeft`/`ControlRight` → `CONTROL`.
- Elsewhere: `ControlLeft`/`ControlRight` → the platform modifier (which canonicalizes to `CONTROL`), and **physical Super contributes nothing** — it is not a keyboard modifier in this model. Phase 11 documents that so it reads as a decision rather than a surprise.

`bevy` is already a dependency of `bevy_kana`; `ButtonInput` and `KeyCode` are available without a feature change, and `keystroke` stays ungated.

### Phase 4a — `bevy_kana` `event!` extension, `KeymapCommand` trait, `command!` macro · status: done (`fd7e91e1`)

#### Work Order

**Goal:** one `command!` invocation declares an input action, a semantic event, an id, authored palette text, and a capability — and the declared metadata is readable from the type registry.

**Spec:**

**The registry holds semantic command *events*, not input actions (R2).** `"camera::home"` resolves to the `bevy_kana` `event!` type (e.g. `CameraHomeEvent`), not the `action!` input-action marker. The command events already derive `Reflect` with `#[reflect(Event)]`, so `ReflectEvent::trigger` fires them by name at runtime — the same mechanism BRP uses (`TypeRegistration::data::<ReflectEvent>()` then `ReflectEvent::trigger`, `bevy/crates/bevy_ecs/src/reflect/event.rs:67`; BRP's `process_remote_trigger_event_request`, `bevy/crates/bevy_remote/src/builtin_methods.rs:1480`).

**Do not plan on dynamically emitting `Start<A>`.** `bevy_enhanced_input::Start<A>` derives only `EntityEvent` — no `Reflect`, no `ReflectEvent` — and enhanced-input's dynamic `ActionFns` table is private. A registry of input actions has no supported way to invoke what it resolved.

**1. Extend `bevy_kana`'s `event!` with an optional `reflect:` fragment** (settled Decision A, option 1).

`event!` (`crates/bevy_kana/src/input/event.rs:25`) matches `$(#[$meta:meta])*` **before** it writes `#[derive(Event, Reflect, Default)]`, so an attribute forwarded by a wrapping macro lands *ahead* of the derive that defines the `reflect` helper. That is the `legacy_derive_helpers` future-incompatibility warning, and this workspace denies warnings — a forwarded `#[reflect(KeymapCommand)]` will not compile. The fix is an arm that splices extra entries into the `#[reflect(...)]` list `event!` writes itself:

```rust
($(#[$meta:meta])* $event:ident, reflect: $($extra:ident),+ $(,)?) => {
    $(#[$meta])*
    #[derive(Event, Reflect, Default)]
    #[reflect(Event, $($extra),+)]
    pub struct $event;
};
```

Add the matching payload-form arm. Keep both existing arms byte-identical.

**This creates no dependency cycle and needs no manifest change.** `$extra:ident` captures a bare token; `bevy_kana` never names `KeymapCommand`, never imports it, and its `Cargo.toml` is untouched. Name resolution happens after expansion, in the *invocation* module — which is in `hana_rubric` (and, from Phase 16 on, in hana), where `ReflectKeymapCommand` is in scope. This is the same property the existing arms already rely on: `event!` emits bare `#[derive(Event, Reflect, Default)]` with no imports of its own.

**Testing the new arm inside `bevy_kana` cannot use `KeymapCommand`** — that type is downstream and invisible here. Prove the splice compiles with a reflected trait `bevy_kana` can name, or a `#[reflect_trait]` declared in the test module.

**2. `src/command/reflect_command.rs`** — the `KeymapCommand` trait, the `ReflectKeymapCommand` type data, and the `command!` macro.

The trait lives here, not in `command/mod.rs`: the table-of-contents exception covers the module-name *type* and the types in its fields or enum payloads; a trait has no fields and does not anchor the directory in that structural sense. The trait clears the `dont-create-traits-for-single-implementations` bar on two counts — dozens of generated implementations plus a documented downstream extension contract.

**The metadata is associated consts, and `ReflectKeymapCommand` is hand-written type data — not `#[reflect_trait]`.** `#[reflect_trait]` generates a `ReflectKeymapCommand` of its own (which would collide by name) and its generated accessor works through `&dyn Reflect`, so it cannot read associated consts at all. Write the type data explicitly and populate it from the consts in a blanket `FromType`:

```rust
pub trait KeymapCommand: Reflect {
    /// Must satisfy `CommandId::is_valid`; checked at expansion by `command!`.
    const ID: &'static str;
    const TITLE: &'static str;
    const DESCRIPTION: &'static str;
    const CAPABILITY: Capability;
}

#[derive(Clone, Debug)]
pub struct ReflectKeymapCommand {
    pub id:          &'static str,
    pub title:       &'static str,
    pub description: &'static str,
    pub capability:  Capability,
}

impl<T: KeymapCommand> FromType<T> for ReflectKeymapCommand {
    fn from_type() -> Self {
        Self { id: T::ID, title: T::TITLE, description: T::DESCRIPTION, capability: T::CAPABILITY }
    }
}
```

**The macro names both types.** Stable `macro_rules!` cannot derive `CameraHomeEvent` from a supplied `CameraHome`, and R2 requires a distinct input action and semantic event, so both identifiers are supplied. Bevy's reflect derive resolves `#[reflect(KeymapCommand)]` through an unqualified `ReflectKeymapCommand` in the invocation module, so **that helper is public and imported at every call site**.

**`ReflectKeymapCommand` is not the only unqualified name the expansion needs.** `action!` and `event!` expand to bare `#[derive(InputAction)]` and `#[derive(Event, Reflect, Default)]` with **no internal imports** — they resolve those derive macros in the *invocation* module. So `command!`'s call sites must also have `InputAction`, `Event`, and `Reflect` in scope. State this in the macro's doc comment and cover it in Phase 16's constraints; a call site that imports only `command` and `ReflectKeymapCommand` fails to compile.

```rust
use bevy::prelude::{Event, Reflect};
use bevy_enhanced_input::prelude::InputAction;
use hana_rubric::{command, ReflectKeymapCommand};

command! {
    action:      CameraHome,
    event:       CameraHomeEvent,
    id:          "camera::home",
    title:       "Reset Camera to Home",
    description: "Return the camera to its default framing.",
}
```

**3. The expansion reaches `action!`/`event!` through `$crate`** (settled Decision B, option 2).

`$crate` in a `macro_rules!` expands to the crate where the macro was *defined*, so inside `hana_rubric`'s `command!` it is `hana_rubric` — it cannot reach `bevy_kana`. Re-export both macros from this crate's root and expand through `$crate`:

```rust
// crates/hana_rubric/src/lib.rs
#[doc(hidden)]
pub use bevy_kana::{action, event};
```

```rust
// inside command!'s expansion
$crate::action!($action);
$crate::event!($event, reflect: KeymapCommand);
```

`#[macro_export]` puts `action!`/`event!` at `bevy_kana`'s **crate root**, so the re-export path is `bevy_kana::{action, event}` — not `bevy_kana::input::…`. `#[doc(hidden)]` keeps them out of rendered docs while leaving them resolvable; `doc(hidden)` never affects name resolution. This is the settled visibility scheme's third bucket. The rejected alternative was expanding to `::bevy_kana::action!`, which would force every consuming crate to carry `bevy_kana` as a direct dependency under exactly that name and would put the device crate into `hana_rubric`'s public contract — the inverse of the D4 split.

Record the chosen form in `command!`'s doc comment.

- **title** → the palette row and the fuzzy-search target. **description** → the palette's secondary line and the JSON schema's hover text. Both required; Phase 4b's startup validation rejects a missing or empty one. **A `Held` command has no palette row** (Phase 4b, Decision E) — its title and description are still required, serving as the key-binding editor's label and the schema's hover text.
- `command!` lives here and **not** in `bevy_kana` because declared ids and `CommandId` are the keymap file's vocabulary; putting them in the device crate is what the D4 split exists to prevent. No cycle — this crate already depends on `bevy_kana`.
- `id` is const-validated at expansion: the macro emits `const _: () = assert!($crate::CommandId::is_valid($id));`. `CommandId` itself is **not** const-constructible (it wraps a `String`), which is why the trait carries `&'static str` and Phase 4b calls `CommandId::try_from` once at build time.
- Generated command types stay `pub` — `action!`/`event!` hardcode `pub struct` and `command!` adds no visibility parameter (settled Decision C, option 2; Phase 16's `pub(crate)` sentence is deleted).

### Phase 4b — `hana_rubric`: `CommandRegistry`, startup validation, cached invocation · status: done

#### Work Order

**Goal:** a validated id → registration table, built once at startup, that dispatches a command by name with no reflection lookup on the input path.

**Spec:**

`src/command/registry.rs` — `CommandRegistry` and `CommandEntry` (title, description, cached `ReflectEvent` handle, and `Invocation`). They stay in one file until a second split criterion joins line count; the anticipated split is `entry.rs` (entry, invocation) vs `registry.rs` (construction, validation, lookup).

**`Invocation` — the resolved counterpart of the declared `Capability`** (settled Phase 4a Decision E). `Capability` is a compile-time const on the trait; `Invocation` is what the registry produces after allocating runtime resources, and it lives on `CommandEntry`:

```rust
pub enum Invocation {
    OneShot,
    Held(CustomInput),
    Unremappable,
}
```

Turning `Capability` into `Invocation` is the one place a `CustomInput` is allocated, and it is the only conversion between the two types. A `Held` command with no input is unrepresentable — do **not** reintroduce it as `Option<CustomInput>` plus a documented invariant.

- Built and validated **once in `Plugin::finish`** by scanning the type registry for `ReflectKeymapCommand` type data. Wire the plugin call in Phase 12; expose the construction and validation as callable functions now so this phase is testable with a bare `App`.
- Each entry's `CommandId` is produced here by `CommandId::try_from(entry.id)` — Phase 4a's trait carries `&'static str` because `CommandId` cannot be built in a const context. There is no generic `T` at scan time: the registry walks `TypeRegistration::data::<ReflectKeymapCommand>()` and sees only a `ReflectKeymapCommand` value (`id`, `title`, `description`, `capability`).
- Validation rejects: duplicate declared ids (`DiagnosticKind::DuplicateCommandId`), an empty title (`MissingCommandTitle`), and an empty description (`MissingCommandDescription`). Each diagnostic's `message` names the offending id. The consts are `&'static str` and always present, so **emptiness is the only checkable failure** — "missing" is not a reachable state.
- **Two further validation cases, for hand-written `KeymapCommand` impls** (settled Phase 4a Decision F). `reflect_command.rs`'s doc comment invites downstream crates to implement the trait directly, which bypasses `command!`'s compile-time id assertion and its `#[reflect(Event)]`. So add `DiagnosticKind::InvalidCommandId` (when `CommandId::try_from(entry.id)` fails) and `DiagnosticKind::CommandEventNotReflected` (when `TypeRegistration::data::<ReflectEvent>()` returns `None` for a type carrying `ReflectKeymapCommand`). Each `message` names the offending type path. A diagnostic, not a panic — an outside crate can trip these, and Phase 13's editor tooling needs the two failures distinguishable.
- **Shipped defaults that do not resolve are Phase 12's check, not this phase's.** This phase has no document model (Phase 6), no merge (Phase 7), and no embedded defaults (Phase 12's `.with_defaults(include_str!(…))`), and Phase 12's `Plugin::finish` already owns that validation.
- Invocation caches the `ReflectEvent` handle at build time. **No reflection lookup on the input path** — resolve id → handle once, then trigger through the cached handle. The handle is cached for **every** capability including `Held` — see the two-phase event below.
- **Allocate one `CustomInput` per `Held` command during construction** and expose a `CommandId` → `CustomInput` lookup on `CommandRegistry` (settled Phase 4a Decision E). `bevy_enhanced_input`'s `CustomInput` is a runtime-allocated `usize` newtype handed out by `CustomInputs::register_input()` (`bevy_enhanced_input-0.26.0/src/context/input_reader/custom.rs:23,79`), so it cannot be a const on the trait. This phase is the only one that walks every command, so it allocates them all in one pass; `Plugin::finish` has `&mut World` and can take `ResMut<CustomInputs>`. `hana_rubric` already depends on `bevy_enhanced_input` (`Cargo.toml:19`) — no new dependency.
- **A `Held` command fires a two-phase semantic event** (settled Phase 4a Decision E). Held commands are driven by `Action<A>` state, but BRP, scripts, and tests cannot hold a key down, and Phase 20 promises id-addressed invocation over BRP. So `command!`'s held form generates `pub struct $Event { pub phase: HoldPhase }` rather than a unit struct, where `HoldPhase` is `Begin` / `End`. **Both input paths converge on the same `CustomInput` before anything downstream sees them**: the physical key path has Phase 11's matcher write the input's `ActionValue`, and the event path has a `Begin`/`End` handler write the *same* input's `ActionValue`. Phase 18's single owner of held state watches one thing either way. Writing `End` when already released is a no-op, not an error.
- **`HoldPhase` lives in `src/command/capability.rs`** next to `Capability`, with the same derives (`Clone, Copy, Debug, Default, Eq, PartialEq, Reflect`) and `#[default] Begin`. It must be reflected and registered so BRP can construct the payload.
- **`command!` gains a third public arm, marked by a leading `held` token** and carrying no `capability:` key — the marker *is* the capability:
  ```rust
  command! { held, action: FreezeTrackingAction, event: FreezeTracking,
             id: "tracking::freeze", title: "…", description: "…" }
  ```
  Do **not** infer the held form from `capability: Capability::Held`. `macro_rules!` matches tokens, so a caller writing `crate::Capability::Held` or a renamed import falls through to the unit-event arm and silently gets an event with no phase. The leading `held` ident cannot collide with an arm beginning `action:`, and it is matched literally rather than through a fragment specifier, so arm order does not matter. **This needs no `bevy_kana` change** — Phase 4a already shipped `event!`'s field arm with `reflect:`, so `event!($Event { phase: HoldPhase }, reflect: KeymapCommand)` compiles today, and Phase 15's pin is unaffected.
- **`Held` commands are absent from the command palette** (settled Phase 4a Decision E). The palette is a discrete do-it-now list; a held command has a duration and no key to release, so a palette row for one either does nothing or sticks on. It still needs a title and description — those are its label in the key-binding editor and its hover text in the Phase 8 schema. Expose the two filters as methods on `Capability` so the palette, the keymap validator, and the schema generator read one answer rather than each re-deriving it:

  | | `is_palette_invocable()` | `is_user_bindable()` |
  | --- | --- | --- |
  | `OneShot` | true | true — any sequence |
  | `Held` | **false** | true — single keystroke only |
  | `Unremappable` | true | false |
- **The `Begin`/`End` handler is this phase's, and it is an observer registered by the same construction path** that allocates the inputs — it has to be, because that path is the only place holding the `CommandId` → `CustomInput` map. It lives in `registry.rs`. Phase 11 owns the *matcher* side of the same input; this phase owns only the event side.
- `#[reflect(KeymapCommand)]` is discovered automatically: `reflect_auto_register` is already enabled on this workspace's `bevy`. Note that automatic registration **never covers generic instantiations** (M4), so any generic command type needs an explicit `register_type`.

### Retrospective

**What worked:** `Invocation` held its line — `Held(CustomInput)` is the only place a `CustomInput` is allocated and the bad state stayed unrepresentable. The cached `ReflectEvent` handle resolves once at build time for every capability, so no reflection lookup sits on the input path.

**What deviated from the plan:**
- `KeymapCommand` gained an `Event` supertrait and a **required** `hold_phase(&self) -> Option<HoldPhase>` method, and `ReflectKeymapCommand` gained a `pub(crate) register_held_observer: fn(&mut World, CustomInput)` field. The Work Order said this phase "consumes only that public output"; a typed `On<Event>` observer cannot be built from `ReflectKeymapCommand` alone, so Phase 4a's shipped surface grew by two items. The method has no default body deliberately: a hand-written held command that forgets it fails to compile instead of registering as silently inert.
- `command!` gained a fourth arm — a literal `capability: Held` match emitting `compile_error!`, placed **before** the generic `capability: $capability:ident` arm. Without it that spelling compiled into a command that allocated an input and ignored every event.
- `CommandRegistry`'s façade grew past `title`/`description`/`custom_input` to `CommandInfo<'_>`, `iter()`, and `capability()`. The declared `Capability` was otherwise dropped during construction, leaving `is_palette_invocable()` / `is_user_bindable()` with no external caller.

**Surprises:**
- Arm order matters after all. The Work Order's claim that "it is matched literally rather than through a fragment specifier, so arm order does not matter" holds for the leading `held,` marker but not for the `capability: Held` guard, which must precede the generic arm.
- `ReflectEvent` is re-exported at `bevy::prelude`, not `bevy::reflect`; importing it from the latter is an unresolved-import error.
- `iter()` has to sort explicitly — the backing map is a `HashMap`, and a palette listing and a generated schema both need run-to-run stability.
- `hana_rubric` has no reverse dependency anywhere in the workspace, so no application can reach its runtime path until Phase 12/14. The smoke target is `bevy_lagrange`'s `programmatic_control`.

### Phase 5 — `hana_rubric`: conditions, the `KeymapContext` contract, `ActiveCondition` · status: todo

#### Work Order

**Goal:** an application declares its context enum by deriving strum traits, and the library registers its variants, descriptions, and active value with no glue code in the app.

**Spec:**

`src/condition.rs` — a single file, not a directory: hana owns `InteractionContext`, so what remains here is one small cluster. It holds `ConditionName`, `ConditionRegistry`, the `KeymapContext` trait and its blanket impl, the `ActiveCondition` resource, and the generic sync system.

**The crate cannot name `InteractionContext`** — that enum is hana's, does not exist yet, and hana already depends on this crate; reading it here would be a crate cycle. The crate declares the contract; the application satisfies it by deriving (R7):

```rust
#[derive(Resource, Copy, Clone, Eq, PartialEq, EnumIter, AsRefStr, EnumMessage)]
#[strum(serialize_all = "snake_case")]
enum GameContext {
    #[strum(message = "While flying the ship")]
    Flying,
    #[strum(message = "While the pause menu is open")]
    Paused,
}

app.add_plugins(KeymapPlugin::new().for_context::<GameContext>());
```

`KeymapContext` is a **blanket impl** over `Resource + Copy + Eq + IntoEnumIterator + AsRefStr + EnumMessage + 'static`, so no downstream app writes an impl by hand. One bound instead of six at the call site, a comprehensible compiler error naming the missing derive, and a documented extension point. It takes the same extension-point exception to `dont-create-traits-for-single-implementations` that `KeymapCommand` takes — one implementation *per application*, not one in total.

| library needs | source |
| --- | --- |
| every variant at startup — registry construction, rejecting unknown condition names, the schema's enum of valid strings | `EnumIter` |
| each variant's name as a string | `AsRefStr` + `serialize_all = "snake_case"` |
| each variant's description — schema hover text, generated reference file | `EnumMessage` via `#[strum(message = "…")]` |
| which variant is active right now | `as_ref()` on the current value |

**Two registration entry points over one generic sync system (R8):**

```rust
KeymapPlugin::new().for_state_context::<C>()  // reads Res<State<C>>, C: States + KeymapContext
KeymapPlugin::new().for_context::<C>()        // reads Res<C>,        C: Resource + KeymapContext
```

Both register `C`'s variants and descriptions into `ConditionRegistry` at startup and add the generic change-detection system that writes `ActiveCondition`. Supporting both costs one wrapper function, since the sync system is already generic over `C`. Hana takes the state path; the resource path serves an app that computes its context ad hoc.

- `ConditionRegistry` — variants and descriptions from strum, **duplicate condition ids rejected at load**. A missing `#[strum(message)]` on a variant is caught by startup validation, not by the compiler — same treatment as a missing command title.
- `ActiveCondition` — a plain resource holding **only a registry-resolved condition handle**, updated by change detection. The input path reads this one resource; it never scans contexts, compares strings, or reflects.
- **Mutual exclusivity is structural** — the enum has exactly one active variant by construction. Do not add a runtime check for it; do enforce that duplicate *names* cannot register.
- **The design never needs `in_state::<T>`** — that gates *systems*, while the keymap needs data-driven selection inside one system.
- **The context enum needs no Bevy reflection.** `EnumInfo::variant_names()` is not used and `reflect_documentation` is not needed. Commands still use reflection for dispatch; conditions use none.
- Export a public `KeymapSystems` ordering handle (with at least a `Route` variant) so an app can guarantee its own context derivation runs before the keymap reads it.

### Phase 6 — `hana_rubric`: JSONC document model with retained source spans · status: todo

#### Work Order

**Goal:** a keymap file parses into typed stages that remember where every binding came from, so diagnostics can point at the offending key.

**Spec:**

`src/keymap/mod.rs` (table of contents), `src/keymap/constants.rs` (the sequence timeout — keymap policy, passed into the matcher; the matcher itself owns no timeout), and `src/keymap/document.rs`.

`document.rs` owns source decoding and location indexing: the `KeymapDocument` anchor, its private serde wire structs, JSONC parsing with retained source spans, `BindingEdit`, and `ContextExpr`. Parser tests live beside the types they construct. **Do not split into `wire.rs` + `parse.rs`** — that is the prohibited definitions-versus-construction split; every parser change would cross the boundary, widen visibility, and separate tests from the types they build.

**File format — root object envelope (R4, supersedes the bare root array):**

```jsonc
{
  "$schema": "./keymap.schema.json",
  "bindings": [
    { "bindings": { "space": "transport::toggle_playback" } },
    { "context": "dimension_lock",
      "bindings": { "space": "dimension_lock::pause_tracking", "b": "dimension_lock::toggle_coupling" } }
  ]
}
```

- The document root is an **object**; the ordered blocks array nests under `"bindings"`. The envelope is required because an editor learns which schema applies from a `$schema` member, and an array has no members.
- Each block has an optional `"context"` and its `"bindings"` map. **Order matters** — later blocks override earlier ones for the same key. JSON objects guarantee neither key order nor duplicate-key rejection, so an object keyed by condition cannot express "these bindings, then those on top," and overriding is the entire point.
- Parse with `serde_json_lenient` — comments and trailing commas. The shipped defaults need explanatory comments, and rejecting a trailing comma in a user file is a bad first experience.
- A binding value is a command id **string**, or `null` (the tombstone, R1/D5b). The `[id, args]` array form is *specified* in the type but **rejected in v1** with a diagnostic saying arguments are not yet supported — this keeps A3 additive.

**Typed stages, private where possible:**
- `ContextExpr` — an enum holding **only** `Name(ConditionName)` in v1, so appendix A2 (boolean `&&`/`||`/`!` composition) is additive. A bare name is a valid expression in any boolean grammar, so `"context": "rotating"` parses identically under a future grammar. Document this in the type's doc comment so nobody flattens it to a `ConditionName`.
- `BindingEdit::{ Bind(CommandId), Unbind }` — `Unbind` is the tombstone.
- `KeystrokeSequence` from `bevy_kana`, guaranteeing at least one stroke.

**Source spans are deliberate work, not free.** `serde_json_lenient` reports line and column for *deserialization* errors, but unknown commands, contexts, and keystrokes are detected **after** deserialization, and its public byte offset covers completed stream values rather than per-binding spans. Index source locations during parsing: for each binding record its byte range, 1-based line and column, block index, context, and original keystroke text, keyed so a later semantic failure can retrieve them.

**Diagnose within the document, before any semantic resolution:** duplicate condition names across blocks, and duplicate keys within one block.

**Visibility:** `pub(super)` for `BindingEdit`, `ContextExpr`, and the resolved/merged stages shared among `keymap/` siblings. Note that a `pub(super)` item cannot be re-exported as `pub(crate)` — if the plugin root needs one, the source item must already be `pub(crate)`.

**Files:**
- `crates/hana_rubric/src/keymap/mod.rs` — populate the existing stub (Phase 3 shipped it as a one-line doc stub and `lib.rs` already declares `mod keymap;`)
- `crates/hana_rubric/src/keymap/constants.rs` — create (sequence timeout)
- `crates/hana_rubric/src/keymap/document.rs` — create

**Constraints from prior phases:**
- **This phase adds no `DiagnosticKind` variants.** Decision D's schedule is three passes, not two: Phase 4a shipped `Diagnostic::message` plus `DuplicateCommandId` / `MissingCommandTitle` / `MissingCommandDescription`, **Phase 4b added `InvalidCommandId` and `CommandEventNotReflected`** (11 variants shipped), and **Phase 7 adds the last three** — `HeldCommandInSequence`, `UnremappableCommand`, `ReservedKeystroke` — because all three require registry resolution, which does not exist until Phase 7. This phase reuses the existing variants. Every diagnostic this phase produces sets `message` — the hold-to-act restriction, the reserved-for-recovery explanation, the closest matching command ids, and the registered condition names all go there, not in `suggestions`.
- A binding string parses as a **sequence**, so the error type is `KeystrokeSequenceParseError` — `Empty` (the string held no keystrokes) or `Keystroke` (one chord failed). Match on that enum, not on `KeystrokeParseError` directly. Its `.token()` and `.offset()` are already relative to the whole sequence string, so building a `Diagnostic` means adding the binding's span start to `.offset()` — nothing further.
- **`KeystrokeParseError::at_offset` is `pub(super)`** and unreachable from `hana_rubric`. This crate reads parse failures; it never constructs them.

**The merge algorithm, exactly (all four review lenses converged on this):**

1. Process embedded defaults first, then the user file; within each source, blocks in file order.
2. Canonical merge identity is `(condition-or-global, complete canonical keystroke sequence)`.
3. At each identity the last **valid** edit wins, as either `Bind(handle)` or `Tombstone`. **An invalid edit is skipped and leaves the prior valid entry in place — a bad user line can never erase a working default.**
4. For active context `C` and sequence `S`: use `(C, S)` when present, **including when it is a tombstone**. Only genuine absence falls through to `(global, S)`. A tombstone dispatches nothing and suppresses the global fallback.
5. Tombstones apply to complete sequences, never to prefix subtrees. A tombstone on `g` does not remove `g g`; a tombstone on `g g` lets `g` fire immediately when no other longer sequence survives.
6. **Compile one resolved matcher per context after applying tombstones and global fallback**, so only live sequences contribute prefixes. Cost is `O(contexts × bindings)` of setup memory and reload-time work; it removes context scans, string comparison, reflection, and allocation from the input path.
7. Diagnose duplicate condition names and duplicate keys within one block (Phase 6 does the document-level half; this phase covers cross-source cases).

**Three distinct states at an identity, and the distinction is load-bearing:** absent means inherit the global, a command means replace it, `null` means the key is inert. `"space": null` inside the `dimension_lock` block wins at that identity and dispatches nothing while a lock is engaged; it does **not** expose the global `Space`. **One precedence rule, no specificity ranking:** a binding with a condition beats a binding without one for the same keystroke. Mutually-exclusive computed states mean at most one block is live, so there is nothing to rank — which is why full boolean expressions are deferred (A2).

**Prefix collisions are not a merge concern.** Defaults binding `g g` while the user binds `g` are not the same keystroke, so layering sees no conflict; the matcher resolves it.
