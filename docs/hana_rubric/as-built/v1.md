# hana_rubric v1

## What it is

`hana_rubric` is the Bevy keymap subsystem shared by Hana applications and examples. It owns
semantic command declaration, canonical keystrokes and multi-stroke matching, JSONC parsing with
source locations, default/user layering, context-aware compilation, hot reload, held-input
routing, generated schema and reference files, durable diagnostics, and the registry surfaces used
by command palettes and BRP.

The crate sits between physical keyboard state and application-owned semantic events. Applications
declare commands and contexts; `hana_rubric` resolves authored text into compact handles and
compiled matchers; downstream observers receive the same event regardless of whether it came from
a physical action, a keymap binding, a palette, or a remote invocation.

`bevy_kana` has no input surface in this design. It exposes only cascade and math utilities; all
keymap and enhanced-input integration lives in `hana_rubric`.

## Architecture and data flow

```text
command! declarations
    -> Bevy reflected type registrations
    -> CommandRegistry
       (validated ids, metadata, dispatch functions, held CustomInputs)

embedded defaults + optional user JSONC
    -> KeymapDocument + retained source locations
    -> MergedKeymap
       (semantic validation, layering, tombstones, contexts, conflicts)
    -> CompiledKeymap + KeymapBindings
       (per-context SequenceMatcher<CommandHandle>, stable command table)

ButtonInput<KeyCode> + ActiveCondition + KeystrokeRouting
    -> route_input in PreUpdate
    -> one-shot event dispatch or held CustomInput transition

disk worker
    -> coalesced byte snapshot and transport diagnostics
    -> app-thread reload transaction
    -> wholesale CompiledKeymap replacement
```

### Command declaration and registry

`command!` declares an enhanced-input action marker, a semantic event, and its reflected command
metadata together:

```rust
command! {
    action:      ResetCamera,
    event:       ResetCameraEvent,
    id:          "camera::reset_home",
    title:       "Reset Camera",
    description: "Return the camera to its default framing.",
}
```

The held form generates an event carrying `phase: HoldPhase`:

```rust
command! {
    held,
    action:      FreezeTracking,
    event:       FreezeTrackingEvent,
    id:          "dimension_lock::freeze_tracking",
    title:       "Freeze Tracking",
    description: "Freeze tracking while the binding remains held.",
}
```

The generated event implements:

```rust
pub trait KeymapCommand: Event + Reflect {
    const ID: &'static str;
    const TITLE: &'static str;
    const DESCRIPTION: &'static str;
    const CAPABILITY: Capability;

    fn build() -> Self;
    fn hold_phase(&self) -> Option<HoldPhase>;
}
```

`CommandRegistry::initialize(&mut World)` scans `ReflectKeymapCommand` type data, validates every
declaration, allocates one `CustomInput` for each held command, installs its held-event observer,
and caches a monomorphized `fn(&mut World)` dispatch function. Runtime invocation does not
reconstruct reflected events or look up type data.

The main query and invocation results are named states:

```rust
CommandRegistry::iter() -> impl Iterator<Item = CommandInfo<'_>>
CommandRegistry::lookup(&CommandId) -> CommandLookup<'_>
CommandRegistry::invoke(&CommandId, &mut World) -> CommandInvocationOutcome
CommandRegistry::held_command_lookup(&CommandId) -> HeldCommandLookupOutcome
```

`CommandInvocationOutcome` distinguishes `Invoked`, `UnknownCommand`, and
`HeldCommandRequiresPhase`. Payload-free invocation deliberately refuses held commands because the
caller cannot choose both `Begin` and `End`.

`Capability` controls where a declaration can be used:

- `OneShot`: user-bindable to any supported sequence and palette-invocable.
- `Held`: user-bindable to one keystroke only and omitted from palettes.
- `Unremappable`: rejected from user keymaps but palette-invocable, for application-owned recovery
  commands.

`CommandId` requires exactly one `::` and two ASCII snake-case segments. `CommandId::is_valid` is
the shared `const fn` used by the macro's compile-time assertion and runtime parsing. The newtype is
reflected as opaque so reflection cannot mutate its private string into an invalid value.

### Keymap document and semantic resolution

The JSONC root is an object with an optional `$schema` and required ordered `bindings` array:

```jsonc
{
  "$schema": "./keymap.schema.json",
  "bindings": [
    {
      "bindings": {
        "g r": "camera::reset_home",
        "shift": "selection::modify_selection"
      }
    },
    {
      "context": "dimension_lock",
      "bindings": {
        "p": "dimension_lock::freeze_tracking",
        "g r": null
      }
    }
  ]
}
```

Each block contains an optional context name and a binding map. A value is either a command-id
string or `null`; `null` is a tombstone. The future `[id, args]` shape is recognized as a reserved
direction but rejected in v1.

`KeymapDocument::parse` runs two passes over the same source:

- `serde_json_lenient` decodes comments, trailing commas, and typed values.
- `JsoncScanner` records byte ranges and one-based line/column locations.

The custom binding-map deserializer preserves duplicate keys and source order. Unknown root or
block members and duplicate authoring receive advisory diagnostics instead of discarding otherwise
valid bindings.

A whole-document failure returns `Err(Vec<Diagnostic>)`. A successful parse returns the usable
document and any per-binding diagnostics together; callers must preserve the success-side
diagnostics.

Layering is resolved before matcher construction:

1. Embedded defaults are applied first, then the user document.
2. Identity is `(global-or-condition scope, complete canonical sequence)`.
3. The last valid edit at an identity wins. An invalid edit is skipped and cannot erase a valid
   lower-layer default.
4. A context-scoped edit replaces the global edit at the same sequence. A context tombstone
   suppresses global fallback; only true absence inherits it.
5. Tombstones remove complete sequences, not prefix subtrees.
6. Unknown contexts contribute no edits.
7. Global bindings are folded into each condition's effective binding set before compilation.
   Runtime does not perform a second global lookup.

Held-prefix conflicts are resolved after layering. Across default and user layers, a valid held
binding wins and the longer sequence is rejected, regardless of which layer supplied the hold.
Within one layer, both the hold and the longer conflicting sequence are rejected because neither
can be interpreted as an override. A tombstone remains the explicit way to remove a lower-layer
hold before introducing a longer sequence.

Validation also rejects:

- unknown command or context names;
- an `Unremappable` command in a keymap;
- a sequence beginning with a protected recovery keystroke;
- a held command bound to more than one keystroke;
- a bare modifier unless it is the sole keystroke of a held command.

### Keystrokes and sequence matching

The canonical key model is:

```rust
pub struct Modifiers { /* family bits */ }
pub enum ModifierFamily { Control, Alt, Shift, Platform }
pub struct OrdinaryKey(KeyCode);
pub enum PrimaryTrigger {
    OrdinaryKey(OrdinaryKey),
    ModifierFamily(ModifierFamily),
}
pub struct Keystroke {
    modifiers: Modifiers,
    primary_trigger: PrimaryTrigger,
}
pub struct KeystrokeSequence { /* non-empty keystrokes */ }
```

Physical Control and physical Super are distinct on every platform. `secondary` is a parse-time
alias: it means Platform on macOS and Control elsewhere. Platform-family output renders as `cmd` on
macOS and `super` elsewhere; `platform` is accepted but never emitted. Bare `shift`, `ctrl`, `alt`,
and `secondary` are legal primary triggers.

`OrdinaryKey` accepts only entries in `CANONICAL_KEY_MAPPINGS`; unsupported `KeyCode` values are
inert rather than pretending to be routable keys. `KeystrokeSequence` is non-empty by construction.

`SequenceMatcher<T: Copy>` is a flat prefix index over canonical `Keystroke` values. Its public
outcomes make deferred and reprocessed input explicit:

```rust
MatchOutcome::{
    Matched(T),
    Deferred(T),
    Pending,
    Reprocess {
        deferred_match: DeferredMatch<T>,
        keystroke: Keystroke,
    },
    NoMatch,
}

DeferredMatch::{Fire(T), NothingToFire}

TimeoutOutcome::{
    Resolved(T),
    DiscardedPartialPrefix,
    AwaitingKeystroke,
    NoPendingSequence,
}
```

A binding such as `g` defers while `g g` remains possible. On timeout, `g` fires. If the next
stroke does not continue the prefix, the deferred command fires first and the unmatched stroke is
processed once more from the root. The matcher performs no parsing or allocation.

### Contexts

Applications define a context enum by deriving `AsRefStr`, `EnumIter`, and `EnumMessage`; the
blanket `KeymapContext` implementation supplies the contract. Variant names become authorable
condition names, and each `#[strum(message = "...")]` supplies schema documentation.

A plugin chooses exactly one source:

```rust
KeymapPlugin::new().for_context::<C>()
KeymapPlugin::new().for_state_context::<C>()
KeymapPlugin::new().for_derived_context(DerivedContext<C>)
```

`DerivedContext<C>` is an ordered table of run conditions:

```rust
pub struct DerivedContext<C> { /* rules and fallback */ }

pub fn new(fallback: C) -> Self;
pub fn when<M>(
    self,
    context: C,
    condition: impl SystemCondition<M>,
) -> Self;
```

First matching rule wins; otherwise the declared fallback applies. Rule order is therefore
semantic. Conditions must describe current world facts, not change-history state such as
`Changed<T>`, `Added<T>`, readers, or `Local<T>`, because short-circuiting means lower rules do not
run while a higher rule matches.

`ActiveCondition` exposes:

```rust
pub enum ActiveConditionState {
    AwaitingContext,
    GlobalRouting,
    ResolvedCondition {
        handle: ConditionHandle,
        name: ConditionName,
    },
}
```

The handle selects the compiled matcher; the name makes the reflected resource meaningful to BRP.
The ignored reflected handle defaults to an unissuable sentinel, so remotely reconstructing a named
condition cannot accidentally select condition zero.

### Runtime and held input

`route_input` is an exclusive `PreUpdate` system ordered after Bevy `InputSystems` and before
`EnhancedInputSystems::Update`. It selects the global or condition matcher from `ActiveCondition`,
resolves sequence timeouts, consumes release edges before press edges, and dispatches matched
commands.

The steady-state input path performs no heap allocation, string parsing, reflection lookup, or
full-keymap scan. Names have already become `CommandHandle` and `ConditionHandle` values; one-shot
dispatch copies out a function pointer before triggering the event.

Held state has one owner: `keymap/runtime/`. Each held command owns one registry-allocated
`CustomInput`. Physical matching and semantic `HoldPhase` events are two refcounted sources for that
input; it remains active while either source remains. Applications keep statically spawned
enhanced-input actions bound with `Binding::Custom(id)`, so remapping changes which key drives the
input without replacing the action entity or causing release/restart flicker.

A keymap generation change, context change, or keyboard-ownership handover:

- cancels pending sequences without firing them;
- releases physical held sources while preserving semantic-event sources;
- publishes resulting custom-input transitions;
- inhibits keys still physically down until they are released.

Left and right keys in one modifier family are independently counted, so a bare Shift hold ends
only after both physical Shift keys are up.

`KeystrokeRouting` handles text entry without stopping the routing schedule:

```rust
take_for_text_entry(
    &mut self,
    owner: KeyboardOwner,
    exempt_commands: impl IntoIterator<Item = CommandId>,
) -> KeyboardClaim;

release(
    &mut self,
    owner: KeyboardOwner,
) -> KeyboardRelease;
```

While a text field owns the keyboard, routing still consumes releases but dispatches only exempt
commands. `KeyboardOwner` prevents one text-entry feature from releasing another feature's claim.
Keeping routing alive is essential: gating the whole route set loses `just_released` edges and can
leave a held command logically pressed.

### Plugin assembly, reload, and disk ownership

The usual application wiring is:

```rust
KeymapPlugin::new()
    .with_app_name("hana")
    .with_defaults(include_str!("keymap.default.jsonc"))
    .with_protected_keystroke(recovery_chord)
    .for_derived_context(derived_context)
```

Embedded defaults commit synchronously before paths, schema generation, or worker startup, so
bindings are live from the first frame and remain usable when no configuration directory exists.

`KeymapPathAvailability` is always inserted:

```rust
KeymapPathAvailability::{
    Resolved(KeymapPaths),
    Unavailable(KeymapPathFailure),
}
```

No application name means defaults-only operation and no filesystem worker. Supplying configuration
without defaults records `MissingDefaultKeymap` and stops before constructing `CommandRegistry`;
adding a completely unconfigured plugin similarly records `UnconfiguredKeymapPlugin`.

A dedicated thread owns all filesystem work:

- resolve the application configuration directory;
- publish the generated default reference and JSON Schema;
- create the first-launch user stub only when absent;
- watch the configuration directory non-recursively;
- also watch an external symlink target's parent when required;
- debounce editor save bursts;
- retry transient absence;
- audit by polling even when native notifications appear healthy;
- report confirmed deletion as a defaults-only snapshot.

The application thread alone parses, validates, merges, compiles, and swaps ECS resources.

The worker uses a capacity-one coalescing slot containing the newest complete snapshot plus bounded
diagnostics. Dropping its channel resource stops and joins the worker; there is no second shutdown
system.

Companion publication uses a same-directory temporary file, changes it to read-only, then renames
it over the destination without following the destination symlink. Existing byte-identical files
are left untouched. The default reference is a generated comment header—protected keystrokes and
registered contexts—followed by the embedded JSONC. The schema is generated from the live command
and condition registries and excludes unremappable commands from binding completion.

Reload is transactional:

- invalid UTF-8 or a document-level parse failure records diagnostics and preserves the current
  generation;
- a successful document with bad individual bindings commits defaults plus all valid edits;
- confirmed user-file deletion commits a defaults-only generation;
- each committed generation replaces both `CompiledKeymap` and `KeymapBindings` wholesale.

`DiagnosticSeverity` and retention are separate concerns. `KeymapLoadFailures::diagnostics` holds
reload and transport reports; `retained_diagnostics` holds startup failures a later reload cannot
reproduce. Merge-derived diagnostics are replaced on each attempted load, while disk and companion
diagnostics remain until bounded retention discards older entries.

`DiagnosticOrigin` identifies the producer without string heuristics:

```rust
KeymapFile(PathBuf)
KeymapDirectory(PathBuf)
EmbeddedDefaults
ContextRegistration
CommandRegistration
DiskWorker
PathsUnavailable(KeymapPathFailure)
```

Diagnostics contain only stable display data—origin, byte range, line, column, block, context,
original keystroke, command id, kind, severity, message, and suggestions—never registry handles or
compiled-stage types.

## Consumer integrations

### Hana

Hana's consumer implementation lives in its `feature/rubric` checkout.

`crates/hana/src/input/mod.rs` installs `hana_rubric` with Hana's embedded defaults, the protected
recovery chord, and a derived `InteractionContext`:

- `resting`;
- `dimension_lock`;
- `dimension_lock_rotation`.

The rotation context requires a lock and expanded rotate affordance belonging to the same
selection. The more specific rotation rule precedes the general lock rule.

Hana declares semantic commands across their owning modules. Two are held—
`selection::modify_selection` and `dimension_lock::freeze_tracking`—and use statically spawned
`Binding::Custom` actions. `inspect::open_command_palette` is unremappable. The three repair
commands are unbound one-shot commands:

- `keymap::open_user_keymap`;
- `keymap::open_default_keymap`;
- `keymap::reveal_configuration_directory`.

`crates/hana/assets/keymap.default.jsonc` contains the shipped ordinary and context-specific
bindings. The recovery chord is deliberately absent. It is Cmd+P on macOS and Ctrl+P elsewhere,
read directly from `ButtonInput<KeyCode>` before normal routing. Its handler cancels pending
sequences and triggers `OpenCommandPaletteEvent` without consulting either the compiled keymap or
`CommandRegistry`, so it still works when either is broken. The same chord is passed to
`with_protected_keystroke`, preventing a user binding from shadowing it.

Escape remains a declared semantic command with Rust-owned physical arbitration. Its ordered
handlers and rotation guard are one ownership boundary; it is not represented as several keymap
commands that could all fire from one press.

`crates/hana/src/input/command_brp.rs` publishes `hana/invoke_command`, which accepts a short
`CommandId` and routes through `CommandRegistry::invoke`. Unknown ids return the declared-id list;
held commands are refused. The reflected `ActiveCondition` resource supplies the stock BRP context
read.

Hana's palette is implemented independently under `crates/hana/src/tool/command_palette/`; it does
not depend on `fairy_dust`. It provides:

- a full-window screen-space overlay with a centered command surface;
- title/id search normalized across case, `::`, `_`, `-`, and whitespace;
- deterministic title-then-id ordering;
- live keystroke labels from `KeymapBindings`;
- omission of held commands and inclusion of one-shot and unremappable commands;
- both reload and retained diagnostic rows, with distinct failure/advisory colors;
- an absolute user-keymap header and origin-appropriate Open/Reveal actions;
- `ImeReplacePanelTree` rebuilds that preserve the active caret and selection;
- commit-authority checks before invocation;
- route-command failures rendered back into the still-open palette.

When the IME field owns the primary window, Hana claims `KeystrokeRouting` with
`inspect::open_command_palette` exempted. The same recovery command can therefore close the palette,
while bare application keys no longer dispatch into the scene as query text is entered.

The Hana workspace currently resolves `hana_rubric`, `hana_diegetic`, `hana_clerestory`,
`hana_conduit`, `hana_lading`, and `hana_prosody` through sibling path dependencies. This keeps one
`hana_diegetic` type identity through the graph. Repointing only Hana's direct `hana_diegetic`
dependency would recreate duplicate panel and event types.

### Fairy Dust

`crates/fairy_dust/src/keymap.rs` installs one baseline `KeymapPlugin` for every Fairy Dust app,
whether or not the palette is enabled, because Fairy Dust's own capabilities are declared commands.
`CommandPaletteKeymap` records defaults, optional application directory, and protected keystrokes
before terminal builder execution installs the plugin once.

`crates/fairy_dust/src/command_palette/` is the reusable example of a registry-driven palette. It
uses the same `KeymapBindings`, diagnostic origins, IME tree replacement, keyboard ownership, and
registry invocation surfaces. Hana copied the behavior and layout concepts but owns a separate
implementation that may diverge.

## Invariants

- The steady-state input path performs no allocation, parsing, reflection lookup, or full-keymap
  scan.
- `keystroke/` remains domain-free: no JSON, command registry, conditions, tombstones, disk, or
  `World`.
- A compiled generation is replaced wholesale; matchers are mutable because pending sequence state
  belongs to them.
- Semantic command events are the convergence point. Keymap, palette, BRP, and enhanced-input
  routes must not invent parallel handler APIs.
- Held-source ownership remains entirely in `keymap/runtime/`; consumers may bind its `CustomInput`
  but must not mirror its refcounts or inhibition state.
- Physical Control and physical Super remain distinct. `secondary` is an alias, not a fifth stored
  modifier.
- A context tombstone suppresses global fallback. Runtime fallback lookup must not be added.
- A protected keystroke protects the first stroke of every sequence; an unremappable capability
  protects a command. They solve different problems.
- Exactly one context source may be registered per app.
- Validated reflected newtypes remain opaque.
- Diagnostics remain acyclic stable data and do not retain internal handles.
- The dual `MIT OR Apache-2.0` license remains intact; keystroke and matching behavior is
  independently implemented, not copied from an Apache-only source.

## Calibration and gotchas

- Sequence timeout: 1 second from the most recent matched stroke.
- Disk debounce: 100 ms.
- Missing-file retry: 50 ms.
- Poll audit: 5 seconds.
- Maximum retained diagnostic batch: 64.
- Companion mode on Unix: `0444`.
- Temporary companion-name attempts: 32.
- Config roots honor `$XDG_CONFIG_HOME`; macOS otherwise uses `~/.config/<app>` rather than
  `~/Library/Application Support`.
- `KeymapBindings` reports a command's global binding first; if it is condition-only, it reports
  the earliest registered condition's binding. It is deterministic display metadata, not an
  active-context query.
- `CommandRegistry::invoke` cannot drive held commands. Trigger the held event with an explicit
  `HoldPhase` when scripting a hold.
- `command!` still generates an `InputAction` marker for commands that have no physical
  enhanced-input action. There is no event-only arm.
- A `command!` call site must import `InputAction`, `Event`, `Reflect`, `ReflectEvent`, and
  `ReflectKeymapCommand` unqualified because the macro-generated derives resolve them at the
  invocation site.
- Automatic reflection registration does not cover generic instantiations; generic command types
  require explicit registration.
- `SequenceMatcher::new` itself is last-wins for duplicate sequences. Semantic resolution must
  continue reducing every identity to one live edit before construction.
- Do not disable `KeymapSystems::Route` for text input. Claim `KeystrokeRouting` instead so release
  edges are still consumed.
- A derived context transition is state-backed and may take additional schedule passes to reach
  `ActiveCondition`; callers must not assume same-frame routing after changing source components.
- Calling `finish()` on a configured keymap plugin starts the worker and writes files. Tests must
  isolate the configuration root rather than touching the developer's real keymap.
- Hana's repair helper uses `create_new` and never overwrites an existing user file; normal
  configured startup has already created the library's valid empty stub.

## Why it is this way

Semantic events are the registry unit because they are meaningful to application observers and
remote callers; input-action markers are only one physical delivery mechanism.

The parser retains a second source index because serde alone cannot preserve the exact duplicate
keys, byte spans, and author spelling needed for actionable diagnostics. The semantic merge remains
separate from parsing so unknown commands, conditions, capabilities, protected chords, and
cross-layer conflicts can be validated against live registries.

Global bindings are premerged into every condition matcher and command ids become handles because
reload is allowed to spend memory and CPU while the input path is not. Wholesale replacement also
gives failed whole-document reloads a simple contract: keep the prior generation unchanged.

Filesystem work runs on a dedicated thread because editor rename-over saves, network filesystems,
watcher failures, symlinks, retries, and read-only companion replacement are latency and reliability
concerns that do not belong in Bevy's frame schedule.

Keyboard text-entry ownership is represented inside routing because stopping routing loses release
edges. A tokenized handover lets several UI features coexist without releasing each other's claims.

The recovery chord belongs to the application while the library owns its reservation. That keeps
`hana_rubric` independent of Hana's UI and context model while ensuring recovery bypasses the two
things it must repair: a broken keymap and a broken command registry.
