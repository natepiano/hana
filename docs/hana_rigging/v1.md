### Doc comment checklist (invariant 11)

- A type or method says **what situation it exists for** and what goes wrong without it.
- Every enum variant says **what the system or the user would observe**, with the concrete device that motivates it. A variant comment that only rephrases the variant name is a defect.
- Where a kernel rule overrides a policy, **the policy's own comment states the override**.
- Where a name was chosen against a plausible alternative, **the rejected name and reason belong in the comment** when the alternative would mislead.
- A `#[non_exhaustive]` attribute **states why it is there**; its absence needs no comment.

The test: a reader who has not read this plan can answer, from the doc comments alone, why the type exists, what each choice makes the system do, and which choice fits their device.

## Phases

### Phase 1 — Crate skeleton and durable identity  · status: done (967c5159)

#### As-built

`crates/hana_rigging` is a Repo A workspace member, entered in the root `[workspace.dependencies]` as `hana_rigging = { version = "0.1", path = "crates/hana_rigging" }`. It depends on `bevy`, `serde`, and `thiserror` and on no device crate — a kind crate depends on `hana_rigging`, never the reverse.

Two identifiers, kept apart by shape:

- `DeviceId(u64)` — opaque runtime handle issued by a monotonic counter on `Devices`, incremented once per newly-seen `DeviceKey` and never reused within a process. Private field, no constructor or integer accessor outside the crate, `Reflect` with no serde, and `#[reflect(Component)]`. It occupies exactly one single-field component and appears inside no other type; that one-component rule is what keeps it out of the persisted set.
- `DeviceKey { kind: DeviceKind, id: DeviceIdSource }` — durable, serde + `Reflect`. The nested `id` variant, not a string field, says whether the identifying value is proof or a hint.

`DeviceIdSource` is the trust level: `Reported { scheme: SchemeName, value: ReportedId }`, `Synthesized { digest: Digest }`, `Authored { value: AuthoredId }`. `Reported` means a value the unit published about itself *and* durable across reboot and replug — two independent conditions, and the only source that can authorize in-service use. `Synthesized` is a hint derived from descriptors: it may restore a saved configuration, it never drives output.

`SchemeName`, `ReportedId`, `AuthoredId`, and `Digest(u64)` are newtypes with private fields and checked constructors returning errors (the workspace forbids `panic`/`unwrap`/`expect`). `Digest` is a fixed-width FNV-1a `u64`, not a `String`, so a malformed digest is unrepresentable. Each has a hand-written `Deserialize` running the same syntax check as its constructor, because a derived `Deserialize` on `DeviceKey` would otherwise construct one directly.

Scheme validation splits across two boundaries. Syntax lives in the newtype. Registration lives in the `RegisteredSchemes` resource, populated at app-build time through `register_device_scheme`; `RegisteredSchemes::validate` is a checked method with unit coverage, applied at the ingest boundary where keys first enter kernel state, not at startup.

`DeviceKind` is `#[non_exhaustive]` — variants `Display`, `Camera`, `AudioInterface`, `DmxUniverse`, `HidPanel`.

**Files:**
- `crates/hana_rigging/src/identity.rs` — `DeviceId`, `DeviceKey`, `DeviceIdSource`, `DeviceKind`
- `crates/hana_rigging/src/scheme.rs` — `SchemeName`, `ReportedId`, `AuthoredId`, `Digest`, `RegisteredSchemes`
- `crates/hana_rigging/tests/compile_fail.rs` + `crates/hana_rigging/tests/compile_fail/` — trybuild harness (target name `compile_fail`), one case plus committed `.stderr` per compile-time guarantee. `device_kind_requires_a_wildcard_arm.rs` (test fn `device_kind_requires_a_wildcard_arm`) reproduces a downstream wildcard-less match on `DeviceKind`; `constructor_bypass.rs` proves the newtype private fields.

**Binds later work:** a scheme names an *identity space*, not an OS or platform, so two reporters may register the same scheme name — that is the co-report join and the migration hinge. Validation therefore checks syntax and registration, never uniqueness. RON round-trip shape, asserted by the serde tests: `DeviceKey(kind: HidPanel, id: Reported(scheme: "usb-serial", value: "CL15K1A00080"))`.

**Gotchas:** `verify.sh test <pkg>` pins `--lib --bins`, so a `compile_fail` doctest is compiled by nobody and asserts nothing — every compile-time guarantee is a `trybuild` case run as `verify.sh test hana_rigging compile_fail`. Keeping `DeviceId` unpersisted is a serialization-exclusion configuration rather than a structural impossibility, so the test asserting a saved device entity serializes with no `DeviceId` is mandatory.

**Ruled out:** `Reflect`-without-serde as the never-persist mechanism — reflected components serialize field-by-field without needing `Serialize`; a startup-time scheme check — validation happens at the ingest boundary instead.

### Phase 2 — Identity evidence and the verdict enum  · status: done (59519f9e)

#### As-built

### Phase 3 — Presence, claim, capabilities, device records, scans, and endpoints  · status: done (00bada98)

#### As-built

`Presence` is `Present` / `Absent` / `Unreachable { since }`. `Unreachable` is separate from `Absent` because collapsing them either resurrects retired outputs or destroys live ones.

`ReportedAs` is how a reporter names a unit, two cases rather than `Option<DeviceKey>`: `Keyed(DeviceKey)`, or `MatchEvidenceOnly` — the reporter sees the unit, has no durable name for it, and contributes evidence joined to a keyed report on `os_id`. ### Phase 4 — Recovery policy and the three attempt policy enums  · status: done (4bf1b6b9), revised by phase 4b

#### As-built

`RecoveryPolicy` answers what to keep: `Forget` (the `Default`, not retained), `Retain` (remember, report, never touch), `ReapplyOnRequest` (re-apply on demand), `ReapplyOnReturn` (re-apply automatically once the returning unit is verified). It is flat and `Copy`, so "re-apply what you never kept" is unrepresentable rather than rejected at construction — no cell to write it in, no constructor to reject it, no public field to bypass one. It is deliberately **not** `#[non_exhaustive]`: exhaustive downstream matching is the intended use and a new variant should be a breaking change the kernel is forced to acknowledge. `#[non_exhaustive]` is reserved for sets that grow with hardware the kernel cannot enumerate — `DeviceKind`, `IdentityVerdict`, `UnverifiedReason`, `DeviceAccessError`. Policy is fixed at registration — a change is cancel plus re-register — and is copied where entity loss cannot erase it.

The three attempt policy enums; together with `RecoveryPolicy` these are the four policies later gates name collectively:

- `RetryOn { NewRevision, Interval(Duration) }`, `NewRevision` the `Default`. It controls whether and when one failed attempt retries, and nothing else — it does not cover capture readback. `NewRevision` keys on the device's own `DeviceRevision`, so a scan reporting it unchanged is not a retry signal and the retry cannot loop forever. `Interval` exists because a camera held open by another application becomes free when that application quits: no device appears or disappears, so a revision-gated retry would never fire. `RetryOn` is a plain enum with no `#[non_exhaustive]` — downstream constructs it and the kernel matches it, so no downstream match exists to break, and a `_` arm is exactly where a new variant gets silently swallowed.
- `OnAbort { LeaveAsIs, Revert }`, `LeaveAsIs` the `Default`. Consulted only when an attempt was abandoned because the device set changed. `LeaveAsIs` suits a device whose reconfiguration is slow or visible — a projector lamp takes tens of seconds — since the set change is about to produce a new target anyway; `Revert` suits a half-applied state that is itself wrong, such as a window parked between two monitors.
- `OnSessionLoss { Recreate, ReportOnly }`, `Recreate` the `Default`. Covers a local session dying on its own for a still-present device — a window destroyed by the compositor, a capture session invalidated across sleep, a HID handle closed by a bus reset — distinct from device absence, which `Presence` and `RecoveryPolicy` handle, and from an abandoned attempt. `Recreate` opens a new session and re-applies the captured configuration without involving application code; it runs as an ordinary attempt so `RetryOn` gates it, and **the rebuild reuses the published image handle so bound materials survive**.

**Kernel abandonment rules:** what happens to an attempt's device is a kernel decision, not policy, except in the third row.

| abandonment cause | rule |
| --- | --- |
| claim lost | never revert — reverting is impossible, not undesirable |
| service vetoed | never revert — re-sending may re-energize a device whose interlock just opened |
| revision changed | consult `OnAbort` |

### Phase 6 — Reporter and driver contracts, type-erasing registration, plugin and set  · status: done

#### As-built

Two traits, because reporting what hardware exists and driving one endpoint are served by different implementations for the same unit, and a merged trait would make `start_apply` — the method that receives the kernel's authorization — a no-op on half of them. `DeviceReporter::discover(&mut self) -> DiscoveryWork` receives **no `World`** and touches no device. `EndpointDriver` carries `type Configuration: Reflect + Component` (`Reflect` so the kernel can hold it erased in `CapturedConfiguration`, `Component` so phase 11 can insert it on the binding entity through `ReflectComponent`), `capture(&mut self, world, endpoint) -> CaptureOutcome<Self::Configuration>`, `start_apply(&mut self, world, endpoint, configuration, attempt: AttemptId, permit: ApplyPermit)` — absolute, not differential, and returns immediately — and `poll(&mut self, world, attempt: AttemptId) -> AttemptProgress`, polled each reconcile until it resolves. **There is no `fulfillment` method**: `poll` returning `AttemptProgress` is the driver's whole outcome vocabulary, and judging "close enough" (60 fps satisfied at 59.94 is `Succeeded`; a window landing on another display is `Substituted`) is a private driver helper. `CaptureOutcome<P>::{Read(P), NotReadable, ReadFailed(DeviceAccessError)}` — `NotReadable` is permanent and the kernel stops asking; `ReadFailed` keeps the previous captured value. It is the one generic kernel type: it never reflects, never lands on an entity, and never enters a registered resource, and no other type may take that exemption.

`ApplyPermit(Purpose)` is a private-constructor token minted only by the kernel and the only token `start_apply` accepts; `Purpose::{InService, RestoreOnly}` is private and `allows_in_service_use() -> bool` is the public predicate. It carries `#[reflect(opaque)]`, as do `ReporterId`, `DriverId`, and `ReporterRevision`, so `FromReflect` cannot bypass a private constructor.

Registration erases the associated type. `Reporters` holds non-generic entries owning a reporter closure plus the registry-issued id and revision counter; `Drivers` holds non-generic entries owning `Box<dyn Any + Send + Sync>` plus typed function pointers for capture, start, and poll, installed once by the entry's generic constructor. Every erased method returns `Result<_, DriverContractError>` — a crossed configuration type or a driver/entry pairing failure yields `DriverTypeMismatch`, which the kernel logs and turns into `AttemptOutcome::Failed` rather than unwrapping. `RiggingAppExt` is the single public extension trait carrying `add_device_reporter(reporter, ReporterRegistration) -> ReporterId`, `add_endpoint_driver(driver) -> DriverId`, and `register_device_scheme(name)`; each id is registry-issued and neither trait exposes a way to construct one. `register_device_scheme` is reached through this app extension and calls `init_resource::<RegisteredSchemes>()` first, so an integration plugin added before or after `RiggingPlugin` behaves identically; registration is idempotent and two crates registering one name is the co-report assertion phase 9's merge rests on.

**Registration resources are removed from `World` for the duration of each dispatch** — the kernel calls through `world.resource_scope::<Reporters, _>` / `::<Drivers, _>` — so a reporter or driver cannot read its own registry while dispatched, and touching it panics. An implementation must also not mutate kernel-owned state (`Devices`, `Attempts`, `RiggingRevision`, device or binding entities) through the `&mut World` it is handed; it reports through its return value alone. A reporter or driver panic is fatal and is not caught.

`RiggingPlugin` builds the kernel resources and `RiggingSystems` (`#[non_exhaustive]`, so a set can be added without breaking a `.after(..)`) chained in `Update` as `Collect → Reconcile → Prepare → Apply` at `plugin.rs:72-81`. `RiggingSystems::Prepare` is the consumer slot the kernel schedules nothing in: it exists for the point where identity and authorization are decided but no `start_apply` has started, which is the only interval in which a consumer can compute the parameters it is about to request. An integration crate validates its environment in `Plugin::finish`, never `build`, so correctness does not depend on plugin insertion order.

### Phase 7 — Asynchronous discovery scheduling, startup readiness, and progress state  · status: done

#### As-built

The kernel owns discovery cadence, batching, task admission, completion collection, and startup readiness; a reporter owns only its integration-specific enumeration and returns owned results. No worker mutates `World`, `Devices`, `Bindings`, entities, revisions, or retained reports, and this phase creates no live `Device` entity — a live entity stays evidence-backed and comes only from reconciliation.

`DeviceReporter::discover` returns `DiscoveryWork::{Immediate(MainThreadDiscoveryJob), Background(DiscoveryJob)}`. `MainThreadDiscoveryJob::new(|world| { … })` is the only thing receiving `&mut World`: it is invoked synchronously, never stored in reporter runtime state, never eligible for `IoTaskPool`, and may only copy already-available state (winit monitor enumeration and other `!Send` main-thread APIs). A `DiscoveryJob` captures sendable inputs while `discover` is on the main thread and runs on `IoTaskPool`. `DeviceScan::{Complete(Vec<DeviceRecord>), Failed(DeviceAccessError)}`; `Unchanged` is gone — not calling a reporter is the self-documenting unchanged case. The registry stamps `ReporterId` and advances `ReporterRevision` only when `Complete` is accepted on the main thread; `Failed` retains the preceding set and revision. **Two-update acceptance:** an immediate result is accepted only on the app update *after* its main-thread job runs.

Registration states how a reporter becomes due and what its silence means: `ReporterRegistration::required(cadence, coverage)` and `ReporterRegistration::optional(cadence, activation, coverage)` — the arities differ, and `required` always starts enabled and cannot be disabled. `ReporterActivation::{Enabled, Disabled}`. `DiscoveryCadence::{OnDemand, EventDriven { backstop: Duration }, Periodic { interval: Duration }}`. `ReporterCoverage::{MatchingEvidenceOnly, EstablishesAbsence(AuthoritativeReporterCoverage)}` with `AuthoritativeReporterCoverage::one(..)` over `CoveredDeviceIdentitySpace::AllKeysOfKind { kind: DeviceKind }`. A reporter registered `MatchingEvidenceOnly` **cannot establish absence** — its successful scan produces no departure, no `DeviceDeparted`, and no `Absent → Present` reacquisition. `ReporterRegistration` and the `DiscoveryControl` resource are `#[reflect(opaque)]` / `#[reflect(Resource, opaque)]` so dynamic reflection cannot bypass their checked methods; `DiscoveryControl` exposes `enable`, `disable`, `request`, and `mark_dirty`, returning `DiscoveryControlError` for an unknown id or an attempt to disable a required reporter, leaving state unchanged. Enabling runs one immediate discovery; disabling cancels queued work only, never drops a running task, and suppresses the coalesced rerun after it reports.

Scheduling computes the whole due list per frame, coalesces duplicate triggers by `ReporterId`, assigns one `DiscoveryBatchId`, then admits jobs — required-startup reporters form the first batch, optional reporters stay out of the due list until startup is ready (their request, dirty signal, and expired deadline remain unconsumed) and then arrive under a distinct batch id. There is no completion barrier after admission. `ReporterRunState::{Disabled, Idle, Queued { batch }, Running { task, rerun }}` with `RerunRequest::{NotRequested, Requested}` guarantees **no duplicate jobs**: a running reporter is never resubmitted and any number of intervening triggers collapse into one later rerun, so a missed interval reruns once with no catch-up burst and a periodic deadline advances from the actual submission schedule. `StartupDiscoveryState::{Discovering, Ready, BlockedByFailure { reporter, error }}` plus the `hardware_ready` run condition gate the app: readiness is derived across the complete required set, so an accepted required failure outranks incomplete required reporters regardless of registration order, and only the absence of failures permits `Discovering` or `Ready`.

`DiscoveryLimits` holds `max_concurrent_jobs`, `max_completions_per_frame` (both `NonZeroUsize`, so a limit cannot switch discovery off), and `progress_after`, with getters, checked setters, and `effective_max_concurrent_jobs`; defaults are two jobs, two completions per frame, 500 ms. Effective concurrency is `min(configured, max(1, IoTaskPool::thread_num() - 1))` — the admission reserve leaves one I/O thread outside discovery whenever the pool has two or more threads, and a one-thread pool admits one job as the unavoidable exception. A runtime change governs the next admission or completion pass and never cancels running work. The per-frame completion budget counts whole reporter results, prioritizing required then oldest queued; a `Complete(Vec<DeviceRecord>)` is atomic and is never split across frames, and remaining finished tasks are retained for the next frame.

`DiscoveryProgress::{Indeterminate, Measured { completed: u32, total: NonZeroU32 }}` flows through `DiscoveryProgressSender` without the job learning its `ReporterId`; the scheduler attaches id and batch. Delivery is a coalescing **single-slot** mailbox per reporter, not a queue. `DiscoveryStatus` is a reflected resource retaining **only current** status — latest activity, progress, outcome, batch counts, and startup state — with no ordered transition history: `ReporterDiscoveryStatus { activity, last_outcome, completed_batches }`, `ReporterActivity::{Disabled, Idle, Queued { batch }, Running { batch, elapsed, progress }}`, `LastDiscoveryOutcome::{NotCompleted, Succeeded { batch, duration }, Failed { batch, duration, error }}` — named variants throughout, no bare optional fields, so a previous success or failure stays visible while the next run is idle, queued, running, or later disabled. The non-reflected registry retains each reporter's latest registry-stamped `DeviceSet` and completion time (`ReporterDeviceSetState`), and the collect-to-reconcile handoff is crate-private: a queue of changed `ReporterId`s plus failures, which phase 9 drains while borrowing every retained set so an unchanged co-reporter's evidence needs no clone.

### Phase 8 — Bindings: registration, routing, and the role lifecycle  · status: done

#### As-built

- `Bindings` is the authoritative resource for durable endpoint ownership, role state, recovery policy, and configuration; binding entities and `ResolvedToDevice` are read-only projections. It is keyed by `RoleKey` with two private reverse indexes (`owner_by_endpoint: HashMap<DeviceEndpoint, RoleKey>`, `roles_by_device: HashMap<DeviceKey, …>`). `Bindings::register` — a duplicate endpoint is a configuration error, surfaced not overwritten — returns `BindingError::EndpointAlreadyOwned { endpoint, owner }` rather than panicking or admitting a second owner. `replace` validates the proposed endpoint before releasing the old one, so failure leaves all three maps and the old binding unchanged; `retire` is idempotent, clears all three indexes atomically, and yields `RetirementOutcome::Retired(Binding)` or `AlreadyUnbound`. Read paths are `binding(&RoleKey) -> Result<&Binding, BindingError>` and `roles_for(&DeviceKey)`; no owned API encodes bound-vs-unbound as a bare `Option`.
- `Binding`'s authored field set: stable `RoleKey`, durable `DeviceEndpoint`, retained `DriverId`, all four policies (`RecoveryPolicy`, `RetryOn`, `OnAbort`, `OnSessionLoss`), `RequestedConfiguration`, `LastKnownGoodConfiguration` — plus the authoritative `RoleState`. Routing is by driver, never by capability: two drivers can serve one `DeviceKey` and take different `Configuration`.
- The **two configuration sources** stay distinct. `RequestedConfiguration::new(C)` is authored intent, erased. `LastKnownGoodConfiguration::{NotEstablished, Known(Box<dyn Reflect>)}` — explicitly distinguishes no readback from a known value — is written only by a safe readback: a successful apply moves the role to `Ready` without copying requested intent into it, `CaptureOutcome::ReadFailed` preserves the prior `Known`, departure/recovery/in-flight attempts freeze it, and `NotReadable` permanently suppresses capture without manufacturing a value. `configuration_for(&RoleKey) -> Result<AvailableConfiguration<'_>, BindingError>` returns `LastKnownGood(&dyn Reflect)` when known, otherwise `Requested(&dyn Reflect)`. Renamed from phase 5's `CapturedConfiguration`.
- The role lifecycle is a **hybrid state/typestate model**: `RoleState::{Waiting, Ready, Applying(AttemptId), StoppedAfterRepeatedFailures, Retired}` is the stored authoritative enum, defaulting to `Waiting` (a newly authored role has observed no usable hardware), and `Bindings` selects constructor-less views `WaitingRole`, `ReadyRole`, `ApplyingRole` from it. Each transition lives on the only view allowed to perform it: `ReadyRole` mints a `CaptureRequest`, `WaitingRole` begins a requested apply or a last-good restore, `ApplyingRole` mints a `PollRequest`/aborts/finishes; `Retired` has no view. Requested applies and last-good restores use distinct request sources paired with in-service and restore-only permits, so restore-only authority cannot carry requested intent. `Drivers::{capture, start_apply, poll}` take those tokens instead of raw ids; `Drivers::start_apply` enforces dispatch-first / state-commit-on-success — callers must go through that boundary rather than setting `RoleState::Applying` themselves, so a missing driver or a configuration-type mismatch leaves the role waiting with no attempt.
- `PendingBindingTransitions` — bounded, sequenced synchronous mutations — is a private `VecDeque<BindingTransition>` in `Bindings`, capacity 4,096, resizable through checked `set_pending_transition_capacity(NonZeroUsize)` (lowering below the pending count fails and changes nothing). Every effective `register`/`replace`/`retire` reserves capacity before touching any map; exhaustion returns `BindingError::PendingTransitionCapacityReached` and mutates nothing. `AlreadyUnbound` queues nothing. Entries carry only sequence + `RoleKey`. The sequence itself is exhaustion-checked, since wraparound would void its ordering guarantee.
- Offline mode is authored inventory, separate from reporter activation and from live entities: `ConfiguredDevice { key, mode }`, `ConfiguredDeviceMode::{Managed, Offline}`, and `HardwareInventory` retaining `ConfiguredDeviceConnection::{NotObserved, Present, Absent, Unreachable}` from `NotObserved`. Offline mode leaves enumeration passive and prevents a device thread from opening — no `capture`, `start_apply`, or `poll` for an offline entry, though passive evidence may still mark it present — and cannot be enabled merely by adding an inventory entry, which creates no `Device`, issues no `DeviceId`, and enables no reporter.
- `ReporterRegistration::{required, optional}` both require `ReporterCoverage::{MatchingEvidenceOnly, EstablishesAbsence(AuthoritativeReporterCoverage)}`, stated in persisted identity terms only (`CoveredDeviceIdentitySpace`), storing no `ReporterId`; the multi-space constructor rejects empty and duplicate sets. Freshness of retained evidence, not the activation switch, decides whether a complete scan may establish `Absent`; any matching retained evidence wins as `Present`. `DeviceIdSource::Authored { value: AuthoredId }` ships with a validated persisted newtype and RON round-trip coverage.

### Phase 9 — Reconciliation: scan ingest, co-report merge, and duplicate detection  · status: done

#### As-built

- `reconcile` (crate-private, `reconcile.rs`) runs once per tick in `RiggingSystems::Reconcile`, after phase 7 has admitted whatever discovery is ready. It drains the changed-reporter ids and failures, borrows each contributor's retained whole set from the non-reflected registry, applies the freshness lease, then returns early on a settled frame — no completed reporter and no lease change means no allocation, no diff, and no revision bump.
- Ingest rejects an unregistered `SchemeName` at the boundary, records it into `Devices::unregistered_schemes()`, and drops the record — producing no device, no component, no event. `DeviceRecord`'s `transport: Option<DeviceKey>` was replaced with `parent: ReportedParent` (`Root` / `ChildOf(DeviceKey)`); ingest is roots-first regardless of listing order and presence folds conjunctively down the chain. A declared capability is attached as a component at ingest.
- Merge is one `HashMap::entry` grouping pass over the retained sets, never a pairwise join: records with an equal `DeviceKey` from different reporters become one device with multiple contributors, and duplicate detection flags a same-key collision within one scan in the same pass. Co-report merge accepts a report carrying match evidence instead of a mintable key, joining through the `os_id` pass — the same structure as a child device reported under a parent; a reporter whose evidence matches nothing is `Unverified`, never a guess, so such a record yields no device and no minted key. The join is restricted to `OsDeviceId::Reported(_)`: the other two variants compare equal to themselves and would fuse two units that each reported no handle.
- Phase 9 produces **no verdict at all** — `Displaced` is phase 11's, and `duplicate_keys` is carried on the frame output for phase 11 to convert into `Unverified(NotUniqueInScan)`.
- `Devices` resource and `DeviceStateLookup::{Retired, Retained(device)}` — the named-enum lookup idiom (alongside `AttemptLookup`, `DeviceResolution`, `DeviceEntityLookup`) — hold durable state keyed by the copyable `DeviceId`, with one `DeviceKey -> DeviceId` map. `Devices::replace_reconciled` and its per-device compare loop install a new generation; retirement drops the whole device state entry. `ReconciledDeviceState` stores `key`, `parent`, `presence`, `claim`, `contributors`, and normalized `declared`/`disputed` capability `TypeId` sets — facts only, never capability values, which stay borrowed through a per-system `CoReportView` (`Vec`, not `SmallVec`: smallvec is not a workspace dependency) compared with `PartialReflect::reflect_partial_eq`.
- Freshness lease semantics: staleness **withdraws evidence**, does not assert absence, and is not a topology change (documented at `devices.rs:151-154`). A reporter is stale when its last `Complete` scan is older than its own declared cadence plus `RiggingLimits::report_grace`; a reporter that never completed a scan and one that declared no cadence are never stale. Staleness is per reporter, and a device goes `Unreachable` only when every contributor is silent. `DeviceScan::Failed` retains the previous complete set and its revision; only freshness expiry later yields `Presence::Unreachable`.
- `RiggingLimits` and `RiggingRevision` were built here; `RiggingRevision` keeps per-submission semantics and reconcile's own tests assert on it. `RiggingRevision::advance` fires **only** on a pass in which a reporter completed a scan; a lease-driven presence flip advances nothing. `RiggingLimits { apply_overrun: 5s, report_grace: 30s }` is a reflected, BRP-tunable resource inserted only if absent; both values read through `Time<Real>`, and tests backdate phase 7's stored completion times instead of advancing a clock.

### Phase 10 — Binding entities, the resolved-device relationship, and the attempt registry  · status: done

### Phase 12 — Attempt lifecycle, retries, and escalation  · status: done

#### Work Order

**Goal:** the kernel starts, bounds, re-validates, retries, and escalates attempts.

**Spec:**

Attempt lifecycle inside `RiggingSystems::Apply`, always through phase 8's typed role views:

1. A `WaitingRole` on a managed device may begin only after authorization. **The stored `WaitingWork` picks the configuration first and the resulting view then demands the matching permit** — permission does not select the configuration. Phase 11 shipped `WaitingRole::{ForHardware, ForRestoration}` (`binding.rs:658-664`), dispatched from `waiting_work` (`binding.rs:398-405`): `ForHardware` resolves to `RequestingRole`, whose `start_requested_apply` rejects anything but an in-service permit (`binding.rs:691-694`), and `ForRestoration` resolves to `RestoringRole`, whose `start_last_known_good_restore` rejects anything but a restore-only permit (`binding.rs:738-741`). Implementing this as permit-driven selection produces code the API refuses. `LastKnownGoodConfiguration::NotEstablished` means there is nothing to restore, so the role stays waiting. The view mints the only `StartApplyRequest` accepted by `Drivers::start_apply`; erased driver dispatch runs first, and only a successful dispatch commits the binding to `Applying(AttemptId)`. A missing driver or configuration-contract error returns with the binding still `Waiting`, while a driver that started returns immediately. An offline inventory entry cannot mint this request under either authorization path.
2. Every tick, only an `ApplyingRole` can mint the `PollRequest` accepted by `Drivers::poll`. **Before** minting it, re-check `Attempt.expected_device_id` against the current `DeviceId` and the attempt's stamped `DeviceRevision` against that device's current one. A mismatch invalidates the attempt before any driver poll — it never lands on a different unit. If a device is switched to offline while an attempt is already running, abort it and never poll again.
3. `Attempt.deadline` bounds the attempt **end to end, not per step**, so a driver that must reset then render has both steps inside one attempt with one settle result and cannot report done between them. Past the deadline the state stays `Applying(AttemptId)` — being overdue is not an error and not a failure, so `poll` keeps being called. Past `deadline + RiggingLimits::apply_overrun` the kernel stops asking and finishes the attempt `Aborted`. That is the bounded-overrun rule: slack for a device that is genuinely converging, a ceiling for one that never will.

   The deadline query is **not** `Attempts::is_overdue(id, now) -> bool`. A bare `bool` over a handle lookup collapses three different situations — within deadline, overdue but inside the overrun budget, and no such attempt — into one bit, and the caller cannot tell "not overdue" from "nothing there". Return a named enum whose variants state which of the three held, and give the overrun case the reading the abort branch needs.

   **The clock source is `Time<Real>`.** Phase 9 reads it the same way and already handles the case this phase would otherwise trip over: on the first frame the clock has not advanced, so an elapsed-time query returns a value that is not yet meaningful. Phase 9's private `FrameClockReading` (`crates/hana_rigging/src/reconcile.rs:59-73`) is the shipped pattern for that — read it before writing a second one, and do not compute deadlines against a clock that has not started.
4. Abandonment follows the kernel rule table from phase 4: claim lost ⇒ never revert; service vetoed ⇒ never revert; revision changed ⇒ consult `OnAbort`.
5. Retry is gated by `RetryOn`. `AttemptOutcome::Aborted` is terminal and never auto-retries.
6. Repeated-failure escalation counts **consecutive attempts, not frames** — that is why it is kernel work and arrival evidence is not — and **self-clears on recovery**.

`Succeeded` and `Substituted` finish through `ApplyingRole`, remove the attempt, and transition the binding to `Ready`. They do **not** copy the requested or restore target into `LastKnownGoodConfiguration`. On the next reconcile, phase 11's `ReadyRole` capture path reads back what actually landed and writes `Known`; until that safe read succeeds, the previous last-known-good value remains unchanged. Failure, abortion, disconnection, and recovery likewise never overwrite it.

Reacquisition keys on the device's **presence readings**, not elapsed time and not a topology counter. An `Absent → Present` cycle shorter than the settle window must not be swallowed: the departure and return arrive in two consecutive completed scans, and comparing the presence variant across them fires the return even though the sets before departure and after return are identical. A content hash would report no change there and the panel would stay blank. This is a kernel test case, not a kernel state — a `Resumed` variant would be a driver field wearing a kernel type.

Retry pacing lives here, replacing both hand-rolled pacers the migration deletes. Kernel state is plain `Send` data, so "any role awaiting?" is an ordinary run condition — the reporters and drivers stay non-send, the *pacing* stops being.

Keyed retirement works with **no live entity**, and is ordered so explicit retirement beats simultaneous device loss.

Phase 9 shipped staleness as evidence *withdrawal*: a device goes `Unreachable` only when every contributing reporter has gone silent (`lease_work` at `crates/hana_rigging/src/reconcile.rs:382`), and that lease-driven presence flip deliberately does **not** call `RiggingRevision::advance` (`reconcile.rs:367`) — the revision moves only on a pass in which a reporter completed a scan. So the revision check passes, unchanged, while the device is unreachable and the attempt keeps polling a device nothing can see.

What exists now:
- `Attempt.rigging_revision` is stamped at authorization and re-checked before poll.
- A lease-driven `Present → Unreachable` flip changes `Presence` and advances nothing.
- `crates/hana_rigging/src/devices.rs` documents that as intended: staleness withdraws evidence, it does not assert absence, and it is not a topology change.

What changes:
This phase reads the device's presence directly and aborts an attempt whose device is no longer `Present`, independent of the revision. The rejected alternative was making a lease-driven flip advance `RiggingRevision`: that reverses a phase 9 decision documented in `devices.rs` and would make every stale-lease frame look like a topology change to every other revision consumer, including phase 13.

The read goes in the **existing pre-poll re-validation**, beside the identity and revision checks that already run there and already hold `attempt.expected_device_id`. It is one added condition, not a new system and not an event subscription:

```rust
match devices.state(attempt.expected_device_id) {
    DeviceStateLookup::Retired          => abort,
    DeviceStateLookup::Retained(device) => { /* abort unless device.presence is Present */ }
}
```

Four constraints on that read:

- **It reads `Devices`, never the device entity's mirrored `Presence`.** The mirror is phase 11's read-only projection and the device entity can be despawned while an attempt is still finishing — the same fact that makes `AttemptFinished` target the binding entity (phase 13, D1). A `Changed<Presence>` query would stop seeing the device at exactly the moment this check matters most.
- **The ordering is already correct.** Reconciliation runs in `RiggingSystems::Reconcile` and the apply systems in `RiggingSystems::Apply`, so this read sees the current frame's reconciliation.
- **Compare by variant, never by value** — `Presence::Unreachable { since }` grows every scan. Call `Presence::is_same_variant` (`presence.rs:37-52`), which phase 11 shipped; do not add a second one here. It is `pub(crate)`, which is fine at this call site — this phase's abort read lives inside the crate.
- **`DeviceStateLookup::Retired` aborts too**, covering a device that left the set entirely. Both `Retired` and any non-`Present` variant abort identically, so `Retired`'s known conflation of "departed" with "never issued" does not matter at this call site.

`Absent` and `Unreachable` are deliberately **not** distinguished: both abort. Phase 4's rule table already separates the abandonment consequences — claim lost never reverts, revision changed consults `OnAbort` — and neither of those is what fires here.

**Decided: invalidation is per device — a `DeviceRevision` that advances on real change replaces the global `RiggingRevision` check, and claim loss and identity downgrade become their own abort reasons.**

Actual problem:
`RiggingRevision` advances on every pass in which a reporter completed a scan (`crates/hana_rigging/src/reconcile.rs:367`), and the Spec invalidates any in-flight attempt whose stamped revision no longer matches. The two together mean **one reporter's routine scan abandons every in-flight attempt kernel-wide**, including attempts on devices that reporter never names. The default `RetryOn::NewRevision` then keys the retry on the same counter, so the role restarts and is abandoned again at scan rate. Phase 21's camera reporter scans every 2 s against applies that settle in seconds; phase 15's displays are worse. Both halves are this phase's own Spec, so this is a conflict inside the plan.

What exists now:
- `attempt_validity` (`crates/hana_rigging/src/apply.rs:224-274`) runs six checks. Five name a specific fact about the attempt's own device: the role exists, the endpoint still resolves to `expected_device_id`, presence is `Present`, `HardwareInventory::ensure_operational` passes, the deadline holds.
- The sixth — `rigging_revision != attempt.rigging_revision` — names nothing about the attempt's device. It reports only that some reporter submitted something.
- **Claim and identity verdict are never re-checked in flight.** `authorized_state` (`devices.rs:318-345`) reads both at authorization; no production path in `apply.rs` reads either again. The revision check is what stands in for them, and it does so by abandoning every attempt in the kernel.
- Phase 4's **Kernel abandonment rules** table already names both as distinct abandonment reasons — "claim lost ⇒ never revert; service vetoed ⇒ never revert" — and `AttemptInvalidation` has a variant for neither.
- Reacquisition after a same-set departure and return does **not** depend on this counter: `observe_stopped_role_endpoint` (`binding.rs:617-624`) compares presence readings frame to frame. The Spec's argument that a content hash would miss the case is true of a hash and does not apply to presence.

What changes:
Invalidation becomes entirely local to the device the attempt targets, so a reporter can no longer reach an attempt on a device it does not name.

- **`DeviceRevision`** — a per-device counter held in `Devices` beside the device's reconciled state, advanced in `Devices::replace_reconciled` when the incoming `ReconciledDeviceState` differs from the retained one. That loop (`devices.rs:145-173`) already holds both values for every device; a re-scan reporting identical state advances nothing, which is what makes routine scanning non-abandoning. Reading it needs a named lookup, not an `Option` — a retired device has no revision, and that is not "revision zero".
- **`Attempt` stamps `DeviceRevision`** instead of `RiggingRevision`, and `attempt_validity` compares against the current one. `AttemptInvalidation::RevisionAdvanced` keeps its name and its meaning narrows to "this device's reconciled state moved under the attempt in a way no other check names" — an endpoint set change, a dispute change. It remains the sole trigger for `OnAbort`, so phase 4's table stays literally true.
- **`RetryGate::AwaitingRevision` carries `DeviceRevision`.** `RetryOn::NewRevision` becomes "retry when this device changed," which is the wake-up signal the variant was always meant to express. The livelock is impossible by construction: the signal that abandons an attempt is no longer produced by scanning.
- **Two new direct checks in `attempt_validity`**, completing phase 4's table: `AttemptInvalidation::ClaimLost` when the device's `Claim` is no longer held for this role, and `AttemptInvalidation::IdentityNoLongerConfirmed` when its `IdentityVerdict` no longer identifies. Both are "never revert" per phase 4, so neither consults `OnAbort`.
- **`RiggingRevision` stays** as the kernel's "how many scans have landed" signal and keeps its per-submission semantics — reconcile's own tests assert on it — but no longer participates in the apply path. It has no other kernel consumer after this change.

The net is one fewer coupling and one more specific check: six checks of which one was vague become seven that each name a fact about the attempt's own device, and the kernel's only cross-device coupling disappears.

**Decided: three consecutive failed attempts move the binding to a named non-retrying failed state, cleared only by a successful attempt.**

Actual problem:
The phase says escalation counts consecutive attempts and clears on recovery, but it names no threshold, storage location, or state change. Later screen work assumes the existing limit of three failures has a kernel equivalent, so a delegate would have to invent both policy and behavior.

What exists now:
- `RetryOn` controls whether and when one failed attempt retries.
- No type stores a consecutive-failure count or describes an escalated role.

What changes:
The existing screen behavior becomes the v1 contract. Three consecutive failed attempts move that binding to a **named non-retrying failed state**; the counter lives per binding, counts attempts rather than frames, and resets **only** on a successful attempt — two failures followed by a third is three, not a fresh start. Leaving the state requires either an explicit application restart call or a successful attempt after reacquisition; the phase 12 Work Order must name both the state and that restart method before dispatch. The cost is one more role state every consumer switching on role state must handle. Counting attempts is what makes this kernel work: a driver reporting arrival evidence cannot know which of its calls belong to the same role's run of failures.

**Decided: a `RestoreOnly` device's first apply runs from `RequestedConfiguration` under a restore-only permit.**

Actual problem:
A device whose verdict is `RestoreOnly` has no reachable apply path in the shipped crate. `authorize_service` refuses that verdict (`devices.rs:298-308`), so the role never becomes `ForHardware`; `ForRestoration` requires `LastKnownGoodConfiguration::Known`, but last-known-good is written only by phase 11's safe capture after a role reaches `RoleState::Ready`, and `Ready` is written only by `ApplyingRole::finish` (`binding.rs:896`) — which needs an apply that already ran. The bootstrap is circular: no apply, so no capture; no capture, so `NotEstablished`; `NotEstablished`, so no restore. Phase 21's "the camera path uses `authorize_restore()`", phase 26 case 2, and phase 15's tier-2 macOS displays all depend on a bootstrap that does not exist.

What exists now:
- `LastKnownGoodConfiguration` starts `NotEstablished` and nothing seeds it.
- A `Synthesized`-keyed camera therefore sits at `WaitingWork::Nothing` forever, starting nothing.

What changes:
Write into this phase's Spec that `LastKnownGoodConfiguration::NotEstablished` is the one case where `RequestedConfiguration` is the restore target: a `RestoreOnly` device's first apply runs from requested intent under a restore-only permit, and every later apply restores the readback value phase 11's safe capture recorded. This needs no persistence layer, no registration argument, and no serialized configuration format — none of which v1 has, and all of which phase 8 deliberately kept out. Nothing changes at the application call site; a camera role is authored exactly as for a proven device.

The meaning of `RestoreOnly` narrows accordingly, and the Spec must say so: it is **not** "the kernel applies nothing until it has seen this device work once" but "the kernel only ever applies what the application asked for, never a configuration of its own choosing". That is the weaker reading and it is the one that makes serial-less hardware usable. The rejected alternative was seeding `Known` at registration from persisted state, which re-opens the storage question v1 excludes.

**Decided: capture-readback back-off lives here, under the same three-strikes rule as attempt escalation.**

Actual problem:
`record_capture` leaves `last_known_good` at `NotEstablished` when a readback returns `CaptureOutcome::ReadFailed`, so `roles_with_a_safe_capture_opportunity` re-qualifies that role on every subsequent frame (`reconcile.rs:1573-1578`). The consequence is not a spurious changed-resource flag: the kernel re-enters `resource_scope::<Bindings>` **and calls `Drivers::capture` again every frame** (`reconcile.rs:1513-1548`). A driver whose readback is permanently broken is dispatched at frame rate forever. This phase already owns retry pacing, but scopes it to attempt outcomes through `RetryOn`, which does not cover capture.

What exists now:
- No back-off, retry budget, or failure counter exists for capture readback anywhere in the plan.
- Phase 13's "no state-change event fires on a settled frame" gate currently carries this as an unowned open case it would have to invent a policy to close.

What changes:
Capture-readback back-off is added to this phase's Spec, counted per role and self-clearing on the first successful readback — the same rule as the repeated-failure escalation decided above, at the same threshold of three, applied to `Drivers::capture` instead of to attempts. After the third consecutive `ReadFailed`, `roles_with_a_safe_capture_opportunity` stops qualifying that role until a readback succeeds; `last_known_good` stays `NotEstablished` meanwhile, which is already what a failed readback means. Phase 13's settled-frame gate therefore becomes unconditional. The rejected alternative was excluding the persistently-failing-readback case from that gate in phase 13, which documents the per-frame driver dispatch instead of stopping it and splits one "count failures, stop, clear on recovery" rule across two phases.

#### Retrospective

**What deviated from the plan:**
- Attempt invalidation was re-specified mid-phase. The Work Order keyed staleness on the global `RiggingRevision`; the shipped kernel keys it on a per-device `DeviceRevision` that advances only when a device's own `ReconciledDeviceState` actually changes.
- `ClaimLost` and `IdentityNoLongerConfirmed` became their own `AttemptInvalidation` variants instead of being absorbed by `RevisionAdvanced`. Both are never-revert, so neither consults `OnAbort`, and phase 4's abandonment table stays literally true with `RevisionAdvanced` still its sole `OnAbort` trigger.

**Surprises:**
- The global counter starved the whole kernel, not just the noisy device. `RiggingRevision` advances on any pass in which any reporter completed a scan, so one reporter's routine rescan abandoned every in-flight attempt kernel-wide — and the default `RetryOn::NewRevision` keyed the retry on that same counter, restarting and re-abandoning the role at scan rate. The regression test is `a_scan_that_changes_one_device_leaves_another_devices_attempt_in_flight`.
- Claim and identity were read only at authorization and never again once an attempt was in flight. The global revision check had been standing in for both.
- `RiggingRevision` survives with its per-submission semantics and its reconcile tests, but now has no kernel consumer outside `reconcile.rs`.

**Implications for remaining phases:**
- Phase 13's settled-frame gate is unconditional: capture-readback back-off stops per-frame `Drivers::capture` dispatch after three consecutive `ReadFailed`.
- `rigging_revision` still appears in later Work Orders as the attempt's stamped field. Those references are stale for the apply path and are corrected as part of this review.

### Phase 13a — Events, the scripted test suite, and the per-binding deadline  · status: done

**Blocked by:** phase 12.

#### Work Order

**Goal:** consumers observe discovery, configured-device, live-device, and apply state changes as events, and every rule in phases 1–12 has a test that runs with no hardware.

**Spec:**

**Every kernel-owned state axis mirrored onto an entity emits on change.** The event list is derived from the mirrored component set, not accumulated case by case: `Presence`, `Claim`, `IdentityVerdict`, `RecoveryPolicy`, `RoleState`, and attempt completion. Each transition event carries the state moved *to*; the state moved *from* is on the entity until the event is delivered, so duplicating it in the payload would let the two disagree.

**Two kernel axes are deliberately outside that derivation.** Phase 11 left `WaitingWork` off the binding entity and `IdentityDecisionOwed` off the device entity, so neither is mirrored and neither emits — by construction, not by oversight. A consumer reading only entities or the Bevy Remote Protocol therefore cannot see that a role owes a restoration or that a human owes an identity decision; both are readable from the resources (`Bindings::waiting_work`, `ReconciledDeviceState::decision_owed`). State that exclusion in this phase so the derivation has no unexplained hole, and so surfacing either one later is a decision someone makes rather than a gap someone finds.

**Two entities, two targets (D1).** `Presence`, `Claim`, and `IdentityVerdict` are per-unit facts on the device entity, so `PresenceChanged`, `ClaimChanged`, `IdentityChanged`, and `DeviceArrived` target it. `RecoveryPolicy` and `RoleState` are per-role and sit on the binding entity, so `RecoveryPolicyChanged`, `RoleStateChanged`, `AttemptFinished`, and `ReapplyConfiguration` target **that** one. This is not a stylistic split: device departure can despawn the device entity while an attempt is still finishing, so an `AttemptFinished` aimed at the device entity would have nowhere to land. `RecoveryPolicyChanged` exists because the once-per-change rule above is derived from the mirrored set, and `RecoveryPolicy` is in it — without the event the derivation has a hole.

Live tools traverse phase 10's Bevy relationship: `ResolvedToDevice` takes a binding entity to its
current live device, and `ResolvedBindings` takes a live device entity to every currently resolved
role using it. Neither is consulted for authored ownership or offline inventory; those queries read
`Bindings` and `HardwareInventory`.

**An event is an `EntityEvent` only when a device entity always exists to target it.** Bevy 0.19 requires an `EntityEvent` to name its target through an `#[event_target]` field, and there is no valid `Entity` to put there for a role whose device has never appeared or has already been despawned. The split:

**`AttemptFinished` and `RetiredRoleAttemptEnded` already ship — do not redefine either.** Phase 12 defined and registered both in `events.rs` and triggers them from `RiggingSystems::Apply` through `announce_attempt_ending` (`apply.rs:306`). `AttemptFinished` targets the **binding** entity (D1: device departure can despawn the device while an attempt is still finishing) and carries `attempt: AttemptId`, `outcome: AttemptOutcome`, and `role: RoleKey` — the last absent from every earlier draft of this phase. This phase's once-per-change rule suite covers them as existing events, exactly as it covers phase 11's `CapabilitiesDisputed`.

Targeted at the **device** entity — this is what lets a consumer say "*my* Stream Deck came back" instead of writing a global match arm over device kinds: `DeviceArrived`, `PresenceChanged { device, presence }`, `ClaimChanged { device, claim }`, and `IdentityChanged { device, verdict }`. `CapabilitiesDisputed { device, capabilities }` is targeted at the device entity too but is **already defined, registered, and emitted by phase 11**; this phase's once-per-change rule suite covers it as an existing event and does not redefine it. Targeted at the **binding** entity: `RoleStateChanged { binding, state }`, `RecoveryPolicyChanged { binding, recovery }`, and `ReapplyConfiguration` — the request to re-apply, replacing clerestory's `RestoreWindow`. `IdentityChanged` is what phases 27 and 19 mean when they say a `Displaced` verdict "emits the event and logs".

Global `Event`, because the device entity is gone or was never there: `DeviceDeparted { key, departure }` — the kernel already tells the two departures apart and only one of them despawns, so the event carries the kind rather than discarding it. `ReconciledDeviceChanges.departed` holds `DeviceDeparture::{KeyLeftTheSet, RetainedButNotPresent}` (`devices.rs:191`); `KeyLeftTheSet` despawns the device entity, `RetainedButNotPresent` leaves it standing. It stays a global `Event` for both, because a consumer of the first has no entity left to read, and it carries the durable key for the same reason; `RetireRole { role }`, replacing `CancelWindowRecovery { window }`; and `RoleAwaiting { role }` / `RoleAvailable { role }`, which mirror clerestory's `WindowRecoveryPending`/`Available` and exist precisely for the interval when no device is bound.

Discovery and authored inventory also have global events because neither requires a live device entity. `DiscoveryProgressChanged { batch, reporter, progress }` and `HardwareDiscoveryProgress { batch, completed, total, running, queued }` begin only after phase 7's `DiscoveryLimits::progress_after`; `DiscoveryFinished { batch, reporter, outcome }` records completion/failure; `StartupDiscoveryChanged { state }` exposes the required-before-ready gate; and `ConfiguredDeviceConnectionChanged { key, connection }` lets UI match an authored hardware representation even when no live entity exists. Phase 8's `ConfiguredDeviceConnection` explicitly distinguishes `NotObserved`, `Present`, `Absent`, and `Unreachable`, and phase 11 retains the current value. Once a live device is identified, the existing device-targeted events carry its detailed presence/claim/verdict transitions. All event payloads use phase 7/8's retained state as their source; events never reconstruct task or deleted inventory state.

Every event derives `Reflect` and is registered, so BRP can watch the whole lifecycle without a consumer.

**The test suite is the deliverable of this phase.** Build a `ScriptedReporter` test harness that replays a list of hand-built scans, so every kernel rule is testable with no hardware and no mocks beyond the scan list:

```rust
#[test]
fn contended_device_does_not_reacquire() {
    let mut app = App::new();
    app.add_plugins(RiggingPlugin)
       .add_device_reporter(ScriptedReporter::new([
           scan![("hid-panel","usb-serial","CL15") => Present, Free],
           scan![("hid-panel","usb-serial","CL15") => Present, Contended(Unidentified)],
       ]), ReporterRegistration::optional(
           DiscoveryCadence::OnDemand,
           Enabled,
           // Not `MatchingEvidenceOnly`: this phase's gate requires departure
           // delivery, `DeviceDeparted`, and an `Absent → Present` reacquisition
           // cycle, and only an absence-establishing coverage can produce them.
           ReporterCoverage::EstablishesAbsence(AuthoritativeReporterCoverage::one(..)),
       ));
    advance_reporter(&mut app); // request + one update to finish + one to accept: arrives
    advance_reporter(&mut app); // request + one update to finish + one to accept: contended
    let binding = app.world().resource::<Bindings>().binding(&role).unwrap();
    assert_eq!(binding.state, RoleState::Waiting);
    assert_eq!(app.world().resource::<Attempts>().len(), 0);   // never seized
}
```

A design that cannot be tested this way has put I/O in the kernel. The load-bearing rule the test above encodes: **`RecoveryPolicy::ReapplyOnReturn` must not fire while `Claim::Contended`.**

Phases 15, 17, 19, 24, and 25 all reuse this harness, so adding a `DeviceRecord` field later breaks every one of them through this one builder rather than through each test.

**Constraints from prior phases:** Phase 12 built the attempt lifecycle this reports on, and shipped **`ReconciledDeviceChanges` as a `Resource`** (`plugin.rs:74`) holding `departed`, `orphaned_entities`, `disputes_changed`, and `connections` — that is the source this phase's departure and connection events read, not a fresh diff. Do not implement a second comparison. It is `pub(crate)`, so `tests/scripted.rs` — an integration target outside the crate — cannot call it, and neither can the `hana_rigging_scripted` crate decided below; those must assert once-per-change through the mirrored components instead of by calling the comparison directly. Three further facts phase 11 shipped that this phase's no-per-frame-change gate depends on. ### Phase 13b — The identity-decision register  · status: todo

#### Work Order

Phase 27's stated remedy does not work: it says a mutating Stream Deck serial yields `Displaced` and "a human replugs", but a replug whose departure and arrival fall in the same reconcile pass re-arms the same join, and the deferred register's "`Displaced` adjudication" is about *adopting* a candidate key, not about clearing a debt already owed. As written, a `Displaced` device is unusable for the rest of the process's life.

What exists now:
- `decision_owed` is written only by `verdict_for` and cleared only by retirement.
- There is no acceptance method on `Devices` and no phase claims one.
- Phase 27 tells the reader a replug resolves it. It does not.

What changes:

**First, the framing in phase 27 was wrong and is corrected there.** A value that rotates on every replug is not an identifier, and a reporter must never hand one over as `DeviceIdSource::Reported`. Deciding what is stable is the **reporter's** responsibility: it synthesizes a key from stable evidence and labels the source accordingly, the kernel takes that claim at face value and derives authority from it (`Reported` and matching ⇒ `Proven`; `Synthesized` ⇒ `RestoreOnly`), and the application sees nothing. A rotating-serial Stream Deck therefore raises **no** identity question at all — it is `Synthesized`, restore-only, and usable through the first-apply-from-requested rule decided above.

What remains is the genuine case: a reporter correctly claims a stable device-reported identity and it later fails to match while a same-kind device occupies the same attachment. A firmware revision that changes serial length (phase 27 fact 2) and an actually-swapped unit (phase 21/26's replacement camera) are both this. The kernel is right to stop and ask; it has no way to be answered.

**The register.** This phase adds `IdentityDecisions`, a public kernel resource holding one entry per unanswered question in arrival order, each naming the role, the saved key, the candidate key, and when it arose. The application drains it however it chooses — a table of rows with per-row buttons, one modal at a time, or not this frame. It is a list, not a flag: several devices can go ambiguous at once, and more can arrive while the operator is answering an earlier one.

**Two answers, both recorded against the candidate key**, so neither re-arms on the next pass:
- **adopt** — the saved key becomes the candidate key. Clearing a flag alone is not enough: the kernel re-derives the mismatch every reconcile pass, so only rewriting the saved key stops the question. This is the "adopting the candidate rewrites the saved key" work phase 27 currently defers; it stops being deferred.
- **reject** — the candidate is refused for that role and the entry is removed. A later *third* unit raises a new question, which is correct.

**Deferral is an explicit state on the entry**, not the absence of an answer. Without it a one-at-a-time dialog cannot tell "the operator has not seen this" from "the operator said later", and it re-prompts every frame. The kernel stores the bit; what deferred means for the UI is the application's.

**Entries expire on their own** when the device departs or the role is retired, so the register never accumulates questions about hardware that is gone.

**Persistence stays application-side** — the kernel does no I/O. An adoption surfaces as an outcome the application writes into the same inventory that authored the original key; a deferral it wants to survive a relaunch is likewise its own to store.

**This phase ships a `fairy_dust` example demonstrating the whole workflow.** `crates/hana_rigging/examples/identity_decision.rs`, authored per `docs/fairy_dust/canonical-example.md`, uses phase 13a's `hana_rigging_scripted` crate to make a device arrive under a saved key, depart, and return as a different candidate at the same attachment — then presents the pending entry in a diegetic dialog with adopt and reject buttons the operator clicks, and shows the role binding afterwards. Two things to settle at dispatch: `canonical-example.md` records per-chip mouse-click activation as unimplemented future work, so the delegate must confirm a clickable diegetic affordance exists or the example needs one; and the example needs `fairy_dust` added as a dev-dependency of `hana_rigging` — `hana_rigging_scripted` already is one (`crates/hana_rigging/Cargo.toml:24`).

**Named types.** The register is `IdentityDecisions`, a public reflected resource. One entry is an `IdentityQuestion` carrying `role: RoleKey`, `saved: DeviceKey`, `candidate: DeviceKey`, the frame reading it arose on, and an `IdentityQuestionState` — `Unseen` (the default) or `Deferred`, so a one-at-a-time dialog can tell "the operator has not seen this" from "the operator said later" and stops re-prompting. An answered entry is removed, so `IdentityQuestionState` has no answered variant. The answer is `IdentityAnswer::{Adopt, Reject}`. Reading one role's question answers `IdentityQuestionLookup::{NoQuestion, Pending(&IdentityQuestion)}` — the crate's `*Lookup` idiom, never a bare `Option`. Draining in arrival order is a slice read plus `IdentityDecisions::answer(&RoleKey, IdentityAnswer)`; nothing hands out a mutable entry.

**Adoption rewrites the binding endpoint, not just the saved key.** `Binding.endpoint.device` is a durable `DeviceKey` indexed in three `Bindings` maps and `HardwareInventory.configured` is keyed the same way, so rewriting only the saved key leaves every affected role resolving `NotResolved` for good. `Adopt` routes through `Bindings::replace` (`binding.rs:322`) and updates the inventory entry in the same operation. `Bindings::replace` returns `BindingError::EndpointAlreadyOwned` when another role already holds the candidate endpoint, which adoption can reach: surface it as a named outcome — `AdoptionOutcome::{Adopted, CandidateEndpointOwned { by: RoleKey }}` — leave the question standing, and let the application resolve the conflict. Adoption never silently steals an endpoint from another role.

**Files:**

**The co-report join is the load-bearing claim of this phase, and it joins on runtime evidence, not on the key.** `xcap 0.9.6` fills `cg_direct_display_id` straight from `CGGetActiveDisplayList` and returns it unchanged; clerestory's `native_monitor_id` bottoms out in the same Core Graphics namespace. The two enumerations therefore agree on the **runtime display id** — but that id is no longer the `DeviceKey`, so the merge can no longer be plain key equality. The screens reporter can read a display id and nothing durable; only clerestory reaches the panel's EDID/ColorSync evidence. So the join is: clerestory owns the durable key and publishes its runtime display id as in-session match evidence; the screens reporter reports the same runtime id; the kernel binds the second report onto the device the first one already keyed. **Verify the id agreement against the locked versions before relying on it** — it is a macOS-verified claim and an assumption everywhere else. Off macOS, the two enumerations stay separate devices and the panel keeps a geometry association *in the panel layer*, where always-return-something is correct and no identity claim is made.

Phase 9's merge therefore accepts a report carrying **match evidence instead of a mintable key** — a reporter that can identify a device only relative to another reporter's report. The mechanism is the same shape as a child device reported under a parent: the record names what it matches on rather than what it is. Build it in phase 9, not here. A reporter whose evidence matches nothing is `Unverified`, never a guess.

**One thing genuinely gets worse and needs a test.** `ScreenSession` entries are never removed today precisely so a material's texture binding stays valid. Under the kernel those are two lifetimes: the reporter must keep its own never-removed handle map keyed by `DeviceKey`, and the kernel's `Retired` phase must **not** be read as "drop the handle". Write the test: a retired role must not invalidate a reporter handle that a material still binds.

`ScreenSessions` stays driver-private and non-send; the reporter never owns or opens a capture session. `start_apply` must **start** the open and return — every real open here is backgrounded with an `mpsc` outcome because opens take seconds. Discovery itself is a separate kernel-scheduled background job and cannot block the app thread.

Fixed for free, and each needs a test: two displays with origins closer than 200 pt no longer alias; `screen_sources()` enumeration failure returns `DeviceScan::Failed`, retaining the previous whole set and revision until phase 9's freshness lease later makes its devices `Presence::Unreachable`, rather than silently blanking every panel's metadata rows; `retry_disconnected_screens` stops needing to be exclusive, because kernel state is `Send` data and "any role awaiting?" is an ordinary run condition.

### Phase 27 — Stream Deck device thread, enumeration, and claim  · status: todo

Constraints the HID survey fixes:

- **One model only: the Stream Deck +**, which is the unit on hand. `Original 0x0060` and the Mini family are separate protocols, one undocumented by Elgato; scope to the + and let the abstraction prove itself on the *second* model rather than the first. Shape the crate around **protocol families** (~6 of them), not the 17 product ids — a Corsair keyboard runs the Stream Deck gen2 protocol, so protocol ≠ vendor.

The enumeration step settles this by measurement: whatever `elgato-streamdeck` reports for the connected unit is the slot count, and a hardcoded 8 or 4 that disagrees with the hardware is a defect either way. Record what the device actually reports in this phase's notes.
- **No tokio.** `elgato-streamdeck`'s `async` feature pulls tokio and the workspace has none. Register enumeration as an optional, initially disabled `DiscoveryCadence::Periodic { interval: Duration::from_secs(10) }` reporter; each due run returns a kernel-managed `DiscoveryWork::Background` closure using the blocking enumerate API on `IoTaskPool`. Phase 7 prevents duplicate jobs, leaves one I/O thread outside discovery when the pool permits, and coalesces a missed interval. New dependencies: `elgato-streamdeck` (brings `hidapi` and `image`) plus `crossbeam-channel`.
- **The owned operational device thread is not optional, but it is not the discovery scheduler.** `HidDevice` is `!Sync`, no OS event stream exists because the usage page is vendor-defined, and Elgato's recommended input poll is 50 ms. Once the managed driver is authorized, one integration-owned thread owns the claimed handle, channels carry commands/input in and reports out, a `PreUpdate` system drains, and `AppExit` releases. Offline inventory and passive discovery never start this thread.
- **Presence is polled, never notified.** There is no hot-plug anywhere in the hidapi stack; re-enumerate on a timer and treat a read-loop error as the disconnect signal.

Device facts this integration crate must handle:

1. **Sleep/resume is a distinct failure mode from unplug** and fires constantly on laptops. On host suspend the HID handle breaks and must be closed and reopened with a full re-render. This is an **integration-crate concern with no new kernel state**: a crate that knows its handle is dead reports `Absent`, then `Present` on reopen, and the normal reacquire path runs. The full re-render is free, because `RecoveryPolicy::ReapplyOnReturn` re-applies the last intentional configuration — which for a panel *is* the key images.
2. **The identity token can change under us — and deciding what is stable is this crate's job, not the kernel's.** Stream Deck serials have been observed mutating across replug, and serial length changed 12→14 across a firmware revision. These are two different situations and this crate must not conflate them. A value that rotates on every replug **is not an identifier** and must never be handed over as `DeviceIdSource::Reported`: this reporter synthesizes the key from stable evidence (attachment plus vendor/product/descriptor) and labels it `Synthesized`, which yields `RestoreOnly` and raises no identity question at all. Such a device is still fully usable, because phase 12 decided a `RestoreOnly` device's first apply runs from `RequestedConfiguration`. A firmware revision that changes a genuinely stable serial is the other case: the saved key legitimately stops matching while the same kind of device occupies the same attachment, and that is the `Displaced` verdict (phase 11). Replugging does **not** resolve it — a replug whose departure and arrival land in the same reconcile pass re-arms the identical join. Phase 13b ships the resolution: `IdentityDecisions` holds the outstanding question and the application adopts or rejects the candidate, where adopting rewrites the saved key. That adoption is **no longer deferred**; the deferred-register entry for it is discharged by phase 13.
3. **Post-claim reset is a driver obligation the kernel already compels.** On open, a zeroed reset report must be written to abort a half-finished image transfer left by a *previous owner* — presence does not imply pristine, and the previous owner may have been another process or a crashed run of hana. `start_apply` is specified as absolute, not differential, so this is how one driver discharges an obligation every driver has. The end-to-end deadline means reset-then-render sits inside one attempt with one settle result.
4. **Claiming is a contest with no good outcome.** hidapi seizes by default on macOS, and a seizing open *succeeds* over the already-running Elgato app while silently disabling its input queues. Contention is the **normal operating state, not an error**, and "we opened it" does not mean "we should have". Report `Claim::Contended` where it can be detected; where it cannot, that is a known producer weakness, not a reason to guess.
5. **Every transport failure arrives as one opaque string** — contention, unplug, and permission denial all surface as `HidError::HidApiError { message }` wrapping a hex `IOReturn`. Classify into `DeviceAccessError` and keep the raw string as driver detail. This is the second device kind to land in the same hole that produced `VIDEO_UNAVAILABLE_LIKELY_CAUSE`.
6. **A blocked device is indistinguishable from an absent one.** On Apple-silicon laptops the "Allow accessory to connect" prompt makes a denied device simply not enumerate, so `Claim::Blocked` is only inferable from *history* — we hold a saved key, the platform has a permission gate, and nothing matching enumerated. That inference needs the durable `DeviceKey`.

Resolved and worth not re-litigating: **Input Monitoring TCC does not apply.** Apple's kernel gates only Keyboard, Mouse, and TouchPad usages; the Stream Deck is a Consumer-page device, so unsigned `cargo run` reaches it with no entitlement and no prompt.

## Post-phase review decisions

Findings from the phase dual reviews that changed the plan rather than the code under review. Each entry records the decision, not the deliberation.

- **A — `verify.sh` strictness is global.** The shared delegate verifier hard-errors when nightly `rustfmt` or `cargo nextest` is missing, for every repository that uses it, with no per-repo opt-in. Invariant 13 is enforced machine-wide. The edit lives in `~/.claude/scripts/delegate/verify.sh` and is outside every phase commit.
- **B — G10's registration half is enforced in phase 9, not phase 1.** Phase 1 has no boundary where keys enter, so `RegisteredSchemes::validate` ships as a checked method with unit coverage and nothing calls it. Phase 9's ingest path is the first place an unregistered name can actually fail, and its acceptance gate now carries that requirement. Phase 1's acceptance line was corrected to state what it verifies rather than asserting a startup check that does not exist.
- **C — the validated newtypes are opaque to reflection.** `SchemeName`, `ReportedId`, and `Digest` carry `#[reflect(opaque)]`, so reflection treats each as one atomic value routed through the registered `Serialize`/`Deserialize` rather than exposing its private field. Without it, any reflection writer — remote inspection, scene load — sets the inner string directly and bypasses the checked constructor, which is the same hole G10's hand-written `Deserialize` closes for persisted text. `Digest` gains nothing but is included so the three identity wrappers behave alike. Field-level reflection access to the inner values is given up; nothing uses it.
- **D — `DeviceId` keeps `#[reflect(Component)]`; exclusion is enforced at the save path.** Entity saving runs through reflection rather than serde, so the absence of serde on `DeviceId` does not by itself keep it out of saved output — the save builder must deny it. That requirement already sits in phase 11's acceptance gate. Dropping the component reflection registration would make the exclusion structural but would also hide the handle from live inspection, which is the primary view for diagnosing why one physical device drew two handles.

## Deferred register

Nothing here ships in v1 and none of it is a phase. Each item names the condition that unblocks it. Phases 1–29 must not pre-build any of it: shipping a type with no consumer is correct only when adding it later would force an audit of existing call sites, and no item here meets that bar — `ServiceVeto` is one axis inside `Devices::authorize_service()`, a declared safe state is one axis on one enum, `Cohesion` attaches to a group that does not exist yet.

- **`Cohesion`** — `enum Cohesion { None, SameDevice, SameHost }`, checked by the kernel and never explained to it, covering the one-interface-one-machine constraint for a speaker group and a laser array on one DAC. Deferred because no v1 device has a cross-device grouping constraint and the only reachable value is `None`. **Trigger:** the first multi-device group. Purely additive — it attaches to a group, not to any existing type.
- **Reassignment** — re-binding N entities to a swapped unit. Deferred because no v1 kind does it; `DeviceEndpoint` keeps it expressible. **Trigger:** the audio work, or a Stream Deck replaced mid-show.
- **`Unreachable` decay timing** — when an `Unreachable` device becomes `Absent`. Deferred because there are no remote nodes in v1, so the kernel treats `Unreachable` as not authorized in service and **never auto-decays**. **Trigger:** the first Art-Net or networked node.
- **`Displaced` adjudication** — **no longer deferred.** Phase 13b ships `IdentityDecisions`: the kernel holds one entry per unanswered question in arrival order, the application drains it however it likes, and adopting a candidate rewrites the saved key while rejecting refuses that candidate — recorded per candidate key so the same question is not asked twice. Entries carry an explicit deferred state and expire on device departure or role retirement. What remains deferred is only whether an unanswered question **survives a restart**: the kernel does no I/O, so persisting the register is the application's decision. **Trigger:** an application that wants its pending identity questions to outlive a relaunch.
- **Attachment path as a stored third evidence axis.** The *evidence* question is closed — AVFoundation's `uniqueID` is a USB location id, so a port-derived value is attachment evidence carrying a `Synthesized` key, and phase 3 keeps it on the record as `AttachmentPath`. What stays deferred is giving it **its own stored axis** at rest. It must never be merged into `DeviceKey`. **Trigger:** a case where port position must be queried independently of identity.
- **The associated-type `Identified` trait.** Write it only when two *implemented* load paths share a batch-resolve-validate-publish body **with compatible failure policy** — all four conditions: both hold deserialized durable references aside unpublished; both resolve a whole batch against current registries; both validate cross-references across the batch; both publish atomically with compatible failure policy. Condition 4 fails today on purpose: a missing device is normal operation, a missing tool definition aborts the load. Then extract only the interface that body calls.
- **`DeviceKey` document persistence.** Rigging produces durable keys in v1 and serde is all it commits to; the document format waits on [[versioned save format]]. Rigging must not block on another in-progress issue.
- **`ServiceVeto`, the safety veto** — the type itself, not just its producer. Not built in v1: no interlock device exists, so the shape would be unvalidated and unexercised. **Trigger:** the first laser or interlocked fixture. Adding it is a fourth axis inside `Devices::authorize_service()`, the sole in-service decision point, plus one enum. Breaking for crates.io consumers, which the exhaustive-enum policy accepts.
- **A declared safe state** — again the type itself. Not built in v1: no v1 device has a declared safe state, and the erased `Box<dyn Reflect>` field it needed broke the `Reflect` derive, `Clone`, and the unrepresentable-illegal-state property. **Trigger:** the first light rig or projector with a required return state. Adding it arrives as a separate declared-state axis beside `RecoveryPolicy`, over the same erased-value mechanism the capability components use, never as a payload on the policy enum. Departure application stays driver-executed; the kernel never drives a device to a safe state itself.
