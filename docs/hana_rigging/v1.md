- A type or method says **what situation it exists for** and what goes wrong without it.
- Every enum variant says **what the system or the user would observe**, with the concrete device that motivates it. A variant comment that only rephrases the variant name is a defect.

### Phase 1 — Crate skeleton and durable identity  · status: done (967c5159)

#### Work Order

**Goal:** `crates/hana_rigging` exists as a workspace member and compiles with the durable-identity type set, its validated newtypes, and a scheme registry whose checked `validate` rejects an unknown name and accepts a repeated registration. Enforcing that check at an ingest boundary belongs to Phase 9, which is the first phase where keys enter.

**Spec:**

Create `crates/hana_rigging` in Repo A. `members` is a glob, so no `members` edit is needed — add the crate to `[workspace.dependencies]` as `hana_rigging = { version = "0.1", path = "crates/hana_rigging" }`, versioned from the start so phase 28 does not find an unversioned path dependency at packaging time. Dependencies: `bevy` (workspace), `serde`, `thiserror` (workspace) — the checked constructors below return errors, and the workspace forbids `panic`/`unwrap`/`expect`. Nothing else. The crate must not depend on `hana_clerestory`, `bevy_winit`, or any device crate — a kind crate depends on `hana_rigging`, never the reverse.

Two identifiers, and confusing them is the bug this crate exists to prevent:

```rust
/// Runtime handle. Opaque, process-local, `Copy`, cheap to compare. Never persisted.
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug, Reflect)]
pub struct DeviceId(u64);

/// Durable designation. Stable, human-readable, migratable, no Rust type paths.
///
/// The nested `id` is the whole point: the variant, not a string, says whether
/// the identifying value is proof or a hint, so a caller cannot lose that
/// distinction by copying a field.
#[derive(Clone, PartialEq, Eq, Hash, Debug, Serialize, Deserialize, Reflect)]
pub struct DeviceKey {
    /// Sort of unit: display, audio interface, DMX universe, HID panel.
    pub kind: DeviceKind,
    /// Where the identifying value came from, and therefore what it licenses.
    pub id:   DeviceIdSource,
}

/// How this unit came to be identified. **This is the trust level.**
#[derive(Clone, PartialEq, Eq, Hash, Debug, Serialize, Deserialize, Reflect)]
pub enum DeviceIdSource {
    /// The unit reported this value itself — a USB serial the hardware exposes,
    /// a monitor serial in its EDID. Proof of which physical unit this is, and
    /// the only source that can ever authorize in-service use.
    Reported { scheme: SchemeName, value: ReportedId },
    /// Derived by hana from descriptors, because the unit exposes nothing unique
    /// to itself — the port-derived camera id, the serial-less display UUID.
    /// A hint: it may restore a saved configuration, it never drives output.
    Synthesized { digest: Digest },
}
```

`DeviceId` wraps a `u64` issued by a monotonic counter on the `Devices` resource (phase 9), incremented once per newly-seen `DeviceKey` and never reused within a process — a handle that outlives its device stays dangling rather than silently naming a different one. It exposes no constructor outside the crate and no accessor for the integer; `Debug` prints it, nothing else reads it.

`DeviceId` gets `Reflect` and **no serde**, and its field is private. It is never persisted, and it appears in exactly **one** place on an entity: its own single-field component, so the handle is visible to BRP and reachable from the entity without a side-table lookup. It appears in no other component and inside no other type — `IdentityVerdict` carries no handle. The verdict answers *which unit is this* and nothing else; a caller holding a verdict already had the entity or the key it looked the device up by.

That one-component rule is what enforces never-persist. Moonshine serializes reflected components field-by-field without needing `Serialize`, so a `Reflect`-without-serde marker would not prevent persistence; what prevents it is the handle occupying a single named component excluded from the persisted set, rather than being scattered through types that each have to stay clean. Since that is a configuration exclusion rather than a structural impossibility, **the persistence test is mandatory**: save a device entity, assert the serialized output contains no `DeviceId`.

Three validated newtypes rather than bare strings, each with a **private field and a checked constructor**:

- `SchemeName` — names an identity space. Registered at app-build time so a typo fails at phase 9's ingest boundary instead of silently minting a second device. Two reporters naming one scheme are asserting they mean the same identity space; that is the migration hinge and the co-report join (phase 9).
- `ReportedId` — the value the unit reported. Opaque to the kernel, meaningful only inside its scheme.
- `Digest(u64)` — the synthesized value. A `u64`, not a `String`: it is an FNV-1a hash, which is 64 bits, and a fixed-width integer makes a malformed digest unrepresentable while dropping two heap allocations.

**Scheme validation splits into two boundaries, because one of them is not reachable from serde** (gate G10). A derived `Deserialize` on `DeviceKey` constructs a `SchemeName` directly and bypasses any checked constructor, and an app-build-time registry is not visible to a deserializer at all:

- **Syntax** lives in the newtype, enforced by a hand-written `Deserialize` that runs the same check as the constructor. A malformed name fails at parse time, wherever it is parsed.
- **Registration** lives in a `RegisteredSchemes` resource populated at app-build time. Every deserialized key is validated against that resource **before** its state is published. That validation runs at phase 9's ingest boundary, the first place a key enters kernel state — phase 1 has no such boundary, so it ships `RegisteredSchemes::validate` as a checked method with unit coverage and nothing calls it yet (post-phase decision B).

Registering the same name twice from two reporters is legal — it is the co-report assertion, so the gate checks registration and syntax, never uniqueness. ### Phase 2 — Identity evidence and the verdict enum  · status: done (59519f9e)

#### Work Order

**Goal:** the kernel can say what the platform reported about a unit and what identity verdict that evidence supports.

**Spec:**


Every identifier the platform can supply — reported serial, OS unique id, attachment path, vendor/product/model, synthesized digest — is retained on the device record even though only the strongest becomes the key. Absence is a named variant, never `Option`:

```rust

    Provided(ReportedId),
    /// Permanent for this hardware — not a bug to fix.
    NotExposedByUnit,
    /// The platform has no API to ask. A different unit on a different OS may report one.
    PlatformCannotReport,
}
```

The identity verdict is computed at reconciliation rather than carried as raw evidence, so it can never contradict the key. It derives **no `PartialEq`**: comparing two verdicts is never the right question, and its absence makes the wrong call fail to compile at the obvious spelling. That is an API deterrent, not a guarantee — Bevy's `Reflect` derive supplies structural `enum_partial_eq`, so a caller reaching through `Reflect` can still compare two `Unverified` values and get `true`. The rule that two unidentified devices never match each other is enforced where it matters, in phase 9's reconciliation, which pairs saved keys against live units and never treats an `Unverified` verdict as a match candidate.

```rust
pub enum IdentityVerdict {
    /// A `Reported` key matched a live unit uniquely. The only verdict that can
    /// mint an in-service authorization.
    Proven,
    /// A `Synthesized` key matched uniquely. Enough to put a saved configuration
    /// back — a window returning to its monitor — and never enough to drive
    /// output. This is the everyday verdict for webcams and serial-less panels.
    RestoreOnly,
    /// A human assigned this address. Authoritative by construction; the unit
    /// reports nothing and the patch *is* the identity.
    Authored,
    /// A saved key matched nothing, but a unit of the right kind sits in the same
    /// slot on the same transport. Neither absent nor confirmed. Needs a human.
    Displaced { saved: DeviceKey },
    /// A human authored this binding and the unit itself reports something else.
    /// The saved key matched; the unit sitting in it is the wrong one. Never
    /// authorized for in-service use — driving a misidentified fixture is how pan data reaches a dimmer.
    WrongUnit { authored: DeviceKey },
    /// Not identified: absent, not unique among live units, or the platform
    /// could not be asked. Carries which of those it was, because they lead to
    /// different policy. Prohibits automatic action.
    Unverified(UnverifiedReason),
}

impl IdentityVerdict {
    /// Identity only — *do we know which unit this is*. **Not** the policy predicate:
    /// in-service authorization also requires presence and claim, folded in `Devices::authorize_service`.
    pub fn identified(&self) -> bool {
        matches!(self, Self::Proven | Self::RestoreOnly | Self::Authored)
    }
}
```

`UnverifiedReason` must include `NotUniqueInScan` (the duplicate-key exclusion of phase 9), plus absence and platform-cannot-report cases. `IdentityVerdict` is `#[non_exhaustive]` — applications match on it.

### Phase 3 — Presence, claim, capabilities, device records, scans, and endpoints  · status: done (00bada98)

#### Work Order

**Goal:** the kernel can hold what a reporter reports — a whole-set scan of a device forest — and can express an N-bindings-to-1-device endpoint.

**Spec:**

```rust
pub enum Presence {
    /// Reporter asserts the unit is there and usable.
    Present,
    /// Reporter asserts the unit is gone.
    Absent,
    /// Reporter cannot tell — remote node silent, transport down.
    /// Distinct from `Absent`: collapsing them either resurrects retired
    /// outputs or destroys live ones.
    Unreachable { since: Duration },
}

/// How a reporter names the unit it is reporting. Two cases rather than an
/// `Option<DeviceKey>` per invariant 7: *I can name this durably* and *I
/// recognise this unit but cannot name it* lead to different merge behaviour,
/// and a reporter forced to mint a key it does not have would put a fabricated
/// identity into the durable key space.
pub enum ReportedAs {
    /// The reporter minted a durable key for this unit.
    Keyed(DeviceKey),
    /// The reporter sees the unit but has no durable name for it. It
    /// contributes evidence only, joined to a keyed report on `os_id`.
    /// Match evidence that joins to nothing yields no device.
    MatchEvidenceOnly,
}

/// One unit as a reporter currently sees it. Reporters report evidence only —
/// there is no `identity` field, because the identity verdict is the kernel's
/// conclusion from comparing this record against the saved set (phase 9), and a
/// reporter that could assert its own verdict could assert `Proven` for a unit
/// that reported nothing.
pub struct DeviceRecord {
    pub reported_as: ReportedAs,
    /// Parent link. Authored devices hang off their interface; child devices off
    /// their host. `None` = root. Says "this hangs off that" and never names a bus.
    ///
    /// This is the one sanctioned `Option` in the crate: invariant 7 forbids
    /// `Option` where absence carries meaning worth distinguishing, and a root
    /// device has exactly one way to have no parent. There is no
    /// `PlatformCannotReportParent` case to lose.
    pub transport: Option<DeviceKey>,
    pub presence:  Presence,
    /// Exclusive-ownership state. Reporter-asserted exactly like `presence` and
    /// orthogonal to it: a device can be `Present` and `Contended`.
    pub claim:     Claim,
    /// What this unit can do, as this reporter sees it. Phase 9 unions these
    /// across co-reporters and inserts them onto the entity as components.
    pub capabilities: Capabilities,

    // Retained evidence. Reconciliation reads every one of these; the key keeps
    // only the strongest, and the rest are what let a `Displaced` verdict be
    // distinguished from a `WrongUnit` one.
    /// What the unit published about itself, or why it published nothing.
    pub serial:    ReportedSerial,
    /// The OS's own handle for this unit — `CGDirectDisplayID`, an
    /// `IOKit` registry id. Stable within a run, never persisted.
    pub os_id:     OsDeviceId,
    /// Where it is attached: USB port path, display slot, network node.
    /// Phase 9 compares this to decide `Displaced`.
    pub attachment: AttachmentPath,
    /// Vendor, product, and model strings as reported. Never identifying on
    /// their own — two identical webcams report identical triples — and the
    /// input to a `Synthesized` digest.
    pub descriptor: DeviceDescriptor,
}
```

There is no fifth evidence field for the synthesized digest. `DeviceIdSource::Synthesized` already carries it inside `key`, and `descriptor` is the input the reporter derived it from — so a `Synthesized` key holds its digest and a `Reported` key retains none.

```rust
/// What a reporter has to say about the devices it can see.
pub enum DeviceScan {
    /// Nothing was scanned since the last report, so there is nothing to say.
    /// The kernel keeps the set it already holds.
    ///
    /// Normal for every reporter on most frames — cameras enumerate every two
    /// seconds, HID every ten, and clerestory only when the display
    /// configuration changes. Returning this builds nothing.
    Unchanged,
    /// A scan completed.
    Complete(DeviceSet),
}

pub struct DeviceSet {
    pub reporter: ReporterId,
    /// Whole current set, not deltas. Absent devices are omitted.
    /// Parent links make this a forest; the kernel ingests roots first.
    pub devices:  Vec<DeviceRecord>,
    /// Monotonic per reporter; the kernel folds these into a global revision.
    pub revision: ReporterRevision,
}
```

`OsDeviceId`, `AttachmentPath`, and `DeviceDescriptor` each follow invariant 7: a named variant for *this platform has no such concept* and for *the platform has the concept and reported nothing*, never `Option`.

`Claim` is defined here, not with the policy enums, because it is a hardware fact a reporter observes — the same category as `Presence` — and nothing about it is authored:

```rust
/// Reporter-asserted, exactly like `Presence`. Orthogonal to it.
pub enum Claim {
    /// This substrate has no notion of exclusive ownership.
    NotApplicable,
    /// We hold it.
    Held,
    /// Claimable; we have not claimed it.
    Free,
    /// Another process holds it, or holds it such that ours would be useless.
    Contended { holder: ClaimHolder },
    /// The platform refuses. The remedy is a permission grant, not a replug.
    Blocked { gate: PermissionGate },
}

/// Who holds a contended device. Named rather than `Option<String>` because
/// *the platform will not say who* and *nobody is named because the string was
/// empty* are different diagnostics, and invariant 7 forbids collapsing them.
pub enum ClaimHolder {
    /// The platform named the holding process.
    Named(String),
    /// The platform reports contention but will not identify the holder —
    /// macOS camera contention reports exactly this.
    Unidentified,
}
```

`PermissionGate` is a named enum, not a string: the kernel matches on it to decide whether a remedy exists, and its variants are the permission classes an integration crate can hit — camera access, screen recording, input monitoring, plus an integration-supplied catch-all carrying its own detail.

**Capabilities live in their own crate, `hana_works`, which both the kernel's consumers and every integration crate depend on.** They are not kernel-owned and not integration-owned. A closed kernel-side vocabulary would violate invariant 1 — the kernel would have to know what a backlight is — and putting the shared types in an integration crate is worse: `Illuminants` already spans a Stream Deck backlight, an LED ring, and a DMX dimmer, so a DMX integration crate would have to depend on the Stream Deck crate to report light. The crate holds the shared component types and nothing else: no systems, no plugin, no dependency on `hana_rigging`.

`Capabilities` is the reporter's declaration, carried on the record and erased so a reporter can also declare a capability private to itself — a Stream Deck's NFC reader has no second implementer and does not belong in the shared crate:

```rust
/// The capability components this reporter claims for this unit. Erased because
/// the kernel must carry types it cannot name — including ones private to a
/// single reporter — without becoming a registry of device classes.
pub struct Capabilities(Vec<Box<dyn Reflect>>);
```

Phase 9 unions these across co-reporters and inserts them onto the device entity. Two mechanisms it needs, both built here: **attach**, which turns an erased value into a component insert through the type registry rather than through `insert_by_ids` and its unsafe `ComponentId`/`OwningPtr` pairing; and **compare**, which decides whether two co-reporters agree about a capability using `PartialReflect::reflect_partial_eq`. Disagreement blocks in-service use (phase 9). Every capability type registers with `App::register_type` in its owner's plugin build, and attach fails loudly for a type that did not — an unregistered capability is a build error the first scan surfaces, not a silent drop.

`ReporterId` and `DriverId` are opaque `u32` newtypes, issued by the registry (phase 6) in registration order and stable for the process. `ReporterRevision` is a `u64` the reporter registry entry increments on every completed scan; it is per-reporter and monotonic, and the kernel folds the set of them into one global `RiggingRevision` (phase 9). None of the three is persisted. The name is `ReporterRevision`, never `TopologyRevision` — the counter belongs to the reporter that scanned, not to a topology.

Two rules about the forest, and no more. Both are enforced by reconciliation, so this phase states them and phase 9 tests them:
- Presence is **conjunctive down the chain** — a child whose parent is `Unreachable` is `Unreachable`, not `Absent`.
- A parent's departure retires descendants **through the same keyed path**, so nothing depends on a live entity existing.

Endpoints, forced by the audio model (speaker entities each map to one hardware output channel, so one registration per device is wrong):

### Phase 4 — Recovery policy and the three attempt policy enums  · status: done (4bf1b6b9), revised by phase 4b

#### Work Order

**Goal:** the kernel can express what to keep, when to act, toward what state, and what to do when an attempt is abandoned or a local session dies.

**Spec:**

```rust
pub enum RecoveryPolicy {
    /// Don't keep this device's configuration when it goes away.
    #[default]
    Forget,
    /// Keep it, but never send it back on its own.
    Retain,
    /// Keep it; send it when application code asks.
    ReapplyOnRequest,
    /// Keep it; send it automatically once the returning unit is verified.
    ReapplyOnReturn,
}
```

Default is `Forget`. **"Re-apply what you never kept" is unrepresentable rather than rejected at construction** — the four states are flat, so there is no cell to write it in, no constructor to reject it, and no public field through which to bypass one. The four legal states: `Forget` = not retained; `Retain` = remember, report, never touch; `ReapplyOnRequest` = remember, re-apply on demand; `ReapplyOnReturn` = re-apply when the verified unit returns.

A declared safe state — answering *toward what state*: blackout for a light rig, shutter closed for a projector — is deferred; see the deferred register. It has no v1 producer, and as an erased `Box<dyn Reflect>` field it would break the `Reflect` derive, make `RecoveryPolicy` non-`Copy` while phases 4 and 8 both need a copy, and force the public-field shape that lets callers write the illegal cell. When the first device needs one, it arrives as a separate declared-state axis beside `RecoveryPolicy`, never as a payload on it. Its constraint is recorded in the deferred register: departure application is **driver-executed** — the kernel supplies the declared value and the fact of departure, and the driver decides whether energizing anything to reach that state is safe. A kernel that "fails safe by applying the safe value" has reintroduced the laser bug under a reassuring name.

`RecoveryPolicy` is **not** `#[non_exhaustive]`. Its variant set are the policy vocabulary this crate defines; an application matching on them exhaustively is the intended use, and a new variant is a breaking change the kernel should be forced to acknowledge. `#[non_exhaustive]` is reserved for the sets that grow with hardware the kernel cannot enumerate — `DeviceKind`, `IdentityVerdict`, `UnverifiedReason`, `DeviceAccessError`.

Policy is fixed at registration — a change is cancel plus re-register — and is copied where entity loss cannot erase it.

The `ServiceVeto` safety veto is deferred; see the deferred register. There is no interlock device in v1, so it would ship with no producer and an unvalidated shape. Every in-service decision resolves through `Devices::authorize_service()` alone (phase 9), so adding the axis later is a one-function edit plus one enum.

The three policy enums:

```rust
pub enum RetryOn {
    /// The device set changed since the failed attempt. Cannot loop forever —
    /// no change, no retry.
    NewRevision,
    /// Fixed cadence, for failures that resolve without any device change.
    Interval(Duration),
}
```

Both variants are required. A camera held open by another application becomes free when that application quits: no device appears or disappears, so the revision never advances, so a revision-gated retry would never fire. Conversely `Interval` alone would hammer a device whose failure is permanent until the set changes. `RetryOn` is a **plain enum, no `#[non_exhaustive]`** — downstream constructs it and the kernel matches it, so no downstream match exists to break, and a `_` arm is exactly where a new variant gets silently swallowed.

```rust
/// What to do with a device when an attempt is abandoned and we can still
/// reach it.
///
/// Only consulted when the attempt was abandoned because the device set
/// changed. A lost claim makes reverting impossible and a service veto makes it
/// unsafe, so the kernel decides both of those itself without reading this.
#[derive(Clone, Copy, Debug, Default)]
pub enum OnAbort {
    /// Leave the device in whatever partial state it reached and let the next
    /// reconcile drive it.
    ///
    /// Right for a device whose reconfiguration is slow or visible — a
    /// projector lamp takes tens of seconds — because the set change that
    /// abandoned this attempt is about to produce a new target anyway.
    #[default]
    LeaveAsIs,
    /// Re-apply the configuration captured before the attempt started.
    ///
    /// Right when a half-applied state is itself wrong: a window parked
    /// between two monitors is visibly broken, not merely stale.
    Revert,
}
```

The abort-cause table is a **kernel rule, not policy**: claim lost ⇒ never revert (reverting is impossible, not undesirable); service vetoed ⇒ never revert (reverting re-sends a configuration that may have been energized, re-energizing a device whose interlock just opened); revision changed ⇒ consult `OnAbort`.

```rust
/// What to do when the local session for a still-present device dies on its
/// own — a window destroyed by the compositor, a capture session invalidated
/// across sleep, a HID handle closed by a bus reset.
///
/// Distinct from device absence, which `Presence` and `RecoveryPolicy` handle, and from
/// an abandoned attempt, which `OnAbort` handles. Nothing unplugged and
/// nothing was in flight.
#[derive(Clone, Copy, Debug, Default)]
pub enum OnSessionLoss {
    /// Open a new session and re-apply the captured configuration, without
    /// involving application code.
    ///
    /// A camera panel goes black for a frame after the laptop wakes and then
    /// repopulates. Runs as an ordinary attempt, so `RetryOn` gates it — a
    /// camera the OS has wedged will not be reopened in a loop. Reuses the
    /// published image handle, so bound materials survive the rebuild.
    #[default]
    Recreate,
    /// Report the loss and do nothing else, leaving the response to
    /// application code.
    ///
    /// For a device where the replacement is a decision, not a repeat — a
    /// window that should be placed differently the second time, or one the
    /// user should be asked about first.
    ReportOnly,
}
```

### Phase 5 — Attempts, captured configuration, and faults  · status: done (556c888f)

#### Work Order

**Goal:** the kernel can name one attempt, say where a role stands in recovery, report an outcome, hold the configuration to return to, and classify a failure.

**Spec:**

```rust
pub enum RoleState {
    /// Registered, unit present, nothing owed.
    Ready,
    /// Nothing can be attempted right now: no device, or one that is present but
    /// contended or policy-gated. `RecoveryPolicy::Retain` rests here indefinitely.
    Waiting,
    /// An apply is in flight. Whether it is past its deadline is not a state —
    /// ask `Attempts::is_overdue(id, now)`, which stays true as polling continues.
    Applying(AttemptId),
    /// Retired by key. Later presence must not revive it.
    Retired,
}

/// The **role**, not the hardware: an app-assigned handle for "the thing this
/// binding is for" that outlives every unit that ever fills it. `WindowKey` and
/// `SecondaryCameraId(u32)` are both this, spelled twice. Distinct from
/// `DeviceKey`, which names a unit — a role survives the unit being unplugged
/// and replaced, which is the whole point.
///
/// The field is private, so the type needs a validating constructor and an
/// accessor or no integration crate can produce one: `RoleKey::new(impl
/// Into<String>) -> Result<RoleKey, RoleKeyError>` rejecting empty values and
/// control characters, and `RoleKey::as_str()`. Match the shipped checked-newtype
/// convention exactly — `endpoint.rs` ships it as `Slot`/`SlotError`, which the
/// rename table above turns into `PartName`/`PartNameError`
/// (`crates/hana_rigging/src/endpoint.rs`) — rather than inventing a second
/// validation shape.
pub struct RoleKey(String);

/// Names one attempt. A `u64` from a monotonic counter on `Attempts` (phase 9),
/// never reused within a process — a late `poll` for a finished attempt must
/// resolve to nothing, not to whatever attempt took its slot.
pub struct AttemptId(u64);

/// The driver's sole outcome report. Split in two so the completion event
/// carries an `AttemptOutcome` and cannot be constructed with `Pending`.
pub enum AttemptProgress { Pending, Finished(AttemptOutcome) }

pub enum AttemptOutcome { Succeeded, Failed(DeviceAccessError), Aborted, Substituted }

/// The configuration a driver last successfully applied to one device.
///
/// The kernel stores this without interpreting it — knowing what a monitor or
/// camera configuration *is* would violate the membership test. It holds the
/// driver's own `Configuration` erased to a reflected value, which the driver
/// recovers by downcast and BRP can display for debugging.
///
/// There is no lifecycle tag on this value. Whether a live re-read is safe is
/// decided at the single site that calls `capture`, from `Presence` and the
/// in-flight attempt registry — both of which the kernel already maintains
/// authoritatively, so the answer cannot go stale there.
```

**The `Attempt` record itself is defined in phase 9, not here.** Two of its fields have types no earlier phase can supply: `permit: ApplyPermit` is phase 6's private-constructor token, and `rigging_revision: RiggingRevision` is phase 9's global counter. This phase ships the vocabulary the record is made of (`AttemptId`, `AttemptProgress`, `AttemptOutcome`, `CapturedConfiguration`) and phase 6 needs only `AttemptId`, so nothing between here and phase 9 is blocked by the deferral.

`AttemptOutcome::Aborted` is **terminal and never auto-retries** — it is what a safety gate closing mid-attempt produces, and collapsing it into an overdue-but-still-polling attempt would re-permit the retry.

**Coverage audit.** This enum is the only outcome vocabulary, so every scenario lands in exactly one case:

| Scenario | Case |
|---|---|
| Working, inside the deadline | `Pending` |
| Working, past the deadline | still `Pending` — overrun is **kernel-side** state. `poll` takes only an `AttemptId` and the kernel owns the timing (phase 6), so the driver neither knows nor reports it; the kernel counts the overrun against the configured budget. |
| Landed as requested, or within the driver's own tolerance (60 fps satisfied at 59.94) | `Finished(Succeeded)` |
| Landed, but on a different device or slot than requested | `Finished(Substituted)` |
| The driver tried and the hardware refused | `Finished(Failed(fault))` |
| Overrun budget exhausted | `Finished(Aborted)` |
| The reporter went stale past its freshness lease | `Finished(Aborted)` |
| The device departed mid-attempt | `Finished(Aborted)` |
| A safety gate closed mid-attempt | `Finished(Aborted)` |

`Aborted` therefore has four producers and no auto-retry from any of them; the reason a caller needs is on the device (`DeviceAccessError`, `Presence`), not multiplied into this enum.

`CapturedConfiguration` is `Box<dyn Reflect>`, never `Box<dyn Any>` and never `ProviderBlob(Vec<u8>)` — bytes are only needed for a value that leaves the process, and this one does not. Reflect costs nothing extra and buys BRP inspectability; reflection blindness already cost a phantom regression during the asset-loading work. Suppression is **per key** — a global pause is a live bug in clerestory today and must not be carried across.

**The erased field is `#[reflect(ignore)]`, and the payload is inspected at the driver's own type instead.** `Box<dyn Reflect>` implements neither `Reflect` nor `PartialReflect` in bevy 0.19 (`bevy_reflect-0.19.0/src/impls/alloc/` has no `Box<T>` impl), so a struct holding a bare erased field cannot derive `Reflect` at all — phase 3 already hit this and shipped `Capabilities` (`crates/hana_rigging/src/capabilities.rs:13-14`) with no derive. Ignoring the field keeps `CapturedConfiguration`, and phase 8's `RequestedConfiguration`, inside reflected containers so `Bindings` and `Devices` stay registered resources. An ignored field still has to satisfy the enclosing type's `FromReflect`, so the enclosing derive may need `#[reflect(default = "..")]` or may have to reduce to `Reflect` alone; settle that against the compiler rather than guessing.

Inspectability is not given up for the captured value — it moves to where that value is typed. Phase 10 inserts the captured configuration onto the binding entity as the driver's own component through `ReflectComponent`, exactly as `Capabilities::attach` (`crates/hana_rigging/src/capabilities.rs:45-65`) already does for capability components, so BRP shows the driver's real struct with real field names rather than an opaque leaf nested in the kernel's tree. `RoleState` is **not** `#[non_exhaustive]`, for the same reason `RecoveryPolicy` is not: it is the kernel's own vocabulary and an application matches it exhaustively. `DeviceAccessError` is, because failure modes arrive with hardware the kernel cannot enumerate.

`DeviceAccessError` is the typed failure classification that replaces prose. ### Phase 6 — Reporter and driver contracts, type-erasing registration, plugin and set  · status: done

#### Work Order

**Goal:** a reporter written in another crate can be registered with `app.add_device_reporter(..)` and a driver with `app.add_endpoint_driver(..)`, and the kernel calls the reporters once per tick inside `RiggingSystems::Collect` without ever naming their types.

**Spec:**

Phase 3 shipped `DeviceScan::Complete(DeviceSet)`, but that lets an integration crate fill the
registry-issued `ReporterId` and `ReporterRevision` itself. Change the public reporter result here
to `DeviceScan::Complete(Vec<DeviceRecord>)`. The typed reporter supplies only its whole current
record list; the non-generic reporter entry constructs the internal `DeviceSet`, stamps the issued
reporter id, and advances the entry-owned revision. This is the same boundary the final ids-and-revisions
paragraph below requires.

Two traits. Reporting what hardware exists and driving one endpoint are separate jobs served by different implementations for the same unit — the monitor reporter only scans, the window driver only captures, applies, and polls — so a single trait would force half its methods to be no-ops, and one of those no-ops would be `start_apply`, the method that receives the kernel's authorization.

```rust
/// Reports what hardware exists. No method on this trait touches a device.
pub trait DeviceReporter: Send + Sync + 'static {
    /// Called once per `RiggingSystems::Collect`. Whole-set, not deltas.
    ///
    /// `&mut World` means this runs on the main thread with exclusive access, so
    /// the reporter may reach `!Send` state through `world.non_send_resource_mut`
    /// and touch thread-locals the kernel never touches. It must **not** block:
    /// enumeration that talks to hardware belongs on a thread the reporter owns,
    /// and `scan` drains that thread's channel. A reporter with nothing new
    /// returns `DeviceScan::Unchanged`.
    fn scan(&mut self, world: &mut World) -> DeviceScan;
}

/// Drives one endpoint. Every method here can touch hardware.
pub trait EndpointDriver: Send + Sync + 'static {
    /// The configuration this driver accepts and reads back — its own type, in
    /// its own vocabulary. `Reflect` is required so the kernel can hold it
    /// erased in `CapturedConfiguration`; `Component` is required so phase 10 can insert the
    /// captured value onto the binding entity through `ReflectComponent` and BRP
    /// can read it at its own type rather than as an opaque box. Two ordinary
    /// derives satisfy both.
    type Configuration: Reflect + Component;

    /// Read the live endpoint's configuration for capture.
    ///
    /// The kernel calls this only when the endpoint is present and no attempt is
    /// in flight for it; the driver does not re-check either condition.
    fn capture(&mut self, world: &mut World, endpoint: &DeviceEndpoint)
        -> CaptureOutcome<Self::Configuration>;

    /// **Start** driving the endpoint to the state `configuration` describes, and
    /// return immediately — every real open in this codebase is backgrounded with
    /// a channel outcome, and a blocking implementation would mandate a
    /// main-thread stall. **Absolute, not differential** — the driver must not
    /// assume a known starting state.
    fn start_apply(&mut self, world: &mut World, endpoint: &DeviceEndpoint,
                   configuration: &Self::Configuration, attempt: AttemptId,
                   permit: ApplyPermit);

    /// Polled each reconcile until it resolves. The kernel's end-to-end deadline
    /// bounds the whole sequence, so a driver that must reset then render
    /// reports `Pending` between the two and cannot claim it is done early.
    /// The driver supplies what counts as arrived — a delivered frame, a stable
    /// position, a completed image write. The kernel only times it.
    /// The sole outcome report. Judging "close enough" is the driver's:
    /// a camera asked for 60 fps and given 59.94 returns `Succeeded`; a window that
    /// lands on a different display returns `Substituted`. That comparison is a
    /// private helper, not a trait method — only the driver knows the
    /// tolerance, and `Reflect` offers no equality to default it from.
    fn poll(&mut self, world: &mut World, apply: AttemptId) -> AttemptProgress;
}
```

`capture` returns a named outcome, not `Option` — invariant 7:

```rust
pub enum CaptureOutcome<P> {
    /// Read back successfully.
    Read(P),
    /// The endpoint is reachable but exposes no readable configuration.
    /// Permanent for this device; the kernel stops asking.
    NotReadable,
    /// A transient read failure. The kernel keeps the previous `CapturedConfiguration` value
    /// and asks again next reconcile.
    ReadFailed(DeviceAccessError),
}
```

`ApplyPermit` is a **private-constructor token minted only by the kernel** and the only token `start_apply` accepts. It is one opaque type with two private cases:

```rust
/// Proof that the kernel authorized this apply, and for what. Opaque: the cases
/// are private, there is no public constructor, and a driver cannot fabricate
/// one — so authorizing in-service use from an unproven identity cannot compile.
pub struct ApplyPermit(Purpose);

enum Purpose {
    /// Minted from `Proven` or `Authored`. The device may be put into service —
    /// driven for the job the application bound it to.
    InService,
    /// Minted additionally from `RestoreOnly`. The device may be returned to a
    /// previously captured configuration and nothing more.
    RestoreOnly,
}
```

One type rather than two because `start_apply` is the only entry point that acts on a device, and a second object-safe entry point for restore would duplicate the whole erased-dispatch path to express one bit. Phase 10 mints the value through its authorization API; Phase 11 stores that value on `Attempt.permit` and passes it to the driver, so the record and the token are the same value. `ApplyPermit` exposes a public predicate — `allows_in_service_use() -> bool` — for drivers whose apply path genuinely differs; drivers that treat both cases alike ignore it.

**The erased dispatch is fallible.** The driver entry's typed `start_apply` function downcasts the `Box<dyn Reflect>` in `CapturedConfiguration` back to `Self::Configuration` before calling the driver, and a mismatched type there is a driver-contract violation, not an unrepresentable state — two drivers can register with `CapturedConfiguration` values crossed. The typed capture, start, and poll functions also downcast the entry's `Box<dyn Any + Send + Sync>` to the concrete driver type they were installed for. A failure of that internal pairing returns the named `DriverContractError::DriverTypeMismatch`. Every erased method returns `Result<T, DriverContractError>`; the kernel logs the error, fails the attempt with `AttemptOutcome::Failed`, and continues. It never unwraps — the workspace denies `unwrap_used`, and a downcast failure must not take the app down.

**Reporters and drivers are borrowed out of the world, not from it.** The non-generic reporter entries live in a `Reporters` resource and the non-generic driver entries in a `Drivers` resource, and calling `scan(&mut World)` while holding a borrow of either aliases the world. The kernel calls each inside `world.resource_scope::<Reporters, _>(..)` / `resource_scope::<Drivers, _>(..)`, so the list is temporarily removed from the world for the duration. The contract that follows, stated on both traits: an implementation must never insert, remove, or read the resource holding it — that resource is absent while it runs, and touching it panics. It must also not mutate kernel-owned state through the `&mut World` it is handed: not `Devices`, not `Attempts`, not `RiggingRevision`, and not the device or binding entities or their kernel components. It reports through its return value and nothing else. An implementation that half-writes kernel state and then returns an error leaves the kernel inconsistent with no way to unwind, which is exactly the failure the whole-set scan model exists to avoid.

A reporter or driver panic is fatal and is not caught. Catching it would leave the kernel holding half a scan from a reporter it can no longer trust, and `resource_scope` would have to reinsert an implementation that just proved it can panic. One that cannot proceed reports a `DeviceAccessError` instead.

**`fn migrate` is struck.** It existed to move a persisted driver blob forward across versions; nothing persists one any more. The two real migrations are versioned and owned where the data lives — clerestory's window state v3 → v4 (phase 17) and catalyst's saved `HardwareKey` values (phase 22).

Registration erases the associated type:

```rust
let reporter = app.add_plugins(RiggingPlugin)
                  .add_device_reporter(MonitorReporter::default());
let driver   = app.add_endpoint_driver(WindowDriver::default());
```

Each call returns the id the registry issued — `ReporterId` and `DriverId` — which is the only way to obtain one. `Reporters` stores non-generic entries containing a `ReporterId`, revision counter, and boxed `FnMut(&mut World) -> DeviceScan`; the generic registration method captures the typed reporter in that closure, so reporter dispatch needs no `Any` downcast. `EndpointDriver`'s associated type cannot appear in a signature reached through `dyn`, so `Drivers` stores non-generic entries containing `Box<dyn Any + Send + Sync>` plus typed function pointers for capture, start, and poll. The entry's generic constructor installs those pointers once, and each private generic function recovers the typed driver before invoking the public trait method. The driver author never writes the erased form and the kernel never names a type it cannot know. A static enum registry would make `hana_rigging` name `hana_clerestory` and invert the dependency.

**Scheme registration is the third app-facing entry point and lives beside the other two.** Phase 1 shipped `RegisteredSchemes` (`scheme.rs:161`) with `register`/`contains`/`validate`, and nothing inserts it into an app; phases 14 and 24 say only "register in the crate's plugin build", which without an entry point means a raw `world_mut().resource_mut::<RegisteredSchemes>()` that panics when `RiggingPlugin` has not built yet. Add an `App` extension whose implementation calls `init_resource::<RegisteredSchemes>()` before registering, so an integration crate's plugin added before or after `RiggingPlugin` behaves identically and plugin insertion order stops being load-bearing:

```rust
app.register_device_scheme(SchemeName::new("edid-serial")?);
```

**All three methods live on one public trait, `RiggingAppExt`.** Rust cannot add inherent methods to Bevy's `App`, so `add_device_reporter`, `add_endpoint_driver`, and `register_device_scheme` require an extension trait, and its name is a public import every integration crate writes — `use hana_rigging::RiggingAppExt;`. Name it once here rather than letting the implementation pick one. Export it from the crate root and the prelude. This follows Bevy 0.19's own `*AppExt` convention.

The kernel holds `Vec<ReporterEntry>` and calls `scan` on each inside a public system set. **The sets are API, not an implementation detail** — a consumer has to be able to sequence its own work against the kernel's phases, and once a consumer outside these two repos sequences against them these four names become effectively permanent, so treat them as settled from here:

```rust
/// Chained in `Update` in this order.
#[non_exhaustive]
pub enum RiggingSystems {
    /// Every reporter's `scan` runs. Nothing has been diffed yet.
    Collect,
    /// The kernel diffs, computes verdicts, mirrors components, and emits its
    /// events at the end of this set.
    Reconcile,
    /// **The consumer slot.** The kernel schedules nothing here. Identity and
    /// authorization are decided and no `start_apply` has started, which is the only
    /// interval in which a consumer can compute the parameters it is about to
    /// request — clerestory's fallback machine (phase 15) builds window targets
    /// here.
    Prepare,
    /// Attempts start, poll, retry, and escalate.
    Apply,
}
```

`#[non_exhaustive]` so a later phase can add a set without breaking anyone's `.after(..)`. `scan(&mut World)` is exclusive by signature, which is what lets a winit reporter reach main-thread-only state while a HID reporter drains a channel from a thread it owns — neither is dragged onto the other's execution model.

**An integration crate validates its own environment in `Plugin::finish`, not in `build`.** Bevy runs `finish` after every plugin has built, so an integration crate that needs `WinitPlugin` and its `WinitMonitors` resource can assert their presence there and fail with a named error regardless of whether the consumer added it before or after `DefaultPlugins`. Asserting in `build` makes correctness depend on plugin insertion order, which the consumer controls and the integration crate cannot see.

Reconcile is **timer backstop plus OS-event fast path**, not the reverse: there is no hot-plug anywhere in the hidapi stack, and monitors — which do get OS events — are the exception in the reference set.

### Phase 7 — Asynchronous discovery scheduling, startup readiness, and progress state  · status: done

#### Work Order

**Goal:** the kernel decides when hardware discovery is due, launches independent reporter jobs on Bevy's `IoTaskPool` without submitting the same reporter twice, keeps capacity available for unrelated I/O work, and exposes enough retained state for startup gating and later UI progress events.

**Spec:**

Phase 6 deliberately separated whole-domain discovery (`DeviceReporter`) from per-endpoint operations (`EndpointDriver`), but its reporter contract still makes every integration own its own thread and calls every reporter once per app update. Replace that temporary execution contract here. The kernel owns discovery cadence, batching, task admission, completion collection, and startup readiness. A reporter owns only the integration-specific enumeration code and returns owned results; no worker may mutate `World`, `Devices`, `Bindings`, entities, revisions, or retained reports.

The public reporter prepares either a main-thread result or one owned background job:

```rust
pub trait DeviceReporter: Send + Sync + 'static {
    /// Prepare one complete discovery run when the kernel says this reporter is due.
    /// This method runs on the main thread, receives no `World`, and must return
    /// without blocking.
    fn discover(&mut self) -> DiscoveryWork;
}

pub enum DiscoveryWork {
    /// Owned work the kernel immediately invokes with `World` on the main thread.
    Immediate(MainThreadDiscoveryJob),
    /// Owned work that can run without `World` on Bevy's I/O task pool.
    Background(DiscoveryJob),
}

pub struct MainThreadDiscoveryJob(
    Box<dyn FnOnce(&mut World) -> DeviceScan + 'static>
);

pub struct DiscoveryJob(
    Box<dyn FnOnce(DiscoveryProgressSender) -> DeviceScan + Send + 'static>
);

pub enum DeviceScan {
    /// Every device currently visible to this reporter.
    Complete(Vec<DeviceRecord>),
    /// Enumeration failed. Keep the reporter's last complete set and revision.
    Failed(DeviceAccessError),
}
```

`DeviceScan::Unchanged` is removed. Not calling a reporter is now the self-documenting unchanged case: cadence state says it is not due, disabled, queued, or already running. `Immediate` exists for APIs such as winit monitor enumeration that must touch `!Send` main-thread state; its `MainThreadDiscoveryJob` is invoked synchronously with `&mut World`, is never stored in reporter runtime state, and is never eligible for `IoTaskPool`. It must only copy/enumerate already-available state and may not perform a slow probe. A background reporter captures sendable inputs from its own integration state while `discover` is on the main thread, then returns a `DiscoveryJob`. Because `DeviceReporter::discover` itself receives no `World`, the background closure cannot move the application world into its job; the main-thread job is the sole discovery boundary that receives it. A completed scan still means the reporter's whole current set, not deltas. The registry stamps `ReporterId` and advances `ReporterRevision` only when `Complete` is accepted on the main thread; `Failed` retains the preceding set and revision.

Reporter registration states whether the application must wait for its first successful result and how it becomes due:

```rust
pub enum DiscoveryCadence {
    /// Runs only when application code explicitly requests it.
    OnDemand,
    /// Runs when marked dirty, with a lightweight timer as a missed-event backstop.
    EventDriven { backstop: Duration },
    /// Runs at most once per interval.
    Periodic { interval: Duration },
}

pub enum ReporterActivation {
    Enabled,
    Disabled,
}

#[derive(Clone, Reflect)]
#[reflect(opaque)]
pub struct ReporterRegistration { /* private invariant-preserving fields */ }

impl ReporterRegistration {
    pub fn required(cadence: DiscoveryCadence) -> Self;
    pub fn optional(cadence: DiscoveryCadence, activation: ReporterActivation) -> Self;
}
```

`required` always starts enabled and cannot be disabled. `optional` is controlled independently of authored inventory: registering or configuring an offline device never enables a reporter. Change `RiggingAppExt::add_device_reporter` to accept the `ReporterRegistration` beside the reporter and return its `ReporterId`. Add a public reflected `DiscoveryControl` resource with checked `enable`, `disable`, `request`, and `mark_dirty` methods. Reflect `DiscoveryControl` as `#[reflect(Resource, opaque)]`, not as a structural resource: dynamic reflection must not expose its private reporter records or bypass the checked methods. `ReporterRegistration` is opaque for the same reason. Enabling performs an initial discovery immediately; disabling cancels only queued work, never drops a running task, and suppresses the coalesced rerun after that task reports. Trying to disable a required reporter or address an unknown id returns a named `DiscoveryControlError` and leaves state unchanged.

The scheduler first computes the complete due list for the frame, coalesces duplicate triggers by `ReporterId`, assigns one logical `DiscoveryBatchId`, then admits independent jobs. Only idle reporters enter that due list: disabled reporters are ineligible, queued reporters are already represented, and running reporters record a coalesced rerun request instead of being submitted again. Required-startup reporters form the first batch. Until every required reporter has produced a successful `Complete`, optional reporters stay out of the due list entirely; their initial request, dirty signal, and expired cadence deadline remain unconsumed. Once startup is ready, those optional reporters become due in a later batch with a distinct `DiscoveryBatchId`. There is no global completion barrier after admission: each result is collected and made available to reconciliation independently. A required failure leaves the readiness gate closed, records the failure for the UI, and is eligible again under its cadence or an explicit request. Startup derives across the complete required set: any accepted required failure deterministically outranks incomplete required reporters regardless of registration order; only the absence of failures permits `Discovering` or `Ready`.

Use an explicit per-reporter runtime state machine:

```rust
enum ReporterRunState {
    Disabled,
    Idle,
    Queued { batch: DiscoveryBatchId },
    Running { task: Task<DeviceScan>, rerun: RerunRequest },
}

enum RerunRequest {
    NotRequested,
    Requested,
}
```

A reporter in `Running` is never submitted again. Any number of timer, dirty, or on-demand triggers while it runs collapse to `RerunRequest::Requested`. When that task completes, the reporter becomes queued exactly once if the request remains applicable; there are no catch-up bursts. A periodic deadline advances from the actual submission/completion schedule rather than replaying every missed interval. `EventDriven` dirty flags coalesce in the same way, and its backstop supplies one due request when OS notification is missed.

Spawn background work through `IoTaskPool::get().spawn(..)` and retain each `Task<DeviceScan>` until `poll_once` yields its result. Enable Bevy's `multi_threaded` feature on `hana_rigging`'s normal workspace dependency so production discovery cannot fall back to the single-threaded task backend through missing dev-feature unification. Sample `Instant::now()` immediately before each actual `IoTaskPool::spawn`; that instant supplies `Running::started_at`, elapsed progress, and the eventual outcome duration. Do not initialize the global task pool from `hana_rigging`: if background work is requested before Bevy's `TaskPoolPlugin` has initialized `IoTaskPool`, retain `DiscoverySchedulerState::Failed { error: IoTaskPoolUnavailable }` and keep required startup closed. This scheduler failure is not a reporter result: `LastDiscoveryOutcome`, `completed_batches`, the retained set, revision, and reconciliation failure handoff remain unchanged because no reporter job ran.

Admission and main-thread reconciliation have separate configurable bounds:

```rust
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct DiscoveryLimits {
    max_concurrent_jobs: NonZeroUsize,
    max_completions_per_frame: NonZeroUsize,
    progress_after: Duration,
}
```

Expose getters plus checked setters that accept `NonZeroUsize`, so application/UI code can tune both limits at runtime but cannot turn discovery off by setting a limit to zero. Defaults: two concurrent discovery jobs, two accepted completions per frame, and progress becomes UI-visible after 500 ms. The effective concurrency is
`min(configured_max, max(1, IoTaskPool::get().thread_num().saturating_sub(1)))`: when the I/O pool has two or more threads, discovery can never occupy its final thread, even when the configured maximum is larger; when the app has configured a one-thread I/O pool, running one discovery job is the unavoidable exception because reserving that sole thread would disable discovery. Document that boundary on the resource and expose the effective value for diagnostics.

Implement `Default` with those values and expose `max_concurrent_jobs`, `max_completions_per_frame`, `progress_after`, `effective_max_concurrent_jobs`, `set_max_concurrent_jobs`, `set_max_completions_per_frame`, and `set_progress_after`. A runtime update governs the next admission or completion pass; it never cancels an already-running reporter. The nonzero job limit is deliberately capacity control, not an enable/disable switch: optional reporter activation remains the separate API for deciding what hardware the application is willing to look for.

Completion budgeting limits the number of whole reporter results accepted per frame, not the number of records inside a result. A reporter's `Complete(Vec<DeviceRecord>)` remains atomic: never split one whole-set snapshot across frames. Prioritize required completions, then oldest queued completion. Retain remaining completed tasks for the next frame. This bounds kernel reconciliation overhead while allowing unrelated app work to continue.

Background jobs may report progress through `DiscoveryProgressSender` without learning their `ReporterId`; the scheduler attaches the id and batch when it receives the update. Progress is self-documenting rather than optional:

```rust
pub enum DiscoveryProgress {
    Indeterminate,
    Measured { completed: u32, total: NonZeroU32 },
}
```

Retain per-reporter activity, latest progress, elapsed time, failure, and batch counts in a reflected `DiscoveryStatus` resource. Its owned state uses named variants instead of bare optional fields:

```rust
pub struct ReporterDiscoveryStatus {
    pub activity: ReporterActivity,
    pub last_outcome: LastDiscoveryOutcome,
    pub completed_batches: u64,
}

pub enum ReporterActivity {
    Disabled,
    Idle,
    Queued { batch: DiscoveryBatchId },
    Running {
        batch: DiscoveryBatchId,
        elapsed: Duration,
        progress: DiscoveryProgress,

}

pub enum LastDiscoveryOutcome {
    NotCompleted,
    Succeeded { batch: DiscoveryBatchId, duration: Duration },
    Failed {
        batch: DiscoveryBatchId,
        duration: Duration,
        error: DeviceAccessError,
    },
}
```

This keeps a previous success or failure visible while the next run is idle, queued, running, or later disabled. `LastDiscoveryOutcome` is exported through the crate prelude beside the other discovery status types. Represent startup readiness explicitly as `StartupDiscoveryState::{Discovering, Ready, BlockedByFailure { reporter, error }}` and expose a public `hardware_ready` run condition. Do not emit Bevy events yet; phase 12 converts these retained transitions into per-reporter and global progress events, and phases 8–10 add configured-device and identified-device state to the same UI model. Before `progress_after`, the state still updates but phase 12 emits no long-running-progress event, avoiding a flash for fast discovery.

The non-reflected reporter registry retains each reporter's latest complete, registry-stamped `DeviceSet` and completion time. The collect/reconcile handoff is a crate-private queue of changed `ReporterId`s plus failures; phase 9 drains that queue and borrows all retained latest sets when any reporter changed, so an unchanged co-reporter's evidence remains available without cloning erased capabilities. This phase never creates a live `Device` entity: a live entity remains evidence-backed and comes only from reconciliation of reporter evidence.

### Phase 8 — Bindings: registration, routing, and the role lifecycle  · status: todo

#### Work Order

**Goal:** an app can author hardware it may not own, bind each role to one uniquely owned endpoint, inspect configuration while that hardware is offline, and move every role through one precise state model without any driver call escaping that model.

**Spec:**

`RoleKey` (phase 5) names a role and `DeviceEndpoint` (phase 3) names where it lives, but nothing binds them. Without a binding record the kernel cannot serve the case it exists for: clerestory and `xcap` both report an equal `DeviceKey` for one display with different `Configuration` types, and `DeviceEndpoint` carries no route, so the kernel cannot tell which driver to hand an apply to, cannot associate configuration with a role, or reject two roles that accidentally claim the same endpoint.

```rust
/// One authored binding: a role, where it goes, who serves it, how it behaves
/// when the unit leaves, and what to ask for.
#[derive(Reflect)]
pub struct Binding {
    pub role:      RoleKey,
    pub endpoint:  DeviceEndpoint,
    /// Which driver serves this endpoint. Routing is by driver, never by
    /// capability: two drivers can serve one `DeviceKey` and take different
    /// `Configuration`, so capability is not a discriminator. Capability routing
    /// is additive later and changes nothing here.
    pub driver:    DriverId,
    pub recovery:  RecoveryPolicy,
    pub retry:     RetryOn,
    pub on_abort:  OnAbort,
    pub on_loss:   OnSessionLoss,
    /// Authoritative per-role runtime state. The binding entity mirrors this value
    /// later; it never becomes a second writer.
    pub state:     RoleState,
    /// What to ask the driver for, erased because the kernel carries a type it
    /// cannot name. The driver registry entry downcasts it to
    /// `Self::Configuration` and reports `DriverContractError` when the binding
    /// names a driver that does not take this type.
    pub requested: RequestedConfiguration,
    /// What a safe readback most recently proved was actually on the endpoint.
    pub last_known_good: LastKnownGoodConfiguration,
}

/// Authored intent, erased.
pub struct RequestedConfiguration(Box<dyn Reflect>);

/// The most recent configuration established by a successful safe readback.
pub enum LastKnownGoodConfiguration {
    /// No safe readback has established an actual endpoint value yet.
    NotEstablished,
    /// A safe readback established this driver-specific value.
    Known(#[reflect(ignore, default = "default_erased_configuration")] Box<dyn Reflect>),
}
```

Rename phase 5's shipped `CapturedConfiguration` to `LastKnownGoodConfiguration` here. This phase is the first owner of the value, so the rename and lifecycle become one coherent change instead of leaving a generic-sounding wrapper for later code to guess about. `RequestedConfiguration::new<T: Reflect>(value)` and `LastKnownGoodConfiguration::known<T: Reflect>(value)` are public typed constructors; both expose only crate-private `as_reflect` access for erased dispatch. `LastKnownGoodConfiguration::NotEstablished` is the semantic default. There is no `Option` around it and no erased unit sentinel representing absence.

`Box<dyn Reflect>` is itself not `Reflect` in bevy 0.19. Apply phase 5's ignored-erased-field treatment to both wrappers, but keep the lifecycle in the enum: only `Known` contains an erased payload and `NotEstablished` is an actual domain state. Neither wrapper is required to derive `Clone`, `Debug`, or `PartialEq`, so `Binding` must not assume those derives. Phase 10 projects only the known last-good value onto the binding entity, because requested and established configurations have the same concrete driver type and one entity can hold only one component of that type. `Bindings` remains the sole authority; the entity is read-only projection.

`requested` is intent, not evidence. A successful apply changes the role to `Ready`; it does **not** copy the requested target into `last_known_good`, because a driver may substitute or normalize what landed. The next safe capture while that role is `Ready`, present, and has no restoration pending records what actually landed. `CaptureOutcome::ReadFailed` preserves the previous enum value; departure, recovery, or an in-flight attempt freezes it; `NotReadable` permanently suppresses further capture for that binding without manufacturing a known value.

`RoleState` is the authoritative per-binding state machine. Correct phase 5's default from `Ready` to `Waiting`: a newly authored role has not observed usable hardware. `Bindings` exposes typed views with no public constructors — `WaitingRole`, `ReadyRole`, and `ApplyingRole` — selected from the stored enum. Kernel-only transition methods live on the view that is allowed to perform them: only `ReadyRole` can mint a `CaptureRequest`; only `WaitingRole` can begin an authorized requested apply or last-good restore; only `ApplyingRole` can mint a `PollRequest`, abort, or finish. `Retired` has no operational view. The binding entity's later `RoleState` component is a read-only mirror of this record.

The request types have private fields and carry the role, driver, endpoint, attempt/permit where applicable, and a borrow of the correct configuration source. Change crate-private `Drivers::{capture,start_apply,poll}` to accept those requests instead of independent raw ids, endpoints, configurations, and attempt ids. The typed driver function pointers remain phase 6's erased boundary, but kernel code cannot assemble a driver call without first obtaining the matching state view. Any temporary dead-code expectation needed before phases 10–11 add production callers must use a specific phase 10/11 cleanup reason and is removed by those phases together with phase 6's five existing expectations.

The registry operations live on a `Bindings` resource keyed by `RoleKey` with two private reverse indexes:

```rust

owner_by_endpoint: HashMap<DeviceEndpoint, RoleKey>,
roles_by_device:   HashMap<DeviceKey, /* role keys */>,
```

- `register(Binding) -> Result<(), BindingError>` fails on either an existing role or `BindingError::EndpointAlreadyOwned { endpoint, owner }`. Duplicate endpoint ownership is illegal in v1 even when the roles differ.
- `replace(Binding) -> Result<Binding, BindingError>` checks the proposed endpoint against `owner_by_endpoint` **before** releasing the old endpoint. An error leaves all three maps and the old binding unchanged. Replacing a role with its currently owned endpoint is legal. It remains a pure registry swap; phase 11 performs attempt abortion from the retained mutation record.
- `retire(&RoleKey) -> RetirementOutcome` is idempotent and removes all three index entries atomically. `RetirementOutcome::{Retired(Binding), AlreadyUnbound}` preserves why no value was returned.
- `binding(&RoleKey) -> Result<&Binding, BindingError>` and `roles_for(&DeviceKey) -> impl Iterator<Item = &RoleKey>` are the read paths; no owned API uses a bare `Option` to encode bound versus unbound.

Do not panic for duplicate ownership. Private maps plus atomic checked operations make invalid construction unavailable through the public API, and a recoverable `BindingError` lets an editor show the two roles involved. Supporting multiple owners later must be an explicit data-model/API feature that replaces `owner_by_endpoint`; it cannot appear accidentally through today’s registration path.

### Phase 9 — Reconciliation: scan ingest, co-report merge, and duplicate detection  · status: todo

#### Work Order

**Goal:** pushing whole-set scans in produces one merged device set — and two reporters reporting one display produce one device.

**Spec:**

Device-as-entity, contract-as-trait-object, state mirrored in a keyed resource:

```rust
// One entity per device. Every component reflected, so BRP sees all of it.
#[derive(Component, Reflect)] pub struct Device;                   // marker
#[derive(Component, Reflect)] pub struct PresentWithUsableClaim;   // exact guarantee
// plus DeviceKey, IdentityVerdict, Presence, Claim, and the capability
// components — which the kernel inserts from DeviceRecord.capabilities
// atomically with the entity. RecoveryPolicy and RoleState are NOT here:
// D1 below puts them on the binding entity, one per bound role.

/// Durable state cannot live only on the entity — keyed retirement must work
/// with no entity alive. The entity mirrors the registry for querying and BRP.
///
/// Keyed by `DeviceId`, not `DeviceKey`: the durable key is two strings, and
/// hashing both on every policy query from application code is the cost that
/// matters. One map resolves a durable key to a handle; everything else is
/// keyed by the copyable handle.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct Devices {
    ids:    HashMap<DeviceKey, DeviceId>,
    state:  HashMap<DeviceId, ReconciledDeviceState>,
    entity: HashMap<DeviceId, Entity>,
    /// Issues `DeviceId`. Monotonic, never reused within a process.
    next:   u64,
}

/// Whether a reported record is a root or is attached beneath another device.
/// This replaces phase 3's domain-owned `Option<DeviceKey>` parent link.
pub enum ReportedTransport {
    Root,
    AttachedTo(DeviceKey),
}

/// Result of resolving one durable key into the current process-local handle.
pub enum DeviceResolution {
    NotResolved,
    Resolved(DeviceId),
}

/// One global revision, folded from every reporter's `ReporterRevision`.
/// Incremented once per reconcile in which **any** reporter returned
/// `DeviceScan::Complete`, whether or not the contents changed.
///
/// Counting completed scans rather than content changes is what makes a rapid
/// `Absent → Present` cycle observable across consecutive reconciles: the set
/// looks identical at both ends, so a content hash would report no change and
/// the panel would stay blank.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct RiggingRevision(u64);

/// In-flight attempts. Issues `AttemptId` from a monotonic counter, never reused.
/// `next` starts at 1, not 0: phase 5 derived `Default` on `AttemptId`, so
/// `AttemptId::default()` is `AttemptId(0)`, and an issued id equal to a
/// defaulted or reflection-round-tripped one would make "a late poll for a
/// finished attempt resolves to nothing" unenforceable.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct Attempts {
    in_flight: HashMap<AttemptId, Attempt>,
    next:      u64,
}

/// One in-flight attempt. Deferred here from phase 5: `permit` is phase
/// 6's token and `rigging_revision` is defined immediately above, so this is the
/// first phase in which the record can compile. It goes in `attempt.rs`
/// alongside phase 5's `AttemptId`/`AttemptProgress`/`AttemptOutcome`, not in
/// `devices.rs` with the registry that holds it.
///
/// `Attempts` above is a reflected resource holding this record, so `Attempt`
/// must be `Reflect` and so must every field type. `deadline` is
/// `bevy_platform::time::Instant` — the only `Instant` bevy 0.19 reflects; on
/// native it is a re-export of `std::time::Instant`, so nothing changes at the
/// call site. Do not use `std::time::Instant` directly: it has no `Reflect`
/// impl and the resource derive fails on it.
#[derive(Clone, Debug, Reflect)]
pub struct Attempt {
    pub id:       AttemptId,
    pub role:     RoleKey,
    pub endpoint: DeviceEndpoint,
    /// The authorisation this attempt was minted under. The kernel mints one
    /// value and both stores it here and hands it to the driver, so there is no
    /// second copy that could disagree. Phase 6 defines it; phase 10 mints it.
    pub permit: ApplyPermit,
    /// The identity this attempt was authorised against.
    /// Re-checked on every poll; a mismatch invalidates it.
    pub expected_device_id: DeviceId,
    /// Global rigging revision at authorisation. A newer revision invalidates.
    /// This is `RiggingRevision`, not `ReporterRevision`: a co-reported device
    /// has several contributing reporters, so one reporter's counter cannot say
    /// whether the topology that made this target valid still holds, and the
    /// driver need not be the reporter whose scan validated it. `RiggingRevision`
    /// is the fold of every reporter's counter (v1.md line 448) and is already
    /// what phase 11 keys reacquisition on. `ReporterRevision` keeps its job —
    /// per-reporter retained-set bookkeeping and freshness — and is not an
    /// authorisation-generation check.
    pub rigging_revision: RiggingRevision,
    /// Bounds the attempt end to end, not per step.
    pub deadline: Instant,

```

**`DeviceId` appears on the entity in exactly one single-field component and nowhere else.** It is BRP-visible there and excluded from the persisted component set; it is carried inside no other type, and `IdentityVerdict` in particular holds no handle. Moonshine serializes reflected components field-by-field without needing `Serialize`, so a `Reflect`-without-serde marker would not prevent persistence — a single named exclusion does, and one component is a thing you can exclude and test.

**Kernel limits are one reflected resource with user-settable fields**, not constants:

```rust
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct RiggingLimits {
    /// How far past `Attempt.deadline` an attempt may keep running before the
    /// kernel abandons it. Bounded overrun rather than a hard cut: a projector
    /// or a camera that is genuinely converging should be given slack, and an
    /// attempt that will never finish must not run forever.
    pub apply_overrun: Duration,
    /// How stale a reporter's last completed scan may be before the kernel
    /// stops trusting it. Past this, that reporter's devices become
    /// `Unreachable` and its in-flight attempts abort.
    pub max_report_age: Duration,
}
```

Both default to values stated in their doc comments and are overridable by inserting the resource before `RiggingPlugin`. Being a reflected resource makes them BRP-tunable at runtime, which is how a slow projector gets diagnosed without a rebuild.

Reconciliation, once per tick in `RiggingSystems::Reconcile`, after phase 7 has admitted and collected whatever discovery work is ready:

1. Drain phase 7's changed-reporter ids and failures. When at least one reporter completed, borrow the latest retained whole set for every contributing reporter from the non-reflected registry; do not call reporters from reconciliation and do not clone their erased capabilities.
2. **Apply the freshness lease before the settled-frame return.** A reporter whose last `Complete` scan is older than `RiggingLimits::max_report_age` is stale: its devices become `Presence::Unreachable`. Staleness is per reporter, so one wedged reporter never invalidates another's devices. A reporter that has never completed a scan is not stale — it is starting up — until its first `Complete` arrives. Phase 11 owns aborting attempts affected by this transition because it owns the attempt lifecycle.
3. **If no reporter completed and no freshness lease changed state, return here.** No allocation, diff, revision bump, or events. This is the common frame — cameras enumerate every two seconds, HID every ten, clerestory only on a display-configuration change — so the settled path costs a loop over reporter timing metadata and lease checks only.
4. Replace `DeviceRecord.transport: Option<DeviceKey>` with `ReportedTransport::{Root, AttachedTo(DeviceKey)}`, then ingest each `DeviceSet` **roots first**, following `AttachedTo` parent links, so the forest is well-formed before presence is folded. Presence is conjunctive down the chain; a parent's departure retires descendants through the keyed path, so nothing depends on a live entity existing.
5. **Merge co-reported devices**, in a **single pass** that groups every reporter's records by key through one `HashMap::entry` — never a pairwise join across reporter lists, which is quadratic in device count. The same pass yields duplicate detection for step 6. Records carrying an **equal `DeviceKey`** from different reporters merge into one device with multiple contributing reporters. One physical display enumerated by both winit and `xcap` is one device, not two. This retires the 200 pt geometry tolerance instead of relocating it, and it works only because `SchemeName` is a shared registry (phase 1): two reporters naming the same scheme are asserting they mean the same identity space.

   The same pass has a second half for records reported as `ReportedAs::MatchEvidenceOnly` (phase 3): they carry no key, so they group by `os_id` against the keyed records already in the map. A match-evidence record that joins to nothing **yields no device** — never a minted key, never a device of its own. This is invariant 3 applied to the merge: a reporter that can recognise a unit but not name it contributes to an existing device or contributes nothing.

   **The `os_id` join is over `OsDeviceId::Reported(_)` and nothing else.** `OsDeviceId` derives `PartialEq` across all three variants (`crates/hana_rigging/src/evidence.rs:11-22`), so two records that each reported *no* handle satisfy `os_id == os_id` and would fuse into one device — exactly the plausible-fallback failure invariant 3 exists to end. A `MatchEvidenceOnly` record whose `os_id` is `PlatformHasNoConcept` or `PlatformReportedNothing` joins nothing and yields no device, the same as a `Reported` handle that matches nothing.
6. **Duplicate keys within one scan disqualify each other.** Every member of a duplicate set becomes `Unverified(NotUniqueInScan)`. This is where the rule that two unidentified units never match each other is enforced: matching runs over keys and evidence, and a record whose verdict is `Unverified` is never a match candidate for another. It is what stops a weak scheme — two identical webcams under one device name — from presenting as `Proven`.

### Phase 11 — Attempt lifecycle, retries, and escalation  · status: todo

#### Work Order

**Goal:** the kernel starts, bounds, re-validates, retries, and escalates attempts.

**Spec:**

1. A `WaitingRole` on a managed device may begin only after authorization. In-service permission selects `RequestedConfiguration`; restore-only permission requires `LastKnownGoodConfiguration::Known` and selects that value. `NotEstablished` means there is nothing to restore, so the role stays waiting. The view transitions the binding to `Applying(AttemptId)` and mints the only `StartApplyRequest` accepted by `Drivers::start_apply`; the driver starts and returns immediately. An offline inventory entry cannot mint this request under either authorization path.
2. Every tick, only an `ApplyingRole` can mint the `PollRequest` accepted by `Drivers::poll`. **Before** minting it, re-check `Attempt.expected_device_id` against the current `DeviceId` and `Attempt.rigging_revision` against `RiggingRevision`. A mismatch invalidates the attempt before any driver poll — it never lands on a different unit. If a device is switched to offline while an attempt is already running, abort it and never poll again.
3. `Attempt.deadline` bounds the attempt **end to end, not per step**, so a driver that must reset then render has both steps inside one attempt with one settle result and cannot report done between them. Past the deadline `Attempts::is_overdue(id, now)` returns true while the state stays `Applying(AttemptId)` — being overdue is not an error and not a failure, so `poll` keeps being called. Past `deadline + RiggingLimits::apply_overrun` the kernel stops asking and finishes the attempt `Aborted`. That is the bounded-overrun rule: slack for a device that is genuinely converging, a ceiling for one that never will.
4. Abandonment follows the kernel rule table from phase 4: claim lost ⇒ never revert; service vetoed ⇒ never revert; revision changed ⇒ consult `OnAbort`.
5. Retry is gated by `RetryOn`. `AttemptOutcome::Aborted` is terminal and never auto-retries.
6. Repeated-failure escalation counts **consecutive attempts, not frames** — that is why it is kernel work and arrival evidence is not — and **self-clears on recovery**.

`Succeeded` and `Substituted` finish through `ApplyingRole`, remove the attempt, and transition the binding to `Ready`. They do **not** copy the requested or restore target into `LastKnownGoodConfiguration`. On the next reconcile, phase 10's `ReadyRole` capture path reads back what actually landed and writes `Known`; until that safe read succeeds, the previous last-known-good value remains unchanged. ### Phase 17 — clerestory persisted window state v3 → v4  · status: todo

#### Work Order

**Goal:** a v3 window-state file loads, restores its windows to the same physical monitors, and is rewritten as v4 with classified keys. **This is gate G8.**

**Spec:**

Conservative conversion with self-heal. Per-version frozen structs: the v3 shape is copied into a `v3` module and frozen there, the v4 shape is the live one, and the conversion is a plain function between them. This is the `windows.ron` `version: 2` pattern grown up.

Conversion rules:

- A v3 entry whose monitor identifier can be classified as reported becomes `DeviceIdSource::Reported { scheme, value }`.
- A v3 entry whose identifier cannot be classified becomes `Synthesized { digest }` — which yields a `RestoreOnly` verdict at runtime, meaning the window still returns to its monitor and still never drives output. That is the correct conservative outcome, not a degradation.
- **Self-heal:** an entry that cannot be converted at all is dropped with a logged warning rather than failing the load. A show that will not open is worse than a window in the wrong place.
- The file is rewritten as v4 on the next save, not eagerly on load.

Do not attempt to make `CGDirectDisplayID` durable across reboots — phase 14 settled that it is a within-run join key and never a persisted one, and the conservative conversion is what makes an old file holding one survivable.

Which tier a v3 entry converts into depends on phase 14's platform investigation: it decides which schemes exist, so it must be finished before the conversion is written. A v3 entry recording a value from a scheme the investigation did not establish is unconvertible and takes the self-heal path.

### Phase 26 — Stream Deck device thread, enumeration, and claim  · status: todo

#### Work Order

**Goal:** the Stream Deck + unit in hand enumerates as a kernel device, is claimed, survives replug, and classifies its failures.

**Spec:**

This is the only genuinely new code — enumeration, claim, reconnect, and error classification, with nothing to copy. It is also the only multi-slot consumer, which is why it is an acceptance target and not a feature.

Constraints the HID survey fixes:

- **One model only: the Stream Deck +**, which is the unit on hand. `Original 0x0060` and the Mini family are separate protocols, one undocumented by Elgato; scope to the + and let the abstraction prove itself on the *second* model rather than the first. Shape the crate around **protocol families** (~6 of them), not the 17 product ids — a Corsair keyboard runs the Stream Deck gen2 protocol, so protocol ≠ vendor.
- **Read the slot counts off the device descriptor, never from a constant.** The + is documented by Elgato as 8 LCD keys (2×4), 4 push-turn dials, and a touch strip above the dials; hana's operator recalls 4 keys and 4 dials. The enumeration step settles this by measurement: whatever `elgato-streamdeck` reports for the connected unit is the slot count, and a hardcoded 8 or 4 that disagrees with the hardware is a defect either way. Record what the device actually reports in this phase's notes.
- **No tokio.** `elgato-streamdeck`'s `async` feature pulls tokio and the workspace has none. Register enumeration as an optional, initially disabled `DiscoveryCadence::Periodic { interval: Duration::from_secs(10) }` reporter; each due run returns a kernel-managed `DiscoveryWork::Background` closure using the blocking enumerate API on `IoTaskPool`. Phase 7 prevents duplicate jobs, leaves one I/O thread outside discovery when the pool permits, and coalesces a missed interval. New dependencies: `elgato-streamdeck` (brings `hidapi` and `image`) plus `crossbeam-channel`.
- **The owned operational device thread is not optional, but it is not the discovery scheduler.** `HidDevice` is `!Sync`, no OS event stream exists because the usage page is vendor-defined, and Elgato's recommended input poll is 50 ms. Once the managed driver is authorized, one integration-owned thread owns the claimed handle, channels carry commands/input in and reports out, a `PreUpdate` system drains, and `AppExit` releases. Offline inventory and passive discovery never start this thread.
- **Presence is polled, never notified.** There is no hot-plug anywhere in the hidapi stack; re-enumerate on a timer and treat a read-loop error as the disconnect signal.

Device facts this integration crate must handle:

1. **Sleep/resume is a distinct failure mode from unplug** and fires constantly on laptops. On host suspend the HID handle breaks and must be closed and reopened with a full re-render. This is an **integration-crate concern with no new kernel state**: a crate that knows its handle is dead reports `Absent`, then `Present` on reopen, and the normal reacquire path runs. The full re-render is free, because `RecoveryPolicy::ReapplyOnReturn` re-applies the last intentional configuration — which for a panel *is* the key images.
2. **The identity token can change under us.** Stream Deck serials have been observed mutating across replug, and serial length changed 12→14 across a firmware revision. That is the `Displaced` verdict. v1 emits `IdentityChanged` (phase 12) and logs; a human replugs. Adopting the candidate rewrites the saved key and is **deferred**; see the deferred register.
3. **Post-claim reset is a driver obligation the kernel already compels.** On open, a zeroed reset report must be written to abort a half-finished image transfer left by a *previous owner* — presence does not imply pristine, and the previous owner may have been another process or a crashed run of hana. `start_apply` is specified as absolute, not differential, so this is how one driver discharges an obligation every driver has. The end-to-end deadline means reset-then-render sits inside one attempt with one settle result.
4. **Claiming is a contest with no good outcome.** hidapi seizes by default on macOS, and a seizing open *succeeds* over the already-running Elgato app while silently disabling its input queues. Contention is the **normal operating state, not an error**, and "we opened it" does not mean "we should have". Report `Claim::Contended` where it can be detected; where it cannot, that is a known producer weakness, not a reason to guess.
5. **Every transport failure arrives as one opaque string** — contention, unplug, and permission denial all surface as `HidError::HidApiError { message }` wrapping a hex `IOReturn`. Classify into `DeviceAccessError` and keep the raw string as driver detail. This is the second device kind to land in the same hole that produced `VIDEO_UNAVAILABLE_LIKELY_CAUSE`.
6. **A blocked device is indistinguishable from an absent one.** On Apple-silicon laptops the "Allow accessory to connect" prompt makes a denied device simply not enumerate, so `Claim::Blocked` is only inferable from *history* — we hold a saved key, the platform has a permission gate, and nothing matching enumerated. That inference needs the durable `DeviceKey`.

Resolved and worth not re-litigating: **Input Monitoring TCC does not apply.** Apple's kernel gates only Keyboard, Mouse, and TouchPad usages; the Stream Deck is a Consumer-page device, so unsigned `cargo run` reaches it with no entitlement and no prompt.

**Files:**
- `crates/hana_streamdeck/` (Repo A) — new kind crate: `Cargo.toml`, device thread, enumeration, claim, fault classification, `DeviceReporter` and `EndpointDriver` impls. The manifest inherits workspace metadata, carries `[lints] workspace = true`, and depends on `hana_rigging.workspace = true`
- `Cargo.toml` (Repo A workspace root) — add `hana_streamdeck = { version = "0.1", path = "crates/hana_streamdeck" }` to `[workspace.dependencies]`. There is no `members` edit: Repo A's `members` is the glob `["crates/*"]`, so the new directory is a member already

**Constraints from prior phases:** Phases 1–12 built the kernel and phase 25 proved it against two real integrations. Register `"usb-serial"` through phase 6's app extension. Reporter enumeration and endpoint driving are separate registrations; phase 7 owns the ten-second enumeration cadence and I/O-pool admission, while the integration-owned handle thread begins only after phase 10/11 authorization. Phase 8 offline mode must leave enumeration passive and prevent that thread from opening. Retain both issued ids and give the driver reflected component configuration. Existing verdict, claim, and access-fault types need no widening. The crate must ship real tests because the scoped test gate rejects an empty package.

### Phase 27 — Stream Deck slots, rendering, and transport wiring  · status: todo

#### Work Order

**Goal:** LCD keys, push-turn dials, and the touch strip are addressable slots on one device, and a key press drives a hana transport action.

**Spec:**

This is where `DeviceEndpoint`/`EndpointId`/`PartName` gets its only v1 exercise. One device, many named parts: `"key/3"`, `"dial/1"`, `"strip"` — each an `EndpointId::Part(PartName::new(..)?)`, never a bare string, since `PartName` is a checked newtype. `PartName` vocabulary is reporter-owned and opaque to the kernel, and the part count comes from phase 26's enumeration, never from a constant. This is also what dissolves "input device that is also a render target" — one device, many parts, bound twice by two kind layers.

Outbound feedback is several distinct channels — key images, the touch strip's own image region, and on other models per-key RGB and LED rings — and an input channel need not be a control at all: on the Studio the NFC reader shares the button report stream, which is why the slot vocabulary must not assume every slot is a control.

**Dirty-tracking and a rate limit from day one.** A full-panel refresh is ~96–288 blocking USB round-trips, each with a JPEG encode, and the **encode rather than the bus** is usually the bottleneck. Writes also need spacing: node's shipped stack serializes through a concurrency-1 queue with a 1 ms gap, commented *"some streamdecks get upset with too many reports in quick succession."* Issued from a Bevy system this blocks the frame; issued from the IO pool it competes with asset streaming. Track dirty slots and rate-limit.

## Post-phase review decisions

Findings from the phase dual reviews that changed the plan rather than the code under review. Each entry records the decision, not the deliberation.

- **A — `verify.sh` strictness is global.** The shared delegate verifier hard-errors when nightly `rustfmt` or `cargo nextest` is missing, for every repository that uses it, with no per-repo opt-in. Invariant 13 is enforced machine-wide. The edit lives in `~/.claude/scripts/delegate/verify.sh` and is outside every phase commit.
- **B — G10's registration half is enforced in phase 9, not phase 1.** Phase 1 has no boundary where keys enter, so `RegisteredSchemes::validate` ships as a checked method with unit coverage and nothing calls it. Phase 9's ingest path is the first place an unregistered name can actually fail, and its acceptance gate now carries that requirement. Phase 1's acceptance line was corrected to state what it verifies rather than asserting a startup check that does not exist.
- **C — the validated newtypes are opaque to reflection.** `SchemeName`, `ReportedId`, and `Digest` carry `#[reflect(opaque)]`, so reflection treats each as one atomic value routed through the registered `Serialize`/`Deserialize` rather than exposing its private field. Without it, any reflection writer — remote inspection, scene load — sets the inner string directly and bypasses the checked constructor, which is the same hole G10's hand-written `Deserialize` closes for persisted text. `Digest` gains nothing but is included so the three identity wrappers behave alike. Field-level reflection access to the inner values is given up; nothing uses it.
- **D — `DeviceId` keeps `#[reflect(Component)]`; exclusion is enforced at the save path.** Entity saving runs through reflection rather than serde, so the absence of serde on `DeviceId` does not by itself keep it out of saved output — the save builder must deny it. That requirement already sits in phase 10's acceptance gate. Dropping the component reflection registration would make the exclusion structural but would also hide the handle from live inspection, which is the primary view for diagnosing why one physical device drew two handles.

## Deferred register

Nothing here ships in v1 and none of it is a phase. Each item names the condition that unblocks it. Phases 1–28 must not pre-build any of it: shipping a type with no consumer is correct only when adding it later would force an audit of existing call sites, and no item here meets that bar — `ServiceVeto` is one axis inside `Devices::authorize_service()`, a declared safe state is one axis on one enum, `Cohesion` attaches to a group that does not exist yet.

- **`Cohesion`** — `enum Cohesion { None, SameDevice, SameHost }`, checked by the kernel and never explained to it, covering the one-interface-one-machine constraint for a speaker group and a laser array on one DAC. Deferred because no v1 device has a cross-device grouping constraint and the only reachable value is `None`. **Trigger:** the first multi-device group. Purely additive — it attaches to a group, not to any existing type.
- **Reassignment** — re-binding N entities to a swapped unit. Deferred because no v1 kind does it; `DeviceEndpoint` keeps it expressible. **Trigger:** the audio work, or a Stream Deck replaced mid-show.
- **`Unreachable` decay timing** — when an `Unreachable` device becomes `Absent`. Deferred because there are no remote nodes in v1, so the kernel treats `Unreachable` as not authorized in service and **never auto-decays**. **Trigger:** the first Art-Net or networked node.
- **`Displaced` adjudication** — who answers a `Displaced` verdict, and whether an unanswered one survives restart. v1 emits `IdentityChanged` and logs; a human replugs. Adopting the candidate rewrites the saved key, which is what the mutating-serial bug needed and did not have. **Trigger:** a UI that can ask.
- **Attachment path as a stored third evidence axis.** The *evidence* question is closed — AVFoundation's `uniqueID` is a USB location id, so a port-derived value is attachment evidence carrying a `Synthesized` key, and phase 3 keeps it on the record as `AttachmentPath`. What stays deferred is giving it **its own stored axis** at rest. It must never be merged into `DeviceKey`. **Trigger:** a case where port position must be queried independently of identity.
- **The associated-type `Identified` trait.** Write it only when two *implemented* load paths share a batch-resolve-validate-publish body **with compatible failure policy** — all four conditions: both hold deserialized durable references aside unpublished; both resolve a whole batch against current registries; both validate cross-references across the batch; both publish atomically with compatible failure policy. Condition 4 fails today on purpose: a missing device is normal operation, a missing tool definition aborts the load. Then extract only the interface that body calls.
- **`DeviceKey` document persistence.** Rigging produces durable keys in v1 and serde is all it commits to; the document format waits on [[versioned save format]]. Rigging must not block on another in-progress issue.
- **`ServiceVeto`, the safety veto** — the type itself, not just its producer. Not built in v1: no interlock device exists, so the shape would be unvalidated and unexercised. **Trigger:** the first laser or interlocked fixture. Adding it is a fourth axis inside `Devices::authorize_service()`, the sole in-service decision point, plus one enum. Breaking for crates.io consumers, which the exhaustive-enum policy accepts.
- **A declared safe state** — again the type itself. Not built in v1: no v1 device has a declared safe state, and the erased `Box<dyn Reflect>` field it needed broke the `Reflect` derive, `Clone`, and the unrepresentable-illegal-state property. **Trigger:** the first light rig or projector with a required return state. Adding it arrives as a separate declared-state axis beside `RecoveryPolicy`, over the same erased-value mechanism the capability components use, never as a payload on the policy enum. Departure application stays driver-executed; the kernel never drives a device to a safe state itself.

### D1 — per-binding state is projected onto the device entity (3 reviewers)

Retention policy, recovery state, and captured configuration belong to a
*binding*, but phase 9 mirrors them onto the *device* entity and phase 10 defines
`Devices::phase(&DeviceKey)`. A Stream Deck with several slots has several
bindings with different policies and different attempts; one component of each
type on one device entity cannot hold them, so insertion is last-write-wins and
`phase(&DeviceKey)` has no correct answer to return. `ApplyFinished` also cannot
reliably target the device entity, since device departure aborts attempts after
that entity may be despawned.

Fix: one entity per registered binding carrying its policy, state, and
configuration mirror; the device entity keeps only per-device facts (`DeviceId`,
`DeviceKey`, identity verdict, presence, claim, capabilities). Recovery and
attempt events target the binding entity. One reviewer additionally proposes a
normative cardinality/authority table in Delegation Context — for each value: what
key sets its cardinality, which store is authoritative, who produces it, how
co-reports combine, where it is mirrored, how changes are compared.

**This resolves phase 9's open decisions on where mirrored policy and recovery
components sit and which copy is authoritative.** Cost: one ECS entity per
binding, and a value is no longer reachable from a single entity.

**Decision: approved 2026-07-31 — split into device and binding entities, with the ownership table.**
One entity per registered binding carries its retention policy, state, and
configuration mirror; the device entity keeps only per-unit facts (`DeviceId`,
`DeviceKey`, identity verdict, presence, claim, capabilities). Recovery and
attempt events target the binding entity, not the device entity. Delegation
Context gains a normative table naming, for every value, its cardinality key,
authoritative store, producer, co-report merge rule, mirror location, and
comparison rule. Phase 9's pending decisions on where mirrored policy and
recovery components sit and which copy is authoritative are settled by this and
are to be deleted. `Devices::phase(&DeviceKey)` is replaced by a binding-keyed
accessor. Work Order edits land after the naming decisions (D3, D4) settle, so
the new types are written once under their final names.

### D2 — rename the `Apply*` record family to `Attempt*` (4 reviewers, unanimous)

`Applys`→`Attempts`, `ApplyFinished`→`AttemptFinished`, `apply.rs`→`attempt.rs`,
`ApplyOutcome::Done`→`Succeeded`. `DeviceProvider::apply` and `RiggingSystems::Apply`

**Decision: approved 2026-07-31 — rename the record family, keep the verbs.**
`Apply`→`Attempt`, `ApplyId`→`AttemptId`, `ApplyProgress`→`AttemptProgress`,
`ApplyOutcome`→`AttemptOutcome`, `Applys`→`Attempts`,
`ApplyFinished`→`AttemptFinished`, `apply.rs`→`attempt.rs`, and

### D3 — what replaces `RigKey` (fork)

"Rig" reads as a hardware assembly, but this type names an application role that
owns a binding — a window, a camera slot, a Stream Deck key. `RetireRig` sounds
like retiring hardware when it removes an authored binding. Candidates:
`BindingKey` (two reviewers — reads directly against `Bindings::register/replace/
retire/get`), `RoleKey` (one — the doc comment already defines it as a role), or
keep `RigKey` (one reviewer renames the state enum but leaves the key). All agree
`hana_rigging`, `RiggingPlugin`, and `RiggingSystems` stay. The choice carries
`Binding.rig`, `RetireRig`, `RigAwaiting`, `RigAvailable`, and `rigs_for`.

One reviewer adds a separate mechanical point: `Bindings::replace(RigKey, Binding)`
takes the identity twice, since `Binding` already holds it — the argument and the
field can disagree.

**Decision: approved 2026-07-31 — `RoleKey`.**
`RigKey`→`RoleKey`, `Binding.rig`→`Binding.role`, `RetireRig`→`RetireRole`,
`RigAwaiting`→`RoleAwaiting`, `RigAvailable`→`RoleAvailable`,
`rigs_for`→`roles_for`. `hana_rigging`, `RiggingPlugin`, `RiggingSystems`,
`RiggingLimits`, and `RiggingRevision` are unchanged. Also mechanical:
`Bindings::replace(RigKey, Binding)` takes the identity twice — it becomes
`replace(Binding)` with `binding.role` as the only key.

**The model, in the author's own words — use this vocabulary in doc prose and
doc comments from here:** devices can do one or more things (a Stream Deck
button, a mixer slider); the device has an id and the thing it can do has an id;
the pair is *current* and transient, because the device can be swapped while the
same job still needs doing; the job is an application-defined **role**; a
**binding** connects a role to that device-id/capability-id pair at runtime.

**Decision (D3b+c): approved 2026-07-31 — `DeviceEndpoint` + `EndpointId`, and
`EndpointId` becomes a two-variant enum.** The author proposed both the composite
name and the enum; no reviewer raised either.

```rust
pub struct DeviceEndpoint {
    pub device: DeviceKey,
    pub id:     EndpointId,
}

pub enum EndpointId {
    /// The device itself — it has no addressable parts.
    Whole,
    /// One reporter-named part within the device: `ch/7`, `key/3`, `nfc`.
    /// The kernel never interprets the name.
    Part(PartName),
}
```

`EndpointRef`→`DeviceEndpoint`; the shipped checked newtype `Slot` becomes
`PartName`, keeping its blank/control-character validation and its
`#[reflect(opaque)]` treatment. Shipped `Capabilities` is untouched — it
legitimately owns the word "capability" for reflected components describing a
device, and `EndpointId` addresses a part of one, which is a different level.

**The variant rule, which is the point of the enum:** `EndpointId` asks one
*structural* question — does this device subdivide? — which is answerable for any
device that will ever exist. Variants must never name device classes
(`Monitor`, `StreamDeck`, `Mixer`): that would put a device catalogue inside the
kernel, and since the enum is public and exhaustive, every new class would be a
breaking release for external integration crates. `Whole` exists so displays and
cameras stop inventing an arbitrary slot string by convention.

`Whole` is not an exclusivity claim — two roles may both bind `Whole` on one
display (a window role and a colour-profile role). `Claim` remains the only
exclusive-ownership mechanism.

`DeviceEndpoint` is serialized and durable, so this shape is settled before any
configuration exists rather than migrated later.

### D4 — `RecoveryPhase` is misnamed and partly derivable (4 reviewers)

`Nominal` and `Retired` are not recovery phases; `Recovering` hides that a
driver is applying configuration; `AwaitingDevice` is also used when the device
is present but contended; and `PastDeadline` changes no behavior, since polling
continues exactly as in `Recovering`. The name also collides with this document's
own implementation phases. All four rename it after the thing it describes
(`BindingState` / `RoleState` / `RigState`) with `Nominal`→`Ready` and
`Recovering`→`Applying`. Forks: drop `PastDeadline` and expose overdue as a
computed check on the attempt (two reviewers) or keep it renamed `Overdue` (two);
drop `Retired` as duplicating absence from the registry (one) or keep it (three).

**Decision: approved 2026-07-31 — `RecoveryPhase` becomes `RoleState`, four variants.**

```rust
pub enum RoleState {
    Ready,
    Waiting,               // no device, or present but contended / policy-gated
    Applying(AttemptId),
    Retired,
}
```

`Nominal`→`Ready`; `AwaitingDevice`→`Waiting` (the old name asserts absence, but
the state is also used when the device is present and contended or
policy-gated); `Recovering(_)`→`Applying(_)`; `PastDeadline` **deleted**.
`RecoveryPhaseChanged`→`RoleStateChanged`.

`Applying`, not `Attempting`: D2 kept `apply` as the action verb and `Attempt` as
the record, so the in-progress state uses the verb and carries the record's id.
`Attempting(AttemptId)` stutters and says less.

`PastDeadline` is dropped because crossing a deadline changes nothing about
handling — polling continues identically — yet as a stored state the crossing
writes a component and fires a transition event while the reporter still reports
`Pending`. Overdue becomes one comparison against the attempt's deadline
(`Attempts::is_overdue(id, now)`). Accepted loss: no event fires at the moment a
deadline is crossed, so a consumer wanting "this is taking longer than expected"
polls the check instead of reacting.

`Retired` is kept. It is a tombstone — retired *by key*, and later presence must
not revive it — so it has to outlive the registry entry; deleting the variant
only moves the tombstone elsewhere.

### D5 — one authorization enum, not two (4 reviewers)

`ApplyKind` and the private `ApplyAuthorization::Purpose` both record `Arm |
Restore`, and this plan currently requires `is_arm()` to agree with
`ApplyKind::Arm` — a runtime consistency requirement for a bit the kernel mints in
one place. One reviewer also notes the stated purpose does not hold: comparing the
two can only prove the kernel copied its own bit correctly, never that the
driver honored it. Shapes proposed: delete `ApplyKind` and let the token be the
sole carrier; one `AuthorizationScope { DriveOutput, RestoreOnly }` used in both
places with `is_arm()`→`permits_output()`; `ApplyAuthorization(AttemptKind)`
keeping the public enum; or delete `ApplyKind` and store the token itself on the
attempt as `Copy + Reflect`.

**Decision: approved 2026-07-31 — one authorization value, `Result` instead of
`Option`, and the "arm" vocabulary retired throughout.**

The Arm/Restore bit is written once, not twice. `ApplyKind` is **deleted**; the
attempt record stores the authorization value itself (`Copy + Reflect`), so
nothing can disagree with anything and BRP still shows which authorization an
attempt ran under. The plan's claim that keeping both lets the kernel name a
driver that drove output under a restore token is **struck**: both copies
record what the kernel authorized, never what the driver did.

`arm` is removed from the crate's vocabulary — including the doc comments already
shipped in `verdict.rs:47,55,101,124`, `policy.rs:28`, and `capabilities.rs:71`
("disarms"). It reads as *made ready but not yet acting*, which is the opposite of
what it meant here. `output` was rejected as its replacement because half the
fleet is input-only — a knob and a camera take input; the axis is whether the
device is doing its real job for the application, not which direction data flows.

| was | is |
| --- | --- |
| `Devices::armable(id) -> Option<ApplyAuthorization>` | `Devices::authorize_service(id) -> Result<ApplyPermit, ApplyAuthorizationError>` |
| `Devices::restorable(id) -> Option<ApplyAuthorization>` | `Devices::authorize_restore(id) -> Result<ApplyPermit, ApplyAuthorizationError>` |
| `ApplyAuthorization` | `ApplyPermit` |
| private cases `Arm \| Restore` | private cases `InService \| RestoreOnly` |
| `is_arm() -> bool` | `allows_in_service_use() -> bool` |
| `Apply.kind: ApplyKind` | deleted; the attempt stores the `ApplyPermit` |
| deferred `Arming` veto | deferred `ServiceVeto` → `ApplyAuthorizationError::ServiceVetoed` |
| prose "arming" / "disarms" / "unarmable" | "in-service" / "blocks in-service use" / "not authorized in service" |

```rust
pub enum ApplyAuthorizationError {
    NotPresent,
    Contended,
    IdentityNotProven,
    CapabilityDisagreement,
    // ServiceVetoed — when the deferred veto axis lands
}
```

`Result` replaces `Option` because the denial reason is already computed inside
the predicate and `None` discards it — exactly when a user is asking why a device
will not come up. `Result` rather than a hand-rolled two-variant enum: same shape,
and `?`/`is_ok`/`map` already work. Cost accepted: one new public enum, callers
match instead of `if let Some`, phase 9 and phase 11 gates each gain items proving
every denial reason comes back correctly. It also makes the deferred veto a new
variant rather than a new signature.

The function names are verbs that grant, not verbs that act: `authorize_service`
does not put anything in service — the driver does that later, when called with
the value. `authorize_service`/`authorize_restore` were preferred over
`put_in_service`/`restore` for that reason, and over `authorize_operation` because
`InService` reads correctly for a knob nobody is turning.

`RestoreOnly` intentionally reuses the word from the shipped
`DeviceIdentity::RestoreOnly` verdict (`crates/hana_rigging/src/verdict.rs`) —
different type, and that verdict is what *causes* this case.

### D6 — `DeviceFault` overlaps `Claim` and `Presence` (3 reviewers)

Its required cases — contention, permission denial, absence, transport failure —
already have current-state homes in shipped `Claim::Contended`, `Claim::Blocked`,
and `Presence::Absent`. Making it a device component creates two current answers
for three conditions, with no authority rule and no clearing rule; `armable` could
see `Presence::Present` beside a fault meaning absence. Phase 9 already omits it
from the component list and phase 12 defines no transition event for it.

All three agree it should be a *historical result payload* only —
`CaptureOutcome::ReadFailed`, `ApplyOutcome::Failed`, and completion events — and
should come out of the entity-component invariant. Fork on name:
`DeviceAccessError`, `OperationFailure`, or keep `DeviceFault`. Independent of the
name, one sub-answer is clearly right and all three support it: name the variants
with the shipped vocabulary — `Contended`, `Blocked`, `Absent`, `Transport` — so
the same condition is not spelled two ways.

**Decision: approved 2026-07-31 — history-only payload, renamed
`DeviceAccessError`, variants spelled with the shipped words.**

The type never becomes a component and never sits on a device entity. It appears
only as a payload on something that already happened and cannot change:
`CaptureOutcome::ReadFailed`, `ApplyOutcome::Failed`, and completion events.
Current state stays where it shipped — `Claim::Contended`, `Claim::Blocked`,
`Presence::Absent` — so the entity carries one answer per question. It is removed
from the entity-component invariant.

Concrete failure this avoids: presence is maintained by scanning and flips back to
`Present` when a unit is replugged; a fault component saying *absent* is
maintained by nobody and never clears, leaving `authorize_service` and a
diagnostic panel reading two different real states.

`DeviceFault` → **`DeviceAccessError`**. "Fault" reads as *the device is broken*,
but three of the four cases are not the device's doing — another app holds it, the
OS refused, it is unplugged.

Variants reuse the shipped vocabulary exactly: `Contended`, `Blocked`, `Absent`,
`Transport`.

```rust
ApplyOutcome::Failed(DeviceAccessError::Contended)
CaptureOutcome::ReadFailed(DeviceAccessError::Transport)
```

`DeviceAccessError` stays **separate** from D5's `ApplyAuthorizationError` even though both
carry a contention and an absence case: `ApplyAuthorizationError` is the kernel declining to
start, `DeviceAccessError` is a failure after starting. Merging them would force
each site to accept variants that cannot occur there. Where the two coincide the
spelling is identical, so `Contended` means one thing crate-wide.

### D7 — `Captured` / `Requested` (4 reviewers, and one real bug)

All four want the adjectives completed: `LastKnownGoodConfiguration` and
`RequestedConfiguration`, since as signatures `Captured` and `Requested` do not
say whether the value is configuration, evidence, or an endpoint.

**The bug:** `Requested` and `Captured` hold the *same* driver `Configuration`
type, and a Bevy entity can hold only one component per type. Phase 8 promises a
projection for the requested value and phase 10 step 10 now mirrors the captured
one, so on one entity the second insert silently overwrites the first and BRP
shows whichever landed last. Fix: mirror only one of them — the captured value —
and drop phase 8's projection promise; `Bindings` stays authoritative for the
requested value.

**Decision: approved 2026-07-31 (D7a) — nouns restored, and only the captured
value is mirrored.**

`Captured` → `LastKnownGoodConfiguration`; `Requested` → `RequestedConfiguration`. As
signatures the bare adjectives never said what they were adjectives of.

**Bug fixed.** Both hold the driver's own `Configuration` type, and a Bevy entity
holds one component per type — so phase 10 step 10's captured mirror and phase 8's
promised requested projection would insert the same Rust type onto the same
entity, the second silently overwriting the first, with the winner decided by
system order. **Only the captured value is mirrored.** Phase 8's projection
promise is deleted; `Bindings` remains the authoritative home for the requested
value, which is already readable there. Wrapping one side in a distinct type was
rejected: the mirror resolves the driver's registered settings type through
`ReflectComponent`, so a wrapper needs its own reflection registration per
driver type — real machinery to surface a value that is already reachable.

**Decision: approved 2026-07-31 (D7b) — `Writable`/`Frozen` deleted; refresh
eligibility is derived where it is asked.**

`LastKnownGoodConfiguration` is the value alone, with no lifecycle tag. The kernel
decides whether a live re-read is safe at the single site where it calls
`capture`, reading `Presence` and the attempt registry directly — the only place
the question is ever asked, and it cannot be stale there because it is computed on
the spot.

Both variants held identical payloads and differed only by situation the kernel
already knows authoritatively. Named failure: a device tagged `Writable` while
present then departs, nothing flips the tag because flipping it is nobody's job,
and on return a live read overwrites the retained intent the copy existed to
preserve. Same defect class as D6.

Accepted cost: freezing stops being visible in the type. It becomes a precondition
in one kernel system plus a doc comment on `capture` — which is where it already
lived, since `capture`'s comment said "called only while `Writable`" rather than
the compiler enforcing it.

### D8 — `Availability` and `Act` are badly named (3 reviewers) · **shipped code**

This is phase 4, already committed, so it is a revision rather than a plan edit.
`Availability` reads as current device usability, which `Presence` and `Claim`
already own; it actually controls configuration *retention and reapplication*.
`Availability::Unregistered` sitting inside a registered `Binding` is the sharpest
case: registry membership already answers that question, so the model states it
twice and a caller can build a registered binding whose policy says unregistered.
`Act` says nothing about reapplication on its own, and
`Availability::Retained(Act::OnReturn)` makes a reader learn two generic words for
four fixed states.

**Decision: approved 2026-07-31 — `Availability` and `Act` are replaced by one
flat `RecoveryPolicy`.** This is a revision to committed phase 4.

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug, Default, Component, Reflect)]
#[reflect(Component)]
pub enum RecoveryPolicy {
    /// Don't keep this device's configuration when it goes away.
    #[default]
    Forget,
    /// Keep it, but never send it back on its own.
    Retain,
    /// Keep it; send it when application code asks.
    ReapplyOnRequest,
    /// Keep it; send it automatically once the returning unit is verified.
    ReapplyOnReturn,
}
```

Same four states, no illegal ones, no nesting — `Act` is deleted. `Forget` and
`Retain` say retention outright instead of borrowing "registered" for it, which
removes the contradiction of an `Unregistered` policy inside a registered
`Binding`. The type becomes `Copy`; it was `Clone`-only solely because of the
nesting, so **phase 5's constraint line saying `Availability` is deliberately not
`Copy` must be rewritten.** "Recovery" is available because D4 renamed
`RecoveryPhase` to `RoleState`.

Files affected: `crates/hana_rigging/src/availability.rs` (type, doc comments, and
its three tests, including `device_components_register_reflection_metadata`),
the crate-root and `prelude` export lists in `crates/hana_rigging/src/lib.rs`, and
every plan reference to `Availability`/`Act`.

### D9 — split `DeviceProvider` into a reporter half and a driver half (1 reviewer)

`DeviceProvider` combines reporting a whole device set with driving one endpoint.
The monitor reporter only scans; the window driver mostly captures, applies, and
polls; both must implement everything, and no-op methods end up inside the safety
boundary. `ProviderId` consequently means both "who reported this fact" and "who
receives this request", which can be different implementations for one display.
**Decision: approved 2026-07-31 — split into `DeviceReporter` and
`EndpointDriver`.**

```rust
trait DeviceReporter { fn scan(&mut self, world: &mut World) -> DeviceScan; }

trait EndpointDriver {
    type Configuration: Reflect + Component;
    fn capture(..); fn start_apply(..); fn poll(..);
}
```

Registration issues a `ReporterId` and a `DriverId`; a dual-role crate registers
twice. Accepted cost: one more registry and one more id type in the kernel.

Grounds: in the v1 fleet the screens reporter reports and drives nothing, the
clerestory window driver drives and reports nothing new, and only the camera
crate does both — so two of three implement half the trait as no-ops. One of
those no-ops is `start_apply`, the method that receives D5's `ApplyPermit`: a
scan-only implementation would ship a function that accepts a kernel-issued permission
slip and discards it, inside the safety boundary. The single trait also forces
every implementer to name a `Configuration: Reflect + Component` type and register
its reflection even when it never applies anything.

It also separates the two questions `ProviderId` currently conflates — who
reported this fact versus who receives this request — which are different
implementations for one display.

Timing: `DeviceProvider` is phase 6 and unbuilt, so this is a plan edit now and a
public-trait break later.

The pending decision at "how a provider crate obtains its `ProviderId`" resolves
under this split: only reporters advance revisions, so the counter belongs to the
reporter registry. Resolve it there, not here.

### D10 — do not erase driver configuration at all (1 reviewer) · **conflicts with a decision already made**

This session settled that the erased field is `#[reflect(ignore)]` and the payload
is inspected at the driver's own type through a `ReflectComponent` mirror. One
reviewer argues the erasure itself is the cost: unlike `Capabilities` — where the
kernel genuinely must union an open set of component types — parameters always
return to one known type per driver, so erasure buys a heap allocation per
value, fallible downcasts on a normal data path, an ignored reflection field, a
`FromReflect` accommodation, a `Component` bound demanded solely for diagnostics,
and reconciliation-time component churn. It proposes registration returning a
typed `ProviderHandle<Configuration>`, typed maps inside the provider adapter, and
deleting `Requested`, the downcast errors, the `Component` bound, and the mirror;
a driver wanting BRP visibility publishes its own component. What is lost is
automatic kernel-wide parameter inspection — which is exactly what was approved
this session. Flagged rather than acted on.

**Decision: rejected 2026-07-31 — erasure and the captured-value mirror stay,
with one refinement adopted.**

The listed costs are paid at reconcile cadence, not per frame: this kernel does no
I/O and runs when the device set changes, so one allocation and one downcast per
capture is not measurable against hardware enumeration. What the alternative gives
up is that every driver is inspectable without its author doing anything — the
property that makes the kernel debuggable when the integration crate belongs to
someone else. The alternative also carries an uncosted friction: a driver
mirroring its own settings must find the device entity, and it holds a
`DeviceEndpoint` (a key), not an `Entity`; the kernel already owns that mapping.

**Refinement adopted:** the mirrored component is inserted only when the value
differs from what is already on the entity. Re-inserting every reconcile fires
change detection every reconcile for every observer of that component. Phase 10's
gate gains an item proving an unchanged capture does not re-trigger change
detection.

Do not relitigate this in a later cycle.

### D11 — `DeviceIdentity` is a verdict, and forbidding equality does not work (1 reviewer) · **shipped code**

Phase 2, already committed. The type is the kernel's *conclusion* about a
device — `DeviceKey` is the identity — so `IdentityVerdict` names what it is.
More substantively: the compile-fail test `device_identity_cannot_be_compared`
prohibits an operation the kernel itself needs. Banning `PartialEq` does not
enforce "an unverified record never matches" — reflection can still compare the
values — and phase 10 has to add a private equality implementation to detect
verdict transitions, **which is what phase 10's open pending decision on comparing
two verdicts without `PartialEq` is about**. **Decision: approved 2026-07-31 — `DeviceIdentity` → `IdentityVerdict`, equality
derived, the compile-fail test deleted.**

`DeviceKey` is the identity; this type is the kernel's conclusion about it, and
every variant is a conclusion. Derives become
`#[derive(Clone, PartialEq, Eq, Debug, Component, Reflect)]` with
`#[reflect(Component, PartialEq)]` — the reflect attribute is required so
reflection-based comparison routes to the derived impl instead of the structural
fallback, otherwise one type has two comparison behaviours. No `Copy`:
`Displaced` and `WrongUnit` carry a `DeviceKey`. Variants are unchanged.

The compile-fail test `device_identity_cannot_be_compared` and its trybuild case
are deleted. Grounds: banning `PartialEq` does not enforce "an unverified record
never matches another" — that rule governs how reconciliation matches a live unit
to a saved key, on keys and evidence, and is enforced in phase 9's matching step.
The ban is also not airtight, because `Reflect` can compare values structurally.
And the kernel needs the comparison: phase 10 must detect a verdict transition to
emit the identity-changed event.

Settles phase 10's pending decision on comparing two verdicts without `PartialEq`
— delete that block. Also correct phase 2's acceptance-gate line ("comparing two
`DeviceIdentity` values with `==` fails to compile") and the phase 10/11 constraint
sentence stating that verdict assertions must match on variants.

Doc comments lose the D5-retired vocabulary: "mint an authorization to arm output"
becomes "mint an authorization for in-service use", and `identified()`'s reference
to `Devices::armable` becomes `Devices::authorize_service`.

`IdentityVerdict::RestoreOnly` (the verdict) and
`ApplyPermit::RestoreOnly` (the permission it produces) share the word
deliberately.

| `EndpointDriver::Parameters` | `Configuration` | `Parameters` reads as call arguments or tuning values; the associated type is the complete device-specific value that is captured, requested, and applied. The `params` argument becomes `configuration`. |
| `CaptureResult<P>` | `CaptureOutcome<C>` | A `*Result` name promises `Ok`/`Err`, `?`, and the `Result` combinators. This enum has three domain answers and no error case. Matches the shipped `AttemptOutcome`. |
| `EndpointDriver::apply` | `start_apply` | It starts background work and returns; `apply` reads as "finishes before returning". Outside crates implement this trait, and a blocking implementation stalls the main thread — the name is the cheapest place to state the contract. `RiggingSystems::Apply`, `RoleState::Applying`, and the domain noun "an apply" are unchanged. |
| `DeviceAuthorization`, `in_service_authorized()` | `ApplyPermit`, `allows_in_service_use()` | The old predicate read circularly — an authorization is "authorized". "Permit" is established Rust vocabulary for a capability that must be *received* from an authority, which is the invariant the private constructor exists to enforce. `Attempt.authorization` becomes `Attempt.permit`; the `authorize_service`/`authorize_restore` predicates keep their verb. |

**`Configuration` over `Settings`.** One lens argued for `Settings`, citing
Bevy's `AssetLoader::Settings` for exactly this role and holding that
`Configuration` duplicates the surrounding `LastKnownGoodConfiguration` /
`RequestedConfiguration`. Rejected: those two hold *this value*, so sharing the
word is cohesion rather than collision. Under `Settings` a "captured
configuration" would be a captured `Settings`, and the reader has to learn that.

**Also settled — raised by a reviewer and declined, so it is not reopened:**

- `capture` stays. It shares a stem with `CaptureOutcome` and the shipped
  `LastKnownGoodConfiguration`; renaming the method drags all three.
- `scan` stayed in phase 6's shipped contract. Phase 7 later supersedes this
  decision: the kernel-owned scheduler calls `discover`, and not scheduling a
  reporter is the nothing-new signal after `DeviceScan::Unchanged` is removed.
- `ReportedId`, `Claim`, and `DriverContractError` stay. Each is shipped, and
  each drew one vote to rename against two or three to keep.
- `AttemptKind` does not exist and stays absent — three lenses confirmed it is in
  neither the source nor the exports. D5 deleted it so `ApplyPermit` alone
  carries the service-versus-restore distinction.

**Explicitly reviewed and kept:** the `add_` versus `register_` split (verified
against Bevy 0.19 — `add_*` installs active behavior, `register_*` records into a
registry; reporters and drivers are invoked, a scheme is only recorded); the
`DeviceReporter` / `EndpointDriver` trait names and the `-Reporter` / `-Driver`
implementer suffixes; `Reporters` / `Drivers` / `Devices` / `Attempts` /
`Bindings` as plural resources, matching `Assets<T>` and `Messages<T>` — adding
`Registry` would lengthen every signature without correcting a false inference;
`DeviceSet` versus `RiggingSystems`; `DeviceEndpoint` / `EndpointId` /
`PartName`; `Presence`; `poll`; and every error name. The theatrical frame is not
half-committed: `Rigging*` names crate-wide orchestration only and everything
beneath it is literal, which is why extending the metaphor downward was rejected.

`RiggingAppExt` was named in the same pass — see phase 6's spec.

**The prose sweep (2026-08-01).** "Provider" is retired from the plan's prose:
it had been covering three different things at once. Every occurrence is now
**reporter** (scan, evidence, `DeviceRecord`, `DeviceSet`, freshness, revision),
**driver** (capture, `start_apply`, poll, the configuration type, handles and
textures, post-start failure), or **integration crate** (a crate that registers
both, crate dependencies, plugin build, file paths). 212 sites.

Retired *type* names keep their spelling wherever they appear, because the text
that names them is recording their removal and the acceptance gates assert their
absence: `ProviderId`, `ProviderRevision`, `DeviceProvider`, `ProviderHandle`,
`ProviderBlob`, `ScriptedProvider`, `MonitorProvider`, and the
`DeviceSet.provider` → `DeviceSet.reporter` row in phase 4b's rename table.

Four names the sweep forced, recorded here rather than left to the implementer:

- `crates/hana_rigging/src/provider.rs` → **`contract.rs`** — it holds both
  traits and both erased entries, so neither role's name fits it.
- `crates/hana_clerestory/src/provider.rs` → **`reporter.rs`** in phase 14 and
  **`driver.rs`** in phase 16. Those were already two different files sharing one
  name across two phases, which the old word concealed.
- Phase 25's integration test `two_provider` → **`two_crate`**; its heading
  becomes "Two-crate integration test". It exercises two integration crates, not
  two implementations of one trait.
- Phase headings follow the same split: phase 6 is "Reporter and driver
  contracts", 12 is "clerestory monitor reporter", 14 is "clerestory's window
  driver", 16 is "Catalyst screens reporter", 18 is "Catalyst cameras reporter
  and driver" — the one crate in the v1 fleet that is both.
