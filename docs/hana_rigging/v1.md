### Doc comment checklist (invariant 11)

- A type or method says **what situation it exists for** and what goes wrong without it.
- Every enum variant says **what the system or the user would observe**, with the concrete device that motivates it. A variant comment that only rephrases the variant name is a defect.
- Where a kernel rule overrides a policy, **the policy's own comment states the override**.
- Where a name was chosen against a plausible alternative, **the rejected name and reason belong in the comment** when the alternative would mislead.
- A `#[non_exhaustive]` attribute **states why it is there**; its absence needs no comment.

The test: a reader who has not read this plan can answer, from the doc comments alone, why the type exists, what each choice makes the system do, and which choice fits their device.

Before a phase's acceptance gate passes, its new public types are read once against the four charter values and against invariants 2, 3, 4, and 7. A type that encodes an invariant the compiler can check beats a runtime check.

Two identifiers, and confusing them is the bug this crate exists to prevent:

```rust
/// Runtime handle. Opaque, process-local, `Copy`, cheap to compare. Never persisted.
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug, Reflect)]
pub struct DeviceId(u64);

/// Durable designation. Stable, human-readable, migratable, no Rust type paths.
///
/// The nested `id` is the whole point: the variant, not a string, says whether
/// the identifying value is proof or a hint, so a caller cannot lose that
/// distinction by copying a field.
#[derive(Clone, PartialEq, Eq, Hash, Debug, Serialize, Deserialize, Reflect)]
pub struct DeviceKey {
    /// Sort of unit: display, audio interface, DMX universe, HID panel.
    pub kind: DeviceKind,
    /// Where the identifying value came from, and therefore what it licenses.
    pub id:   DeviceIdSource,
}

/// How this unit came to be identified. **This is the trust level.**
#[derive(Clone, PartialEq, Eq, Hash, Debug, Serialize, Deserialize, Reflect)]
pub enum DeviceIdSource {
    /// The unit reported this value itself — a USB serial the hardware exposes,
    /// a monitor serial in its EDID. Proof of which physical unit this is, and
    /// the only source that can ever arm output.
    Reported { scheme: SchemeName, value: ReportedId },
    /// Derived by hana from descriptors, because the unit exposes nothing unique
    /// to itself — the port-derived camera id, the serial-less display UUID.
    /// A hint: it may restore a saved configuration, it never drives output.
    Synthesized { digest: Digest },
}
```

`DeviceId` wraps a `u64` issued by a monotonic counter on the `Devices` resource (phase 8), incremented once per newly-seen `DeviceKey` and never reused within a process — a handle that outlives its device stays dangling rather than silently naming a different one. It exposes no constructor outside the crate and no accessor for the integer; `Debug` prints it, nothing else reads it.

`DeviceId` gets `Reflect` and **no serde**, and its field is private. It is never persisted, and it appears in exactly **one** place on an entity: its own single-field component, so the handle is visible to BRP and reachable from the entity without a side-table lookup. It appears in no other component and inside no other type — `DeviceIdentity` carries no handle. The verdict answers *which unit is this* and nothing else; a caller holding a verdict already had the entity or the key it looked the device up by.

That one-component rule is what enforces never-persist. Moonshine serializes reflected components field-by-field without needing `Serialize`, so a `Reflect`-without-serde marker would not prevent persistence; what prevents it is the handle occupying a single named component excluded from the persisted set, rather than being scattered through types that each have to stay clean. Since that is a configuration exclusion rather than a structural impossibility, **the persistence test is mandatory**: save a device entity, assert the serialized output contains no `DeviceId`.

Three validated newtypes rather than bare strings, each with a **private field and a checked constructor**:

- `SchemeName` — names an identity space. Registered at app-build time so a typo fails at phase 8's ingest boundary instead of silently minting a second device. Two providers naming one scheme are asserting they mean the same identity space; that is the migration hinge and the co-report join (phase 8).
- `ReportedId` — the value the unit reported. Opaque to the kernel, meaningful only inside its scheme.
- `Digest(u64)` — the synthesized value. A `u64`, not a `String`: it is an FNV-1a hash, which is 64 bits, and a fixed-width integer makes a malformed digest unrepresentable while dropping two heap allocations.

**Scheme validation splits into two boundaries, because one of them is not reachable from serde** (gate G10). A derived `Deserialize` on `DeviceKey` constructs a `SchemeName` directly and bypasses any checked constructor, and an app-build-time registry is not visible to a deserializer at all:

- **Syntax** lives in the newtype, enforced by a hand-written `Deserialize` that runs the same check as the constructor. A malformed name fails at parse time, wherever it is parsed.
- **Registration** lives in a `RegisteredSchemes` resource populated at app-build time. Every deserialized key is validated against that resource **before** its state is published. That validation runs at phase 8's ingest boundary, the first place a key enters kernel state — phase 1 has no such boundary, so it ships `RegisteredSchemes::validate` as a checked method with unit coverage and nothing calls it yet (post-phase decision B).

Registering the same name twice from two providers is legal — it is the co-report assertion, so the gate checks registration and syntax, never uniqueness. Tests: a syntactically malformed name fails to deserialize; a well-formed but unregistered name fails `RegisteredSchemes::validate`; a name registered by two providers is accepted.

`DeviceKind` is `#[non_exhaustive]` — a camera integration should not need a laser arm — with a comment stating why. Variants at minimum: `Display`, `Camera`, `AudioInterface`, `DmxUniverse`, `HidPanel`. Its `compile_fail` doctest asserting downstream wildcard arms moves here from `hana_hardware/src/key.rs`, which phase 21 deletes; it must land in Repo A before G2 is established. `verify.sh test` runs `--lib` only, so express it as a `trybuild` case rather than a doctest — a doctest gate would never execute.

### Phase 2 — Identity evidence and the verdict enum  · status: done (59519f9e)

#### Work Order

**Goal:** the kernel can say what the platform reported about a unit and what identity verdict that evidence supports.

**Spec:**


Every identifier the platform can supply — reported serial, OS unique id, attachment path, vendor/product/model, synthesized digest — is retained on the device record even though only the strongest becomes the key. Absence is a named variant, never `Option`:

```rust
pub enum ReportedSerial {
    Provided(ReportedId),
    /// Permanent for this hardware — not a bug to fix.
    NotExposedByUnit,
    /// The platform has no API to ask. A different unit on a different OS may report one.
    PlatformCannotReport,
}
```

The identity verdict is computed at reconciliation rather than carried as raw evidence, so it can never contradict the key. It derives **no `PartialEq`**: comparing two verdicts is never the right question, and its absence makes the wrong call fail to compile at the obvious spelling. That is an API deterrent, not a guarantee — Bevy's `Reflect` derive supplies structural `enum_partial_eq`, so a caller reaching through `Reflect` can still compare two `Unverified` values and get `true`. The rule that two unidentified devices never match each other is enforced where it matters, in phase 8's reconciliation, which pairs saved keys against live units and never treats an `Unverified` verdict as a match candidate.

```rust
pub enum DeviceIdentity {
    /// A `Reported` key matched a live unit uniquely. The only verdict that can
    /// mint an arm authorization.
    Proven,
    /// A `Synthesized` key matched uniquely. Enough to put a saved configuration
    /// back — a window returning to its monitor — and never enough to drive
    /// output. This is the everyday verdict for webcams and serial-less panels.
    RestoreOnly,
    /// A human assigned this address. Authoritative by construction; the unit
    /// reports nothing and the patch *is* the identity.
    Authored,
    /// A saved key matched nothing, but a unit of the right kind sits in the same
    /// slot on the same transport. Neither absent nor confirmed. Needs a human.
    Displaced { saved: DeviceKey },
    /// A human authored this binding and the unit itself reports something else.
    /// The saved key matched; the unit sitting in it is the wrong one. Never
    /// armable — driving a misidentified fixture is how pan data reaches a dimmer.
    WrongUnit { authored: DeviceKey },
    /// Not identified: absent, not unique among live units, or the platform
    /// could not be asked. Carries which of those it was, because they lead to
    /// different policy. Prohibits automatic action.
    Unverified(UnverifiedReason),
}

impl DeviceIdentity {
    /// Identity only — *do we know which unit this is*. **Not** the policy predicate:
    /// arming also requires presence and claim, folded in `Devices::armable`.
    pub fn identified(&self) -> bool {
        matches!(self, Self::Proven | Self::RestoreOnly | Self::Authored)
    }
}
```

`UnverifiedReason` must include `NotUniqueInScan` (the duplicate-key disarm of phase 8), plus absence and platform-cannot-report cases. `DeviceIdentity` is `#[non_exhaustive]` — applications match on it.

### Phase 3 — Presence, claim, capabilities, device records, scans, and endpoints  · status: done (00bada98)

#### Work Order

**Goal:** the kernel can hold what a provider reports — a whole-set scan of a device forest — and can express an N-bindings-to-1-device endpoint.

**Spec:**

```rust
pub enum Presence {
    /// Provider asserts the unit is there and usable.
    Present,
    /// Provider asserts the unit is gone.
    Absent,
    /// Provider cannot tell — remote node silent, transport down.
    /// Distinct from `Absent`: collapsing them either resurrects retired
    /// outputs or destroys live ones.
    Unreachable { since: Duration },
}

/// How a provider names the unit it is reporting. Two cases rather than an
/// `Option<DeviceKey>` per invariant 7: *I can name this durably* and *I
/// recognise this unit but cannot name it* lead to different merge behaviour,
/// and a provider forced to mint a key it does not have would put a fabricated
/// identity into the durable key space.
pub enum ReportedAs {
    /// The provider minted a durable key for this unit.
    Keyed(DeviceKey),
    /// The provider sees the unit but has no durable name for it. It
    /// contributes evidence only, joined to a keyed report on `os_id`.
    /// Match evidence that joins to nothing yields no device.
    MatchEvidenceOnly,
}

/// One unit as a provider currently sees it. Providers report evidence only —
/// there is no `identity` field, because the identity verdict is the kernel's
/// conclusion from comparing this record against the saved set (phase 8), and a
/// provider that could assert its own verdict could assert `Proven` for a unit
/// that reported nothing.
pub struct DeviceRecord {
    pub reported_as: ReportedAs,
    /// Parent link. Authored devices hang off their interface; child devices off
    /// their host. `None` = root. Says "this hangs off that" and never names a bus.
    ///
    /// This is the one sanctioned `Option` in the crate: invariant 7 forbids
    /// `Option` where absence carries meaning worth distinguishing, and a root
    /// device has exactly one way to have no parent. There is no
    /// `PlatformCannotReportParent` case to lose.
    pub transport: Option<DeviceKey>,
    pub presence:  Presence,
    /// Exclusive-ownership state. Provider-asserted exactly like `presence` and
    /// orthogonal to it: a device can be `Present` and `Contended`.
    pub claim:     Claim,
    /// What this unit can do, as this provider sees it. Phase 8 unions these
    /// across co-reporters and inserts them onto the entity as components.
    pub capabilities: Capabilities,

    // Retained evidence. Reconciliation reads every one of these; the key keeps
    // only the strongest, and the rest are what let a `Displaced` verdict be
    // distinguished from a `WrongUnit` one.
    /// What the unit published about itself, or why it published nothing.
    pub serial:    ReportedSerial,
    /// The OS's own handle for this unit — `CGDirectDisplayID`, an
    /// `IOKit` registry id. Stable within a run, never persisted.
    pub os_id:     OsDeviceId,
    /// Where it is attached: USB port path, display slot, network node.
    /// Phase 8 compares this to decide `Displaced`.
    pub attachment: AttachmentPath,
    /// Vendor, product, and model strings as reported. Never identifying on
    /// their own — two identical webcams report identical triples — and the
    /// input to a `Synthesized` digest.
    pub descriptor: DeviceDescriptor,
}
```

There is no fifth evidence field for the synthesized digest. `DeviceIdSource::Synthesized` already carries it inside `key`, and `descriptor` is the input the provider derived it from — so a `Synthesized` key holds its digest and a `Reported` key retains none.

```rust
/// What a provider has to say about the devices it can see.
pub enum DeviceScan {
    /// Nothing was scanned since the last report, so there is nothing to say.
    /// The kernel keeps the set it already holds.
    ///
    /// Normal for every provider on most frames — cameras enumerate every two
    /// seconds, HID every ten, and clerestory only when the display
    /// configuration changes. Returning this builds nothing.
    Unchanged,
    /// A scan completed.
    Complete(DeviceSet),
}

pub struct DeviceSet {
    pub provider: ProviderId,
    /// Whole current set, not deltas. Absent devices are omitted.
    /// Parent links make this a forest; the kernel ingests roots first.
    pub devices:  Vec<DeviceRecord>,
    /// Monotonic per provider; the kernel folds these into a global revision.
    pub revision: ProviderRevision,
}
```

`OsDeviceId`, `AttachmentPath`, and `DeviceDescriptor` each follow invariant 7: a named variant for *this platform has no such concept* and for *the platform has the concept and reported nothing*, never `Option`.

`Claim` is defined here, not with the policy enums, because it is a hardware fact a provider observes — the same category as `Presence` — and nothing about it is authored:

```rust
/// Provider-asserted, exactly like `Presence`. Orthogonal to it.
pub enum Claim {
    /// This substrate has no notion of exclusive ownership.
    NotApplicable,
    /// We hold it.
    Held,
    /// Claimable; we have not claimed it.
    Free,
    /// Another process holds it, or holds it such that ours would be useless.
    Contended { holder: ClaimHolder },
    /// The platform refuses. The remedy is a permission grant, not a replug.
    Blocked { gate: PermissionGate },
}

/// Who holds a contended device. Named rather than `Option<String>` because
/// *the platform will not say who* and *nobody is named because the string was
/// empty* are different diagnostics, and invariant 7 forbids collapsing them.
pub enum ClaimHolder {
    /// The platform named the holding process.
    Named(String),
    /// The platform reports contention but will not identify the holder —
    /// macOS camera contention reports exactly this.
    Unidentified,
}
```

`PermissionGate` is a named enum, not a string: the kernel matches on it to decide whether a remedy exists, and its variants are the permission classes a provider can hit — camera access, screen recording, input monitoring, plus a provider-supplied catch-all carrying its own detail.

**Capabilities live in their own crate, `hana_works`, which both the kernel's consumers and every provider depend on.** They are not kernel-owned and not provider-owned. A closed kernel-side vocabulary would violate invariant 1 — the kernel would have to know what a backlight is — and putting the shared types in a provider crate is worse: `Illuminants` already spans a Stream Deck backlight, an LED ring, and a DMX dimmer, so a DMX provider would have to depend on the Stream Deck crate to report light. The crate holds the shared component types and nothing else: no systems, no plugin, no dependency on `hana_rigging`.

`Capabilities` is the provider's declaration, carried on the record and erased so a provider can also declare a capability private to itself — a Stream Deck's NFC reader has no second implementer and does not belong in the shared crate:

```rust
/// The capability components this provider claims for this unit. Erased because
/// the kernel must carry types it cannot name — including ones private to a
/// single provider — without becoming a registry of device classes.
pub struct Capabilities(Vec<Box<dyn Reflect>>);
```

Phase 8 unions these across co-reporters and inserts them onto the device entity. Two mechanisms it needs, both built here: **attach**, which turns an erased value into a component insert through the type registry rather than through `insert_by_ids` and its unsafe `ComponentId`/`OwningPtr` pairing; and **compare**, which decides whether two co-reporters agree about a capability using `PartialReflect::reflect_partial_eq`. Disagreement disarms (phase 8). Every capability type registers with `App::register_type` in its owner's plugin build, and attach fails loudly for a type that did not — an unregistered capability is a build error the first scan surfaces, not a silent drop.

`ProviderId` is an opaque `u32` newtype, issued by the provider registry (phase 6) in registration order and stable for the process. `ProviderRevision` is a `u64` the provider increments on every completed scan; it is per-provider and monotonic, and the kernel folds the set of them into one global `RiggingRevision` (phase 8). Neither is persisted. The name is `ProviderRevision`, never `TopologyRevision` — the counter belongs to the provider that scanned, not to a topology.

Two rules about the forest, and no more. Both are enforced by reconciliation, so this phase states them and phase 8 tests them:
- Presence is **conjunctive down the chain** — a child whose parent is `Unreachable` is `Unreachable`, not `Absent`.
- A parent's departure retires descendants **through the same keyed path**, so nothing depends on a live entity existing.

Endpoints, forced by the audio model (speaker entities each map to one hardware output channel, so one registration per device is wrong):

```rust
/// What a registration actually binds to.
pub struct EndpointRef { pub device: DeviceKey, pub slot: Slot }

/// Provider-defined, opaque to the kernel.
/// "0" | "ch/7" | "u1/c37" | "key/3" | "encoder/1" | "nfc"
pub struct Slot(String);
```

One display is one device with one slot — the degenerate case, and it costs screens and cameras nothing.

`Cohesion` **does not ship in v1** (see the deferred register). Do not define it here: an enum with one reachable value and no test is worse than its absence, and adding it later is purely additive because it attaches to a group rather than to any existing type.

### Phase 4 — Availability and the three policy enums  · status: done

#### Work Order

**Goal:** the kernel can express what to keep, when to act, toward what state, and what to do when an attempt is abandoned or a local session dies.

**Spec:**

```rust
pub enum Availability {
    /// No registry entry; the binding is forgotten on departure.
    Unregistered,
    /// Keep the last intentional configuration across absence, and act per `Act`.
    Retained(Act),
}

pub enum Act {
    /// Report only. Never touch the device.
    Never,
    /// Re-apply only when explicitly asked.
    OnRequest,
    /// Re-apply automatically when the *verified* unit returns.
    OnReturn,
}
```

Default is `Unregistered`. **"Re-apply what you never kept" is unrepresentable rather than rejected at construction** — there is no cell to write it in, so there is no constructor to reject it and no public field through which to bypass one. The four legal states: `Unregistered` = not registered; `Retained(Never)` = remember, report, never touch; `Retained(OnRequest)` = remember, re-apply on demand; `Retained(OnReturn)` = re-apply when the verified unit returns.

A declared safe state — answering *toward what state*: blackout for a light rig, shutter closed for a projector — is deferred; see the deferred register. It has no v1 producer, and as an erased `Box<dyn Reflect>` field it would break the `Reflect` derive, make `Availability` non-`Clone` while phases 4 and 8 both need a copy, and force the public-field shape that lets callers write the illegal cell. When the first device needs one, it arrives as a `Retain` axis alongside `Act`. Its constraint is recorded in the deferred register: departure application is **provider-executed** — the kernel supplies the declared value and the fact of departure, and the provider decides whether energizing anything to reach that state is safe. A kernel that "fails safe by applying the safe value" has reintroduced the laser bug under a reassuring name.

`Availability` and `Act` are **not** `#[non_exhaustive]`. Their variant sets are the policy vocabulary this crate defines; an application matching on them exhaustively is the intended use, and a new variant is a breaking change the kernel should be forced to acknowledge. `#[non_exhaustive]` is reserved for the sets that grow with hardware the kernel cannot enumerate — `DeviceKind`, `DeviceIdentity`, `UnverifiedReason`, `DeviceFault`.

Policy is fixed at registration — a change is cancel plus re-register — and is copied where entity loss cannot erase it.

The `Arming` safety veto is deferred; see the deferred register. There is no interlock device in v1, so it would ship with no producer and an unvalidated shape. Every arming decision resolves through `Devices::armable()` alone (phase 8), so adding the axis later is a one-function edit plus one enum.

The three policy enums:

```rust
pub enum RetryOn {
    /// The device set changed since the failed attempt. Cannot loop forever —
    /// no change, no retry.
    NewRevision,
    /// Fixed cadence, for failures that resolve without any device change.
    Interval(Duration),
}
```

Both variants are required. A camera held open by another application becomes free when that application quits: no device appears or disappears, so the revision never advances, so a revision-gated retry would never fire. Conversely `Interval` alone would hammer a device whose failure is permanent until the set changes. `RetryOn` is a **plain enum, no `#[non_exhaustive]`** — downstream constructs it and the kernel matches it, so no downstream match exists to break, and a `_` arm is exactly where a new variant gets silently swallowed.

```rust
/// What to do with a device when an attempt is abandoned and we can still
/// reach it.
///
/// Only consulted when the attempt was abandoned because the device set
/// changed. A lost claim makes reverting impossible and an arming veto makes it
/// unsafe, so the kernel decides both of those itself without reading this.
#[derive(Clone, Copy, Debug, Default)]
pub enum OnAbort {
    /// Leave the device in whatever partial state it reached and let the next
    /// reconcile drive it.
    ///
    /// Right for a device whose reconfiguration is slow or visible — a
    /// projector lamp takes tens of seconds — because the set change that
    /// abandoned this attempt is about to produce a new target anyway.
    #[default]
    LeaveAsIs,
    /// Re-apply the configuration captured before the attempt started.
    ///
    /// Right when a half-applied state is itself wrong: a window parked
    /// between two monitors is visibly broken, not merely stale.
    Revert,
}
```

The abort-cause table is a **kernel rule, not policy**: claim lost ⇒ never revert (reverting is impossible, not undesirable); arming vetoed ⇒ never revert (reverting re-sends a configuration that may have been energized, re-energizing a device whose interlock just opened); revision changed ⇒ consult `OnAbort`.

```rust
/// What to do when the local session for a still-present device dies on its
/// own — a window destroyed by the compositor, a capture session invalidated
/// across sleep, a HID handle closed by a bus reset.
///
/// Distinct from device absence, which the availability axes handle, and from
/// an abandoned attempt, which `OnAbort` handles. Nothing unplugged and
/// nothing was in flight.
#[derive(Clone, Copy, Debug, Default)]
pub enum OnSessionLoss {
    /// Open a new session and re-apply the captured configuration, without
    /// involving application code.
    ///
    /// A camera panel goes black for a frame after the laptop wakes and then
    /// repopulates. Runs as an ordinary attempt, so `RetryOn` gates it — a
    /// camera the OS has wedged will not be reopened in a loop. Reuses the
    /// published image handle, so bound materials survive the rebuild.
    #[default]
    Recreate,
    /// Report the loss and do nothing else, leaving the response to
    /// application code.
    ///
    /// For a device where the replacement is a decision, not a repeat — a
    /// window that should be placed differently the second time, or one the
    /// user should be asked about first.
    ReportOnly,
}
```

### Phase 5 — Attempts, captured configuration, and faults  · status: todo

#### Work Order

**Goal:** the kernel can name one attempt, say where a rig stands in recovery, report an outcome, hold the configuration to return to, and classify a failure.

**Spec:**

```rust
pub enum RecoveryPhase {
    /// Registered, unit present, nothing owed.
    Nominal,
    /// The unit is gone and its configuration is retained. Nothing can be
    /// attempted until it returns. `Act::Never` rests here indefinitely.
    AwaitingDevice,
    /// The unit is back and verified, and an apply is in flight to take it back.
    Recovering(ApplyId),
    /// That apply passed its deadline. Not an error and not a failure — the
    /// device may still be converging — so it is retried rather than reported.
    PastDeadline(ApplyId),
    /// Retired by key. Later presence must not revive it.
    Retired,
}

/// The **role**, not the hardware: an app-assigned handle for "the thing this
/// binding is for" that outlives every unit that ever fills it. `WindowKey` and
/// `SecondaryCameraId(u32)` are both this, spelled twice. Distinct from
/// `DeviceKey`, which names a unit — a rig survives the unit being unplugged
/// and replaced, which is the whole point.
pub struct RigKey(String);

/// Names one attempt. A `u64` from a monotonic counter on `Applys` (phase 8),
/// never reused within a process — a late `poll` for a finished attempt must
/// resolve to nothing, not to whatever attempt took its slot.
pub struct ApplyId(u64);

/// Which authorisation the kernel minted for an attempt. Recorded on the
/// `Apply` so a provider that drives output under a restore authorisation is a
/// contract violation the kernel can name after the fact rather than a silent
/// arming. Phase 6's `ApplyAuthorization` token is the runtime carrier; this is
/// the durable record of which case it was.
pub enum ApplyKind { Arm, Restore }

pub struct Apply {
    pub id:       ApplyId,
    pub rig:      RigKey,
    pub endpoint: EndpointRef,
    /// Which authorisation case this attempt was minted under.
    pub kind:     ApplyKind,
    /// The identity this attempt was authorised against.
    /// Re-checked on every poll; a mismatch invalidates it.
    pub expected: DeviceId,
    /// Scan revision at authorisation. A newer revision invalidates.
    pub revision: ProviderRevision,
    /// Bounds the attempt end to end, not per step.
    pub deadline: Instant,
}

/// The provider's sole outcome report. Split in two so the completion event
/// carries an `ApplyOutcome` and cannot be constructed with `Pending`.
pub enum ApplyProgress { Pending, Finished(ApplyOutcome) }

pub enum ApplyOutcome { Done, Failed(DeviceFault), Aborted, Substituted }

/// The configuration a provider last successfully applied to one device.
///
/// The kernel stores this without interpreting it — knowing what a monitor or
/// camera configuration *is* would violate the membership test. Each variant
/// holds the provider's own `Parameters` erased to a reflected value, which the
/// provider recovers by downcast and BRP can display for debugging.
pub enum Captured {
    /// Safe to overwrite from live readback.
    Writable(Box<dyn Reflect>),
    /// Absent or mid-attempt: live readback would poison the intent.
    Frozen(Box<dyn Reflect>),
}
```

`ApplyOutcome::Aborted` is **terminal and never auto-retries** — it is what a safety gate closing mid-attempt produces, and collapsing it into `PastDeadline` would re-permit the retry.

**Coverage audit.** This enum is the only outcome vocabulary, so every scenario lands in exactly one case:

| Scenario | Case |
|---|---|
| Working, inside the deadline | `Pending` |
| Working, past the deadline | still `Pending` — overrun is **kernel-side** state. `poll` takes only an `ApplyId` and the kernel owns the timing (phase 6), so the provider neither knows nor reports it; the kernel counts the overrun against the configured budget. |
| Landed as requested, or within the provider's own tolerance (60 fps satisfied at 59.94) | `Finished(Done)` |
| Landed, but on a different device or slot than requested | `Finished(Substituted)` |
| The provider tried and the hardware refused | `Finished(Failed(fault))` |
| Overrun budget exhausted | `Finished(Aborted)` |
| The provider went stale past its freshness lease | `Finished(Aborted)` |
| The device departed mid-attempt | `Finished(Aborted)` |
| A safety gate closed mid-attempt | `Finished(Aborted)` |

`Aborted` therefore has four producers and no auto-retry from any of them; the reason a caller needs is on the device (`DeviceFault`, `Presence`), not multiplied into this enum.

`Captured` is `Box<dyn Reflect>`, never `Box<dyn Any>` and never `ProviderBlob(Vec<u8>)` — bytes are only needed for a value that leaves the process, and this one does not. Reflect costs nothing extra and buys BRP inspectability; reflection blindness already cost a phantom regression during the asset-loading work. Suppression is **per key** — a global pause is a live bug in clerestory today and must not be carried across.

`RecoveryPhase` is **not** `#[non_exhaustive]`, for the same reason `Availability` and `Act` are not: it is the kernel's own vocabulary and an application matches it exhaustively. `DeviceFault` is, because failure modes arrive with hardware the kernel cannot enumerate.

`DeviceFault` is the typed failure classification that replaces prose. It is `#[non_exhaustive]` — new hardware brings new failure modes — and must at minimum distinguish contention, permission denial, absence, and transport error, carrying a provider detail string alongside: the classification is kernel-readable, the detail is not. This retires `VIDEO_UNAVAILABLE_LIKELY_CAUSE`, a guessed cause shipped as UI.

### Phase 6 — Provider contract, type-erasing registration, plugin and set  · status: todo

#### Work Order

**Goal:** a provider written in another crate can be registered with `app.add_device_provider(..)`, and the kernel calls it once per tick inside `RiggingSet::Collect` without ever naming its type.

**Spec:**

One associated type — the provider's own configuration vocabulary — and five methods, one defaulted:

```rust
pub trait DeviceProvider: Send + Sync + 'static {
    /// The configuration this provider accepts and reads back — its own type, in
    /// its own vocabulary. `Reflect` is required so the kernel can hold it
    /// erased in `Captured` and BRP can show it; an ordinary derive satisfies it.
    type Parameters: Reflect;

    /// Stable across runs. Namespaces `DeviceKey.kind`; appears in diagnostics.
    fn id(&self) -> ProviderId;

    /// Called once per `RiggingSet::Collect`. Whole-set, not deltas.
    ///
    /// `&mut World` means this runs on the main thread with exclusive access, so
    /// the provider may reach `!Send` state through `world.non_send_resource_mut`
    /// and touch thread-locals the kernel never touches. It must **not** block:
    /// enumeration that talks to hardware belongs on a thread the provider owns,
    /// and `scan` drains that thread's channel. A provider with nothing new
    /// returns `DeviceScan::Unchanged`.
    fn scan(&mut self, world: &mut World) -> DeviceScan;

    /// Read the live endpoint's configuration for capture.
    /// Called only while `Captured::Writable`.
    fn capture(&mut self, world: &mut World, endpoint: &EndpointRef)
        -> CaptureResult<Self::Parameters>;

    /// **Start** driving the endpoint to the state `params` describes, and return
    /// immediately — every real open in this codebase is backgrounded with a
    /// channel outcome, and a blocking apply would mandate a main-thread stall.
    /// **Absolute, not differential** — the provider must not assume a known
    /// starting state.
    fn apply(&mut self, world: &mut World, endpoint: &EndpointRef,
             params: &Self::Parameters, apply: ApplyId, auth: ApplyAuthorization);

    /// Polled each reconcile until it resolves. The kernel's end-to-end deadline
    /// bounds the whole sequence, so a provider that must reset then render
    /// reports `Pending` between the two and cannot claim it is done early.
    /// The provider supplies what counts as arrived — a delivered frame, a stable
    /// position, a completed image write. The kernel only times it.
    /// The sole outcome report. Judging "close enough" is the provider's:
    /// a camera asked for 60 fps and given 59.94 returns `Done`; a window that
    /// lands on a different display returns `Substituted`. That comparison is a
    /// private helper, not a trait method — only the provider knows the
    /// tolerance, and `Reflect` offers no equality to default it from.
    fn poll(&mut self, world: &mut World, apply: ApplyId) -> ApplyProgress;
}
```

`capture` returns a named outcome, not `Option` — invariant 7:

```rust
pub enum CaptureResult<P> {
    /// Read back successfully.
    Read(P),
    /// The endpoint is reachable but exposes no readable configuration.
    /// Permanent for this device; the kernel stops asking.
    NotReadable,
    /// A transient read failure. The kernel keeps the previous `Captured` value
    /// and asks again next reconcile.
    ReadFailed(DeviceFault),
}
```

`ApplyAuthorization` is a **private-constructor token minted only by the kernel** and the only token `apply` accepts. It is one opaque type with two private cases:

```rust
/// Proof that the kernel authorized this apply, and for what. Opaque: the cases
/// are private, there is no public constructor, and a provider cannot fabricate
/// one — so arming from an unproven identity cannot compile.
pub struct ApplyAuthorization(Purpose);

enum Purpose {
    /// Minted from `Proven` or `Authored`. The device may be driven.
    Arm,
    /// Minted additionally from `RestoreOnly`. The device may be returned to a
    /// previously captured configuration and nothing more.
    Restore,
}
```

One type rather than two because `apply` is the only entry point that acts on a device, and a second object-safe entry point for restore would duplicate the whole erased-dispatch path to express one bit. The kernel records which case it minted in `Apply.kind` (phase 5's `ApplyKind`, written by the kernel in phase 10 when it mints the token), so a provider that drives output under a `Restore` token is a contract violation the kernel can name after the fact. `ApplyAuthorization` exposes a public predicate — `is_arm() -> bool` — for providers whose apply path genuinely differs; providers that treat both alike ignore it.

**The erased dispatch is fallible.** The adapter downcasts the `Box<dyn Reflect>` in `Captured` back to `Self::Parameters` before calling `apply`, and a mismatched type there is a provider-contract violation, not an unrepresentable state — two providers can register with `Captured` values crossed. Every erased method returns `Result<T, ProviderContractError>`; the kernel logs the error, fails the attempt with `ApplyOutcome::Failed`, and continues. It never unwraps — the workspace denies `unwrap_used`, and a downcast failure must not take the app down.

**Providers are borrowed out of the world, not from it.** The erased provider list lives in a `Providers` resource, and calling `scan(&mut World)` while holding a borrow of that resource aliases the world. The kernel calls every provider inside `world.resource_scope::<Providers, _>(..)`, so the list is temporarily removed from the world for the duration. The contract that follows, stated on the trait: a provider must never insert, remove, or read the `Providers` resource — it is absent while the provider runs, and touching it panics. A provider must also not mutate kernel-owned state through the `&mut World` it is handed: not `Devices`, not `Applys`, not `RiggingRevision`, and not the device entities or their kernel components. It reports through its return value and nothing else. A provider that half-writes kernel state and then returns an error leaves the kernel inconsistent with no way to unwind, which is exactly the failure the whole-set scan model exists to avoid.

A provider panic is fatal and is not caught. Catching it would leave the kernel holding half a scan from a provider it can no longer trust, and `resource_scope` would have to reinsert a provider that just proved it can panic. A provider that cannot proceed returns a fault.

**`fn migrate` is struck.** It existed to move a persisted provider blob forward across versions; nothing persists a provider blob any more. The two real migrations are versioned and owned where the data lives — clerestory's window state v3 → v4 (phase 15) and catalyst's saved `HardwareKey` values (phase 20).

Registration erases the associated type:

```rust
app.add_plugins(RiggingPlugin)
   .add_device_provider(MonitorProvider::default());
```

An associated type cannot appear in a signature reached through `dyn`, so the typed provider above cannot itself be a `Box<dyn DeviceProvider>`. `add_device_provider` wraps it in an adapter — **written once inside `hana_rigging`** — that implements a separate object-safe trait. The provider author never writes the erased form and the kernel never names a type it cannot know. `dyn` is required not for dispatch cost, which is irrelevant at a few calls per reconcile, but because providers live in other crates: a static enum registry would make `hana_rigging` name `hana_clerestory` and invert the dependency.

The kernel holds `Vec<Box<dyn ErasedDeviceProvider>>` and calls `scan` on each inside a public system set. **The sets are API, not an implementation detail** — a consumer has to be able to sequence its own work against the kernel's phases, and once a consumer outside these two repos sequences against them these four names become effectively permanent, so treat them as settled from here:

```rust
/// Chained in `Update` in this order.
#[non_exhaustive]
pub enum RiggingSet {
    /// Every provider's `scan` runs. Nothing has been diffed yet.
    Collect,
    /// The kernel diffs, computes verdicts, mirrors components, and emits its
    /// events at the end of this set.
    Reconcile,
    /// **The consumer slot.** The kernel schedules nothing here. Identity and
    /// availability are decided and no `apply` has started, which is the only
    /// interval in which a consumer can compute the parameters it is about to
    /// request — clerestory's fallback machine (phase 13) builds window targets
    /// here.
    Prepare,
    /// Attempts start, poll, retry, and escalate.
    Apply,
}
```

`#[non_exhaustive]` so a later phase can add a set without breaking anyone's `.after(..)`. `scan(&mut World)` is exclusive by signature, which is what lets a winit provider reach main-thread-only state while a HID provider drains a channel from a thread it owns — neither is dragged onto the other's execution model.

**A provider validates its own environment in `Plugin::finish`, not in `build`.** Bevy runs `finish` after every plugin has built, so a provider that needs `WinitPlugin` and its `WinitMonitors` resource can assert their presence there and fail with a named error regardless of whether the consumer added it before or after `DefaultPlugins`. Asserting in `build` makes correctness depend on plugin insertion order, which the consumer controls and the provider cannot see.

Reconcile is **timer backstop plus OS-event fast path**, not the reverse: there is no hot-plug anywhere in the hidapi stack, and monitors — which do get OS events — are the exception in the reference set.

### Phase 7 — Bindings: registration, routing, and the rig lifecycle  · status: todo

#### Work Order

**Goal:** an app can say "this rig wants that endpoint, served by that provider, with this availability and recovery policy, at these parameters" — and can replace or retire that binding — with nothing yet reconciled.

**Spec:**

`RigKey` (phase 5) names a role and `EndpointRef` (phase 3) names where it lives, but nothing binds them. Without a binding record the kernel cannot serve the case it exists for: clerestory and `xcap` both report an equal `DeviceKey` for one display with different `Parameters` types, and `EndpointRef` carries no route, so the kernel cannot tell which provider to hand an apply to, cannot associate captured parameters with a rig, and cannot implement replace-in-place.

```rust
/// One authored binding: a role, where it goes, who serves it, how it behaves
/// when the unit leaves, and what to ask for.
#[derive(Reflect)]
pub struct Binding {
    pub rig:          RigKey,
    pub endpoint:     EndpointRef,
    /// Which provider serves this endpoint. Routing is by provider, never by
    /// capability: two providers can report one `DeviceKey` and take different
    /// `Parameters`, so capability is not a discriminator. Capability routing
    /// is additive later and changes nothing here.
    pub provider:     ProviderId,
    pub availability: Availability,
    pub retry:        RetryOn,
    pub on_abort:     OnAbort,
    pub on_loss:      OnSessionLoss,
    /// What to ask the provider for, erased for the same reason `Captured` is:
    /// the kernel carries a type it cannot name. The adapter downcasts it to
    /// `Self::Parameters` and reports `ProviderContractError` when the binding
    /// names a provider that does not take this type.
    pub requested:    Requested,
}

/// Authored parameters, erased.
pub struct Requested(Box<dyn Reflect>);
```

`Requested` erases exactly the way `Captured` does and takes the same reflection treatment phase 5 settled — see phase 5's pending decision. `Box<dyn Reflect>` is itself not `Reflect` in bevy 0.19, so `Binding` cannot derive `Reflect` over a bare erased field; whatever phase 5 chose for `Captured` (field-level `#[reflect(ignore)]`, or a hand-written opaque impl) is applied verbatim here. Do not invent a second mechanism, and do not drop the derive — `Bindings` must stay a reflected resource.

The registry and its four operations, all on a `Bindings` resource keyed by `RigKey` with a reverse index from `DeviceKey` so reconciliation can find every rig affected by one device without scanning:

- `register(Binding) -> Result<(), BindingError>` — fails if the `RigKey` is already bound. Silently overwriting would strand an in-flight attempt with no owner.
- `replace(RigKey, Binding) -> Result<(), BindingError>` — the cancel-plus-re-register path. Aborts any in-flight `Apply` for that rig with `ApplyOutcome::Aborted` before the new binding takes effect, so the provider is never polled against parameters nobody asked for.
- `retire(&RigKey)` — removes the binding and emits `RetireRig`. Idempotent: retiring an unbound rig is not an error, because retirement races departure.
- `get(&RigKey) -> Option<&Binding>` and `rigs_for(&DeviceKey) -> impl Iterator<Item = &RigKey>` — the two read paths reconciliation uses.

**A binding names a `DeviceKey`, never a `DeviceId`.** The key is durable and survives the unit being unplugged; the handle is not. Resolution happens per reconcile through `Devices::resolve` (phase 8), which is what makes a rig outlive the unit filling it. A binding whose endpoint resolves to an armable device drives `RigAvailable`; one that resolves to nothing drives `RigAwaiting` (phase 10). Both are emitted from reconciliation, not from this phase — registering a binding for a device that is not there yet is normal and must not error.

- `crates/hana_rigging/src/binding.rs` — new; `Binding`, `Bindings`, `Requested`, `BindingError`, the four operations and the reverse index

### Phase 8 — Reconciliation: scan ingest, co-report merge, and duplicate detection  · status: todo

#### Work Order

**Goal:** pushing whole-set scans in produces one merged device set — and two providers reporting one display produce one device.

**Spec:**

Device-as-entity, provider-as-trait-object, state mirrored in a keyed resource:

```rust
// One entity per device. Every component reflected, so BRP sees all of it.
#[derive(Component, Reflect)] pub struct Device;   // marker
#[derive(Component, Reflect)] pub struct Live;     // present ∧ claim usable
// plus DeviceKey, DeviceIdentity, Presence, Claim, Availability,
// RecoveryPhase, and the capability components — which the kernel inserts from
// DeviceRecord.capabilities atomically with the entity.

/// Durable state cannot live only on the entity — keyed retirement must work
/// with no entity alive. The entity mirrors the registry for querying and BRP.
///
/// Keyed by `DeviceId`, not `DeviceKey`: the durable key is two strings, and
/// hashing both on every policy query from application code is the cost that
/// matters. One map resolves a durable key to a handle; everything else is
/// keyed by the copyable handle.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct Devices {
    ids:    HashMap<DeviceKey, DeviceId>,
    state:  HashMap<DeviceId, DeviceState>,
    entity: HashMap<DeviceId, Entity>,
    /// Issues `DeviceId`. Monotonic, never reused within a process.
    next:   u64,
}

/// One global revision, folded from every provider's `ProviderRevision`.
/// Incremented once per reconcile in which **any** provider returned
/// `DeviceScan::Complete`, whether or not the contents changed.
///
/// Counting completed scans rather than content changes is what makes a
/// same-frame `Absent → Present` pair observable: the set looks identical at
/// both ends, so a content hash would report no change and the panel would
/// stay blank.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct RiggingRevision(u64);

/// In-flight attempts. Issues `ApplyId` from a monotonic counter, never reused.
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct Applys {
    in_flight: HashMap<ApplyId, Apply>,
    next:      u64,
}
```

**`DeviceId` appears on the entity in exactly one single-field component and nowhere else.** It is BRP-visible there and excluded from the persisted component set; it is carried inside no other type, and `DeviceIdentity` in particular holds no handle. Moonshine serializes reflected components field-by-field without needing `Serialize`, so a `Reflect`-without-serde marker would not prevent persistence — a single named exclusion does, and one component is a thing you can exclude and test.

**Kernel limits are one reflected resource with user-settable fields**, not constants:

```rust
#[derive(Resource, Reflect)]
#[reflect(Resource)]
pub struct RiggingLimits {
    /// How far past `Apply.deadline` an attempt may keep running before the
    /// kernel abandons it. Bounded overrun rather than a hard cut: a projector
    /// or a camera that is genuinely converging should be given slack, and an
    /// attempt that will never finish must not run forever.
    pub apply_overrun: Duration,
    /// How stale a provider's last completed scan may be before the kernel
    /// stops trusting it. Past this, that provider's devices become
    /// `Unreachable` and its in-flight attempts abort.
    pub max_report_age: Duration,
}
```

Both default to values stated in their doc comments and are overridable by inserting the resource before `RiggingPlugin`. Being a reflected resource makes them BRP-tunable at runtime, which is how a slow projector gets diagnosed without a rebuild.

Reconciliation, once per tick in `RiggingSet::Reconcile`, after every provider has scanned in `Collect`:

1. Call `scan` on each registered provider inside one `resource_scope` over `Providers`. `DeviceScan::Unchanged` means keep the set already held — build nothing.
2. **If every provider returned `Unchanged`, return here.** No allocation, no diff, no revision bump, no events. This is the common frame — cameras enumerate every two seconds, HID every ten, clerestory only on a display-configuration change — so the settled path must cost a loop over the provider list and nothing more.
3. **Apply the freshness lease.** A provider whose last `Complete` scan is older than `RiggingLimits::max_report_age` is stale: its devices become `Presence::Unreachable`, and its in-flight attempts finish `Aborted`. Staleness is per provider, so one wedged provider never invalidates another's devices. A provider that has never completed a scan is not stale — it is starting up — until its first `Complete` arrives.
4. Ingest each `DeviceSet` **roots first**, following `transport` parent links, so the forest is well-formed before presence is folded. Presence is conjunctive down the chain; a parent's departure retires descendants through the keyed path, so nothing depends on a live entity existing.
5. **Merge co-reported devices**, in a **single pass** that groups every provider's records by key through one `HashMap::entry` — never a pairwise join across provider lists, which is quadratic in device count. The same pass yields duplicate detection for step 6. Records carrying an **equal `DeviceKey`** from different providers merge into one device with multiple contributing providers. One physical display enumerated by both winit and `xcap` is one device, not two. This retires the 200 pt geometry tolerance instead of relocating it, and it works only because `SchemeName` is a shared registry (phase 1): two providers naming the same scheme are asserting they mean the same identity space.

   The same pass has a second half for records reported as `ReportedAs::MatchEvidenceOnly` (phase 3): they carry no key, so they group by `os_id` against the keyed records already in the map. A match-evidence record that joins to nothing **yields no device** — never a minted key, never a device of its own. This is invariant 3 applied to the merge: a provider that can recognise a unit but not name it contributes to an existing device or contributes nothing.

   **The `os_id` join is over `OsDeviceId::Reported(_)` and nothing else.** `OsDeviceId` derives `PartialEq` across all three variants (`crates/hana_rigging/src/evidence.rs:11-22`), so two records that each reported *no* handle satisfy `os_id == os_id` and would fuse into one device — exactly the plausible-fallback failure invariant 3 exists to end. A `MatchEvidenceOnly` record whose `os_id` is `PlatformHasNoConcept` or `PlatformReportedNothing` joins nothing and yields no device, the same as a `Reported` handle that matches nothing.
6. **Duplicate keys within one scan disarm themselves.** Every member of a duplicate set becomes `Unverified(NotUniqueInScan)`. This is where the rule that two unidentified units never match each other is enforced: matching runs over keys and evidence, and a record whose verdict is `Unverified` is never a match candidate for another. It is what stops a weak scheme — two identical webcams under one device name — from presenting as `Proven`.
Steps 7 through 9 — the verdict, the diff, and the entity projection — are phase 9.

### Phase 10 — Apply lifecycle, retries, and escalation  · status: todo

#### Work Order

**Goal:** the kernel starts, bounds, re-validates, retries, and escalates attempts.

**Spec:**

Attempt lifecycle inside `RiggingSet::Apply`:

1. A rig in `AwaitingDevice` whose device becomes armable (or restorable, for a restore) starts an attempt — `apply` is called and returns immediately, the phase becomes `Recovering(ApplyId)`.
2. Every tick, `poll` is called for each in-flight attempt. **Before** calling it, re-check `Apply.expected` against the device's current `DeviceId` and `Apply.revision` against the current revision. A mismatch invalidates the attempt — it never lands on a different unit.
3. `Apply.deadline` bounds the attempt **end to end, not per step**, so a provider that must reset then render has both steps inside one attempt with one settle result and cannot report done between them. Past the deadline the phase becomes `PastDeadline(ApplyId)` — not an error and not a failure, so `poll` keeps being called. Past `deadline + RiggingLimits::apply_overrun` the kernel stops asking and finishes the attempt `Aborted`. That is the bounded-overrun rule: slack for a device that is genuinely converging, a ceiling for one that never will.
4. Abandonment follows the kernel rule table from phase 4: claim lost ⇒ never revert; arming vetoed ⇒ never revert; revision changed ⇒ consult `OnAbort`.
5. Retry is gated by `RetryOn`. `ApplyOutcome::Aborted` is terminal and never auto-retries.
6. Repeated-failure escalation counts **consecutive attempts, not frames** — that is why it is kernel work and arrival evidence is not — and **self-clears on recovery**.

Reacquisition keys on `RiggingRevision`, not elapsed time. An `Absent → Present` cycle shorter than the settle window must not be swallowed: each completed scan advances the revision, so a departure and a return reported in the same frame produce two increments and fire, even though the before and after sets are identical. A content hash would report no change there and the panel would stay blank. This is a kernel test case, not a kernel state — a `Resumed` variant would be a provider field wearing a kernel type.

Retry pacing lives here, replacing both hand-rolled pacers the migration deletes. Kernel state is plain `Send` data, so "any rig awaiting?" is an ordinary run condition — the providers stay non-send, the *pacing* stops being.

Keyed retirement works with **no live entity**, and is ordered so explicit retirement beats simultaneous device loss.

### Phase 15 — clerestory persisted window state v3 → v4  · status: todo

#### Work Order

**Goal:** a v3 window-state file loads, restores its windows to the same physical monitors, and is rewritten as v4 with classified keys. **This is gate G8.**

**Spec:**

Conservative conversion with self-heal. Per-version frozen structs: the v3 shape is copied into a `v3` module and frozen there, the v4 shape is the live one, and the conversion is a plain function between them. This is the `windows.ron` `version: 2` pattern grown up.

Conversion rules:

- A v3 entry whose monitor identifier can be classified as reported becomes `DeviceIdSource::Reported { scheme, value }`.
- A v3 entry whose identifier cannot be classified becomes `Synthesized { digest }` — which yields a `RestoreOnly` verdict at runtime, meaning the window still returns to its monitor and still never drives output. That is the correct conservative outcome, not a degradation.
- **Self-heal:** an entry that cannot be converted at all is dropped with a logged warning rather than failing the load. A show that will not open is worse than a window in the wrong place.
- The file is rewritten as v4 on the next save, not eagerly on load.

Do not attempt to make `CGDirectDisplayID` durable across reboots — phase 12 settled that it is a within-run join key and never a persisted one, and the conservative conversion is what makes an old file holding one survivable.

Which tier a v3 entry converts into depends on phase 12's platform investigation: it decides which schemes exist, so it must be finished before the conversion is written. A v3 entry recording a value from a scheme the investigation did not establish is unconvertible and takes the self-heal path.

### Phase 24 — Stream Deck device thread, enumeration, and claim  · status: todo

#### Work Order

**Goal:** a Stream Deck MK.2 or XL enumerates as a kernel device, is claimed, survives replug, and classifies its failures.

**Spec:**

This is the only genuinely new code — enumeration, claim, reconnect, and error classification, with nothing to copy. It is also the only multi-slot consumer, which is why it is an acceptance target and not a feature.

Constraints the HID survey fixes:

- **One model only: the Stream Deck +**, which is the unit on hand. `Original 0x0060` and the Mini family are separate protocols, one undocumented by Elgato; scope to the + and let the abstraction prove itself on the *second* model rather than the first. Shape the crate around **protocol families** (~6 of them), not the 17 product ids — a Corsair keyboard runs the Stream Deck gen2 protocol, so protocol ≠ vendor.
- **Read the slot counts off the device descriptor, never from a constant.** The + is documented by Elgato as 8 LCD keys (2×4), 4 push-turn dials, and a touch strip above the dials; hana's operator recalls 4 keys and 4 dials. The enumeration step settles this by measurement: whatever `elgato-streamdeck` reports for the connected unit is the slot count, and a hardcoded 8 or 4 that disagrees with the hardware is a defect either way. Record what the device actually reports in this phase's notes.
- **No tokio.** `elgato-streamdeck`'s `async` feature pulls tokio and the workspace has none. Use the blocking API on `IoTaskPool`. New dependencies: `elgato-streamdeck` (brings `hidapi` and `image`) plus `crossbeam-channel`.
- **The owned device thread is not optional.** `HidDevice` is `!Sync`, no OS event stream exists because the usage page is vendor-defined, and Elgato's recommended input poll is 50 ms. One thread owns the handle, channels carry commands in and reports out, a `PreUpdate` system drains, `AppExit` releases.
- **Availability is polled, never notified.** There is no hot-plug anywhere in the hidapi stack; re-enumerate on a timer and treat a read-loop error as the disconnect signal.

Device facts this provider must handle:

1. **Sleep/resume is a distinct failure mode from unplug** and fires constantly on laptops. On host suspend the HID handle breaks and must be closed and reopened with a full re-render. This is a **provider concern with no new kernel state**: a provider that knows its handle is dead reports `Absent`, then `Present` on reopen, and the normal reacquire path runs. The full re-render is free, because `Act::OnReturn` re-applies the last intentional configuration — which for a panel *is* the key images.
2. **The identity token can change under us.** Stream Deck serials have been observed mutating across replug, and serial length changed 12→14 across a firmware revision. That is the `Displaced` verdict. v1 emits `IdentityChanged` (phase 11) and logs; a human replugs. Adopting the candidate rewrites the saved key and is **deferred**; see the deferred register.
3. **Post-claim reset is a provider obligation the kernel already compels.** On open, a zeroed reset report must be written to abort a half-finished image transfer left by a *previous owner* — presence does not imply pristine, and the previous owner may have been another process or a crashed run of hana. `apply` is specified as absolute, not differential, so this is how one provider discharges an obligation every provider has. The end-to-end deadline means reset-then-render sits inside one attempt with one settle result.
4. **Claiming is a contest with no good outcome.** hidapi seizes by default on macOS, and a seizing open *succeeds* over the already-running Elgato app while silently disabling its input queues. Contention is the **normal operating state, not an error**, and "we opened it" does not mean "we should have". Report `Claim::Contended` where it can be detected; where it cannot, that is a known producer weakness, not a reason to guess.
5. **Every transport failure arrives as one opaque string** — contention, unplug, and permission denial all surface as `HidError::HidApiError { message }` wrapping a hex `IOReturn`. Classify into `DeviceFault` and keep the raw string as provider detail. This is the second device kind to land in the same hole that produced `VIDEO_UNAVAILABLE_LIKELY_CAUSE`.
6. **A blocked device is indistinguishable from an absent one.** On Apple-silicon laptops the "Allow accessory to connect" prompt makes a denied device simply not enumerate, so `Claim::Blocked` is only inferable from *history* — we hold a saved key, the platform has a permission gate, and nothing matching enumerated. That inference needs the durable `DeviceKey`.

Resolved and worth not re-litigating: **Input Monitoring TCC does not apply.** Apple's kernel gates only Keyboard, Mouse, and TouchPad usages; the Stream Deck is a Consumer-page device, so unsigned `cargo run` reaches it with no entitlement and no prompt.

**Files:**
- `crates/hana_streamdeck/` (Repo A) — new kind crate: `Cargo.toml`, device thread, enumeration, claim, fault classification, `DeviceProvider` impl. The manifest inherits workspace metadata, carries `[lints] workspace = true`, and depends on `hana_rigging.workspace = true`

## Post-phase review decisions

Findings from the phase dual reviews that changed the plan rather than the code under review. Each entry records the decision, not the deliberation.

- **A — `verify.sh` strictness is global.** The shared delegate verifier hard-errors when nightly `rustfmt` or `cargo nextest` is missing, for every repository that uses it, with no per-repo opt-in. Invariant 13 is enforced machine-wide. The edit lives in `~/.claude/scripts/delegate/verify.sh` and is outside every phase commit.
- **B — G10's registration half is enforced in phase 8, not phase 1.** Phase 1 has no boundary where keys enter, so `RegisteredSchemes::validate` ships as a checked method with unit coverage and nothing calls it. Phase 8's ingest path is the first place an unregistered name can actually fail, and its acceptance gate now carries that requirement. Phase 1's acceptance line was corrected to state what it verifies rather than asserting a startup check that does not exist.
- **C — the validated newtypes are opaque to reflection.** `SchemeName`, `ReportedId`, and `Digest` carry `#[reflect(opaque)]`, so reflection treats each as one atomic value routed through the registered `Serialize`/`Deserialize` rather than exposing its private field. Without it, any reflection writer — remote inspection, scene load — sets the inner string directly and bypasses the checked constructor, which is the same hole G10's hand-written `Deserialize` closes for persisted text. `Digest` gains nothing but is included so the three identity wrappers behave alike. Field-level reflection access to the inner values is given up; nothing uses it.
- **D — `DeviceId` keeps `#[reflect(Component)]`; exclusion is enforced at the save path.** Entity saving runs through reflection rather than serde, so the absence of serde on `DeviceId` does not by itself keep it out of saved output — the save builder must deny it. That requirement already sits in phase 9's acceptance gate. Dropping the component reflection registration would make the exclusion structural but would also hide the handle from live inspection, which is the primary view for diagnosing why one physical device drew two handles.

## Deferred register

Nothing here ships in v1 and none of it is a phase. Each item names the condition that unblocks it. Phases 1–26 must not pre-build any of it: shipping a type with no consumer is correct only when adding it later would force an audit of existing call sites, and no item here meets that bar — `Arming` is one axis inside `Devices::armable()`, a declared safe state is one axis on one enum, `Cohesion` attaches to a group that does not exist yet.

- **`Cohesion`** — `enum Cohesion { None, SameDevice, SameHost }`, checked by the kernel and never explained to it, covering the one-interface-one-machine constraint for a speaker group and a laser array on one DAC. Deferred because no v1 device has a cross-device grouping constraint and the only reachable value is `None`. **Trigger:** the first multi-device group. Purely additive — it attaches to a group, not to any existing type.
- **Reassignment** — re-binding N entities to a swapped unit. Deferred because no v1 kind does it; `EndpointRef` keeps it expressible. **Trigger:** the audio work, or a Stream Deck replaced mid-show.
- **`Unreachable` decay timing** — when an `Unreachable` device becomes `Absent`. Deferred because there are no remote nodes in v1, so the kernel treats `Unreachable` as not-armable and **never auto-decays**. **Trigger:** the first Art-Net or networked node.
- **`Displaced` adjudication** — who answers a `Displaced` verdict, and whether an unanswered one survives restart. v1 emits `IdentityChanged` and logs; a human replugs. Adopting the candidate rewrites the saved key, which is what the mutating-serial bug needed and did not have. **Trigger:** a UI that can ask.
- **Attachment path as a stored third evidence axis.** The *evidence* question is closed — AVFoundation's `uniqueID` is a USB location id, so a port-derived value is attachment evidence carrying a `Synthesized` key, and phase 3 keeps it on the record as `AttachmentPath`. What stays deferred is giving it **its own stored axis** at rest. It must never be merged into `DeviceKey`. **Trigger:** a case where port position must be queried independently of identity.
- **The associated-type `Identified` trait.** Write it only when two *implemented* load paths share a batch-resolve-validate-publish body **with compatible failure policy** — all four conditions: both hold deserialized durable references aside unpublished; both resolve a whole batch against current registries; both validate cross-references across the batch; both publish atomically with compatible failure policy. Condition 4 fails today on purpose: a missing device is normal operation, a missing tool definition aborts the load. Then extract only the interface that body calls.
- **`DeviceKey` document persistence.** Rigging produces durable keys in v1 and serde is all it commits to; the document format waits on [[versioned save format]]. Rigging must not block on another in-progress issue.
- **`Arming`, the safety veto** — the type itself, not just its producer. Not built in v1: no interlock device exists, so the shape would be unvalidated and unexercised. **Trigger:** the first laser or interlocked fixture. Adding it is a fourth axis inside `Devices::armable()`, the sole arming decision point, plus one enum. Breaking for crates.io consumers, which the exhaustive-enum policy accepts.
- **A declared safe state** — again the type itself. Not built in v1: no v1 device has a declared safe state, and the erased `Box<dyn Reflect>` field it needed broke the `Reflect` derive, `Clone`, and the unrepresentable-illegal-state property. **Trigger:** the first light rig or projector with a required return state. Adding it reintroduces a `Retain` axis alongside `Act` — `Availability::Retained(Act)` becomes `Retained { retain, act }` — over the same erased-value mechanism the capability components use. Departure application stays provider-executed; the kernel never drives a device to a safe state itself.
